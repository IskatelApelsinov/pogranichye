# 002 — Claude: серверная симуляция, генерация мира и контракты

## Результат (2026-11-16)

Полный аудит, карта подсистем и список разрывов — `3-dev/docs/AUDIT-002-SERVER-WORLD.md`.
Коротко:

- **Самый значимый разрыв**: ADR 0006 §2 требует два различимых режима появления
  (демо-котёл / открытый мир с выбором региона), но `server.reserveBody` их не знает —
  новый игрок получает первое свободное взрослое тело по возрастанию ID, без фильтра по
  области. Это новая фича с UX-решением (как выбирается режим), не точечный баг — зафиксировал
  в аудите и НЕ чиню втихую, нужно отдельное согласование/task_ai, как и с 011.
- Переходы фронтира, бесшовный мир, детерминизм генерации, экономика/NPC/рынок,
  персистентность и масштаб — проверены по существующим тестам, разрывов с концепцией не
  найдено (ссылки на конкретные тесты в аудите).
- Вода не моделируется как геометрия — уже известное, задокументированное ограничение
  (comms 0254/протокол), не новая находка.
- Нет offline catch-up симуляции при простое сервера — открытый архитектурный вопрос,
  не мой уровень решения без владельца.
- Мелкое исправление контракта: добавлена явная перекрёстная ссылка в
  `ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md` между `/api/world` (рендер-геометрия, знание разработчика)
  и `known_places` (карта знаний персонажа) — оба факта были задокументированы раньше, но
  раздельно.

**Не входило в этот аудит**: Unity PlayMode (не трогал код/не заявляю проверенным);
реализация режима появления (решение владельца); офлайн catch-up (архитектурное решение).

**Исполнитель:** Claude  
**Подсистема:** `1-server/` (Go), серверная симуляция и генерация.  
**Приоритет:** после ознакомления с задачей 001; серверный аудит можно выполнять параллельно, не меняя контракт без согласования.

## Цель

Проверить, что сервер действительно реализует живой непрерывный мир из исходной концепции, а не только выдаёт Unity отдельные игровые сцены/заготовки. Сервер остаётся единственным авторитетом мира.

## Источники

Прочитать `AI_WORK_RULES.md`, `3-dev/docs/СКЕЛЕТ-ЖИВОГО-МИРА.md`, `3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md`, все относящиеся ADR (особенно 0003 и 0006), README сервера и последние сообщения comms.

## Что проверить

1. Два режима входа по ADR 0006: demo/starter cauldron и open-world start. Это два входа в одну симуляцию, с общей моделью персонажа/мира/сохранения; не удалять ни один режим.
2. Переходы между регионами/фронтиром при физическом перемещении: куда ведёт движение в каждом направлении, когда и кем открываются новые области, идемпотентность и сохранение.
3. Генерацию глобального мира: seed/determinism, биомы, рельеф, вода, растительность/ресурсы, дороги/тропы, дикие места, поселения и связность. Проверить, не заканчивается ли содержательный мир пустой плоскостью/горизонтом.
4. Контракты terrain/chunk/layout/world/map: какие данные сервер выдаёт для рендера, какие данные предназначены только для служебного manifest, а какие являются картой знаний персонажа.
5. Карта игрока должна вытекать из серверного состояния знаний/наблюдений (rumoured/located/visited/known и текущая модель проекта), а не из полного developer manifest.
6. NPC/экономика/ресурсы/лошади/рынок: авторитетное состояние, конечные запасы, действия, reqid/idempotency, ошибки и обновление frame.
7. Время, offline simulation, persistence/reload, deterministic RNG и масштабирование регионов/AOI.

## Ограничения

- Не менять Unity-код и не заявлять, что проверен Unity PlayMode.
- Не менять концепцию, ADR 0003/0006 или вводить отдельный мир для демо.
- Не вводить новую сетку/кэш/протокол параллельно текущему без ADR и согласования.
- Не увеличивать лимиты NPC как замену корректной spatial AOI.
- Не выдавать клиенту developer manifest как карту его персонажа.

## Критерии готовности

- Карта серверных подсистем, API, persistence и контрактов с конкретными путями/символами.
- Тесты/прогоны, подтверждающие или опровергающие физическое открытие фронтира и непрерывное путешествие в любом направлении.
- Список разрывов «концепция → код → тест → клиентский контракт».
- Минимальные серверные исправления отдельными PR и сообщения ChatGPT в `3-dev/comms/` при изменении клиентского контракта.
- Отдельно описать, какие данные/seed/descriptor должен получать Unity для визуализации серверно-сгенерированной местности.
