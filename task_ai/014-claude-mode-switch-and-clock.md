# 014 — Claude: выбор режима появления в тонком клиенте и видимые игровые часы

**Исполнитель:** Claude  
**Подсистема:** Go server + thin-client/web.  
**Связано:** ADR 0006, task_ai/002, task_ai/005, 3-dev/docs/ПЛАН-ВОССТАНОВЛЕНИЯ-ДЕМО.md.

## Контекст от владельца

1. В тонком клиенте не видно переключения режима старта/появления. По ADR 0006 игрок должен иметь выбор между демо-котлом и полноценным стартом во внешнем мире. Важно проверить не только наличие UI, но и то, что выбор реально влияет на серверный spawn.
2. В игре не хватает понятного отображения времени суток/дня. Иногда создаётся впечатление, что постоянно ночь. В Unity уже есть серверная синхронизация визуального цикла через top-level hour, но в thin-client нужен явный индикатор дня и времени, а серверный ход часов надо проверить.

## Часть A — режимы старта (основной приоритет)

Пройти весь путь от UI до серверного состояния:
- регистрация/создание профиля → выбор режима → выбор региона/страны для внешнего мира (если поддержано текущей моделью) → создание/резервирование персонажа → первый world frame;
- повторный вход существующего игрока должен продолжать прежнего персонажа и сохранение, а не показывать новый выбор и не создавать новую душу;
- проверить, что выбранный режим сохраняется надёжно и сервер действительно использует его при spawn;
- демо-режим должен вести в одну из стартовых деревень котла;
- full-game/open-world режим должен вести во внешнее поселение/стартовую точку внешнего мира, среди обычного населения, не в котёл;
- один персонаж, один Entity ID, единое сохранение. Никаких двух независимых миров/персонажей для одного аккаунта.

Проверить UI тонкого клиента: сейчас переключатель отсутствует или не доходит до регистрации. Добавить понятный экран выбора с двумя равноправными вариантами:
- «Демо — стартовый котёл» (короткое пояснение);
- «Полная игра — внешний мир» (короткое пояснение и регион/страна, если сервер реально предлагает список допустимых вариантов).

Не показывать выбор режима при обычном входе уже существующего персонажа. Не подменять выбор фиктивным локальным переключателем: выбранное значение должно передаваться серверу, валидироваться и влиять на резервирование/создание тела.

**Ограничения:**
- Следовать ADR 0006; не менять его смысл.
- Не использовать op:travel как телепорт или выбор режима.
- Не делать произвольный spawn по координатам от клиента.
- Не создавать второй аккаунт/душу ради второго режима.
- Если текущая модель аккаунта/персонажа не позволяет смену режима до создания тела, предложить минимальный совместимый контракт и описать миграцию; wire менять только аддитивно и покрыть тестами.
- Не ломать старых клиентов и уже существующие профили. Если для legacy-профиля режим неизвестен, определить безопасное поведение и документировать его.

## Часть B — часы и ощущение постоянной ночи

Проверить серверный источник времени:
- где задаются скорость игрового времени и начальная дата/час;
- сколько реальных минут занимает игровой час и полный игровой день при текущих настройках;
- как часы продолжаются между reconnect/restart и что происходит при отсутствии игроков;
- проверить, нет ли ошибок/застревания в ночных часах и не зависит ли ход часов от частоты кадров/числа подключённых клиентов.

В thin-client добавить заметный, но компактный индикатор «День N · HH:00» из серверного состояния. Использовать authoritative day/hour, не системное время устройства. Если кадр сейчас передаёт только hour, проверить, откуда корректно получить номер дня; не вычислять его из клиентских секунд. При необходимости добавить только аддитивное поле в frame и обновить протокол/fixtures/тесты.

Не менять скорость игрового времени или расписания NPC по собственной инициативе. Если темп действительно слишком быстрый/медленный или стартовое время даёт длительную ночь, дать измерения и конкретную рекомендацию владельцу до изменения баланса.

## Проверки и критерии готовности

1. Тесты backend на оба spawn mode, выбор региона (если есть), повторный вход, стабильность Entity ID и отсутствие дублирования персонажа.
2. Тесты на то, что новый выбор режима не влияет на уже существующие профили/персонажей.
3. Thin-client: ручной smoke checklist для регистрации в каждом режиме и повторного входа; UI не должен терять выбранное значение при ошибке/возврате назад.
4. Clock: тесты прогресса часов/дня, сохранения при reconnect/restart (в рамках текущей архитектуры), описание реального коэффициента времени.
5. Thin-client показывает серверные день и часы, корректно обновляет их с кадрами; при отсутствии данных честно показывает «время неизвестно», а не системное время.
6. Go: go test ./... и go vet ./... в 1-server; перечислить команды и результаты.
7. Обновить протокол и fixtures только при реальном изменении wire. Unity не менять.
