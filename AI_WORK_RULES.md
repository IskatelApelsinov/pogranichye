# Постоянные правила разработки для всех ИИ и чатов

Этот файл — обязательная точка входа для ChatGPT, Claude, Qwen и любого другого помощника, работающего с репозиторием. Прочитать его ДО предложений, аудита и изменений кода. Затем открыть документы, перечисленные ниже.

## 1. Концепция проекта — не обсуждается заново

**Пограничье — серверная симуляция живого мира. Unity и thin-client — только клиенты/окна в эту симуляцию. Это не самостоятельная Unity-игра, к которой мы постепенно прикручиваем сервер.**

- Go-сервер — единственный авторитетный источник состояния и правил мира: время, сущности, NPC, их разум/память/цели/действия, экономика, ресурсы, перемещение, события, сохранение и продолжение жизни мира.
- Unity — толстый визуальный клиент: получает состояние/события, отображает мир, собирает ввод игрока и отправляет намерения серверу. Не принимает авторитетных игровых решений, не симулирует NPC и не создаёт реальные игровые сущности локально.
- Thin-client — ещё один клиент того же персонажа и мира. Никаких отдельных миров, персонажей или правил для разных клиентов.
- Accounts знает пользователей и связывает пользователя с персонажем, но не владеет симуляцией мира.
- Генерация мира, его физическая/экономическая логика и знания персонажа принадлежат серверу. Клиенты могут процедурно собирать только визуальное представление по серверным данным/seed/описаниям; визуальная генерация не становится источником игровой истины.
- Мир должен жить и развиваться независимо от подключённого клиента, в рамках серверной модели времени, сохранения и симуляции.

## 2. Документы-источники истины

Перед архитектурными решениями читать и соблюдать:
1. `3-dev/docs/СКЕЛЕТ-ЖИВОГО-МИРА.md` — несущий документ концепции.
2. `3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md` — действующий контракт.
3. Все действующие ADR в `3-dev/docs/adr/`.
4. `3-dev/comms/README.md` и актуальные сообщения в `3-dev/comms/`.
5. README корня и README соответствующих подсистем.

Не переписывать и не заменять существующие решения собственными предположениями. Если документы противоречат друг другу или текущему коду — зафиксировать расхождение и предложить решение, не выбирать молча. ADR не отменять без отдельного решения владельца проекта.

В частности, соблюдать ADR 0003 и ADR 0006: режим стартового котла/демо и режим открытого мира — два предусмотренных способа входа в одну симуляцию. Не удалять котёл, не превращать его в отдельную игру и не заменять оба режима случайным спавном без явного решения владельца.

## 3. Разделение ответственности

- Claude: Go-сервер, симуляция, генерация мира на сервере, сохранение, серверные тесты, серверные API и контракты.
- ChatGPT: Unity-клиент, клиентская архитектура, интеграция с контрактом, ревью межсистемных изменений и координация.
- Qwen: отдельные, явно назначенные задачи Unity-клиента, визуализации, стриминга, UI, ввода и клиентской производительности в собственной ветке `agent/qwen-unity-workstream`. Не менять сервер и wire contract без отдельной передачи/согласования.
- Владелец проекта: продуктовые решения и запуск/проверка приложения; может выполнять задачи из `task_human/`.
- Межсистемные изменения обсуждать через `3-dev/comms/` и контракт. Не просить одного помощника проверять сборку/тесты чужой подсистемы, если у него нет соответствующей среды.

Это рабочее распределение, а не повод игнорировать интеграцию: каждый обязан описывать точку стыка, формат данных, владельца и критерий проверки.

## 4. Как работать

- Работать маленькими проверяемыми шагами. Сначала установить факты по репозиторию, затем менять код.
- Не натягивать архитектуру обычной Unity-игры на серверную симуляцию. Не дублировать серверную логику в клиенте.
- Не создавать параллельные системы координат, кэши, реестры сущностей, генераторы мира или контракты без проверки уже существующих.
- Не заявлять «готово», «проверено», «работает» без фактического результата. Различать написано, статически проверено, покрыто тестом и проверено в работающем клиенте.
- Не делать массовый рефакторинг ради красоты. Сначала карта ответственности и зависимости, затем безопасное поэтапное разделение.
- Любое изменение должно иметь объяснение: зачем, какие файлы/системы затронуты, как связано с серверной симуляцией, как проверено, что осталось.
- Не менять продуктовую концепцию и не создавать новые ADR без необходимости и согласования.
- Все технические имена в новом коде (типы, методы, свойства, поля, локальные переменные) писать на английском. Существующие JSON wire keys не переименовывать ради стиля.

## 5. Система задач — обязательна

Работать через две папки в корне:
- `task_ai/` — задания ChatGPT, Claude и Qwen. В каждом файле явно указать исполнителя и подсистему.
- `task_human/` — задания владельцу проекта.

Формат имени: `NNN-краткое-название.md`. Первая строка незавершённого задания — `!В работе`. При полном выполнении исполнитель заменяет первую строку ровно на `!Выполнено`. Если заблокировано — `!Блокировано` и причина. Не ставить `!Выполнено`, пока критерии приёмки не выполнены.

В задании должны быть: цель, контекст/ссылки, конкретные шаги, ограничения, критерии готовности, результат/заметки и кто следующий владелец. Не смешивать в одном задании серверную и клиентскую реализацию, если можно разделить на независимые задачи с явным контрактом.

При начале новой итерации каждый ИИ:
1. Читает этот файл и документы-источники.
2. Смотрит незавершённые задачи в обеих папках.
3. Выбирает следующую задачу своего профиля, не дублируя работу другого.
4. После работы обновляет файл задачи и создаёт/обновляет handoff для второго исполнителя при необходимости.
5. В ответе владельцу кратко сообщает сделанное, commit/PR, реальные проверки и следующий шаг.

## 6. Если открыт новый чат

Не полагаться на память чата. Начинать с этого файла и списка задач в репозитории. Этот файл — переносимый контекст проекта для любой модели и любого нового чата.
