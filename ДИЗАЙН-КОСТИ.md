# Кости и случайность «Приграничья» — архитектура (фундамент прототипа и боевой игры)

Это разбор того, КАК в игре устроена случайность, и ПОЧЕМУ именно так. На этом
строится всё: бой, добыча, погода, события, азартные игры, спавн, A-LIFE. Решение
принимается «на вырост» — чтобы не переделывать, когда прототип станет реальной игрой.

Код ядра: `world/dice.py`. Первое применение: спавн игрока (`mp._newborn`).

---

## 1. Зачем вообще отдельная система, а не `random`

Голый `random` в сетевой живущей игре создаёт четыре проблемы:

1. **Нельзя воспроизвести баг.** «У меня зверь выбил 3 шкуры, а у соседа 0» — без
   детерминизма не повторить и не отладить.
2. **Нельзя доказать честность.** В азартных играх (кости, очко, дурак на монеты)
   игрок вправе подозревать, что «казино» подкрутило. Нужна проверяемость.
3. **Хрупкий детерминизм.** Когда вся симуляция тянет числа из ОДНОГО потока,
   добавление любой мелочи (новая черта, лишний бросок) сдвигает ВСЮ последующую
   случайность. Мы это уже видели: добавили черты характера — изменились цифры всей
   симуляции. Это чинится только независимыми потоками.
4. **Клиент не должен катать кости.** Иначе читер «перекатывает» удачу. Бросок —
   только на сервере.

Поэтому случайность — это отдельная подсистема с гарантиями, а не вызов `random()`.

---

## 2. Пять свойств, которые мы требуем

1. **Детерминизм.** Один мировой сид + та же последовательность событий → те же
   исходы. Даёт отладку, тесты, реплеи, «перемотку».
2. **Независимые потоки.** У каждой подсистемы/сущности/типа события — свой поток.
   Бросок в «погоде» не влияет на «бой». Добавление системы не ломает чужую
   случайность. Это главное архитектурное решение.
3. **Сервер-авторитет.** Клиент шлёт намерение → сервер катит → присылает результат.
   Клиент никогда не генерирует игровую случайность.
4. **Доказуемая честность (для денег).** Схема commit-reveal: сервер заранее
   публикует хеш секрета, после игры раскрывает секрет — игрок пересчитывает кости
   и проверяет, что их не подменили.
5. **Переживает рестарт.** Состояние потока — одно 64-битное число; сохраняется с
   миром. После перезапуска поток продолжается, а не катится заново.

---

## 3. Движок: splitmix64 + SHA-256-сиды

- **Генератор — splitmix64**: чистая целочисленная арифметика по модулю 2⁶⁴.
  Одинаков на любой платформе и версии Python (в отличие от `random`, чья внутренняя
  реализация формально не гарантирована между версиями). Быстрый, статистически
  хороший для игр, состояние — одно число (идеально для сохранения).
- **Сид потока — первые 8 байт SHA-256** от строки `мировой_сид | ключ…`. Так потоки
  с разными ключами статистически независимы и стабильны (один и тот же ключ всегда
  даёт один и тот же стартовый сид).

> Почему не Mersenne Twister (`random`): у него состояние 2.5 КБ (дорого сохранять на
> каждый поток) и межверсионная воспроизводимость не гарантируется. Для КРИПТО-стойкости
> splitmix64 недостаточно, но нам нужна не крипта, а воспроизводимость + равномерность;
> честность денег закрывается отдельно (commit-reveal), а не стойкостью генератора.

## 4. API (world/dice.py)

**Потоки через хаб** (состояние сохраняется в мире):
```python
hub = RngHub("world-5")
hub.stream("combat", entity_id).roll(20)      # d20 для конкретной сущности
hub.stream("weather").chance(0.3)             # независимо от боя
hub.stream("loot", beast_id).roll_n(2, 6)     # 2d6 добычи
```
**Чистый бросок от ключа** (не сохраняется — однозначно привязан к событию):
```python
hub.once("daily-weather", day, village_idx).weighted([("ясно",5),("дождь",2),("буря",1)])
```
**Богатая нотация костей** (как в настолках):
```python
s.roll(6)            # один d6
s.roll_n(3, 6)       # 3d6 (сумма)
s.d("3d6+2")         # разбор выражения
s.advantage(20)      # преимущество (2 броска, больший)
s.disadvantage(20)   # помеха (меньший)
s.exploding(6)       # взрывной кубик (на максимуме катим ещё)
s.pool(6, 6, 4)      # пул: сколько из 6d6 >= 4 (система успехов)
s.weighted([...])    # взвешенный выбор
s.shuffle(list)      # Фишер–Йейтс на нашем потоке
```
**Персист:** `hub.to_dict()` / `RngHub.from_dict()` — сохраняется вместе с миром.

**Честные кости (деньги):**
```python
fair = FairDice(secret="случайный-нонс", public="Kate vs Bot|ставка10")
commit = fair.commit()         # показываем игроку ДО игры (хеш)
st = fair.stream()             # катим игру из секрета
# ... после игры:
reveal = fair.reveal()         # показываем секрет
FairDice.verify(reveal, commit)   # игрок проверяет: кости не подменили
```

## 5. Схема ключей потоков (конвенция)

Ключ потока = осмысленный путь. Предлагаемая конвенция:
- `("spawn")` — куда рождается новый игрок (персистентный, равномерно спредит).
- `("combat", entity_id)` — бой конкретной сущности.
- `("loot", beast_id, day)` — добыча (привязка ко дню — разная каждый раз).
- `("weather", shard_id)` — погода шарда.
- `("event", village_idx, day)` — дневные события деревни.
- `("gamble", table_id)` — азартная игра за столом (а лучше FairDice).
- `("alife", entity_id)` — решения A-LIFE конкретного жителя.

Правило: **в ключ кладём то, что должно делать поток независимым**. Нужен один и тот
же результат при повторе — ключ стабильный. Нужна новизна каждый раз — добавляем в
ключ день/счётчик, либо берём персистентный `stream()` (он сам двигается).

## 6. Сервер-авторитет: кто и когда катит

- Клиент НИКОГДА не присылает «я выбросил 6». Он шлёт намерение (`hunt`, `dice`,
  `card`), сервер катит из нужного потока и возвращает исход + (для честных игр)
  commit/reveal.
- Мини-игры на клиенте дают лишь **качество** (0..1) — мастерство игрока, — а не сам
  бросок. Итог считает сервер из качества + костей. Так ловкость рук влияет, но
  «перекатать удачу» нельзя.

## 7. Честность азартных игр (commit-reveal) — как будет в реальной игре

Сценарий для «очко/дурак/кости на монеты»:
1. Перед партией сервер генерирует секретный нонс, считает `commit = sha256(секрет)`
   и показывает `commit` обоим игрокам (и пишет в лог партии).
2. Колода/кости катятся из потока `FairDice(секрет, public=состав стола+ставка)`.
3. После партии сервер раскрывает `секрет`. Любой игрок (или сторонний наблюдатель)
   берёт раскрытый секрет, проверяет `sha256(секрет) == commit` и **пересчитывает все
   броски/раздачу** — убеждаясь, что они не менялись по ходу.
4. `public` включает публичные входы (имена, ставка, время), чтобы сервер не мог
   заранее заготовить выгодный себе секрет под известную руку.

Это стандарт «provably fair» казино. Ядро уже умеет (`FairDice`); осталось подключить
к играм (план миграции ниже).

## 8. План миграции (поэтапно, без поломок)

Сейчас ядро внедрено и используется для спавна. Дальше — по одному, с тестами:
1. **Азартные игры → FairDice.** `dice()`, `card`(очко), `durak`, PvP-столы: катать
   из FairDice, показывать commit в UI до игры и reveal после. Высокий приоритет —
   это прямой запрос «на этом строится реальная игра».
2. **Бой и добыча → `hub.stream("combat"/"loot", …)`.** Убирает зависимость боя от
   порядка других бросков.
3. **Погода/события/A-LIFE → именованные потоки.** Чинит хрупкий детерминизм
   симуляции (добавление системы перестанет сдвигать чужие числа).
4. **Регионовый `random.Random` → RngHub** в движке систем (`Region.rng`). Самый
   объёмный шаг; делаем последним, когда конвенция ключей устоится.

Каждый шаг — отдельный коммит с тестами на детерминизм и распределение.

- Подключено к **спавну**: деревня новичка выбирается из персистентного потока
  `spawn` — распределение по всем 10 деревням (починка «всё время Усть-Ворон»).
- Хаб сохраняется в мире (`rng` в world_save) и переживает рестарт.

## 10. Открытые вопросы к обсуждению
- Нужна ли КРИПТО-стойкость где-то, кроме денег? (Пока — нет; splitmix64 + commit-reveal
  закрывают задачи.)
- Формат показа честности игроку: показывать ли commit/reveal в UI явно, или прятать
  за кнопкой «проверить честность»?
- Привязывать ли спавн к аккаунту (стабильно) или всегда новый (сейчас — поток spawn,
  т.е. каждый новый персонаж в новом месте). Обсудим, что лучше по геймплею.
