# Сетевая часть: регистрация, БД, мультиплеер

Проработка + статус реализации. Опирается на уже построенное:
сервер-авторитетный мир, игрок = обычный агент (`Character` с `driver='player'`),
горячие/холодные поселения, игрок хранится отдельно от мира (`playerstore`).

## Статус (что уже сделано)

Решения Kate: **1 персонаж на аккаунт; перма-смерть с могилой и хроникой;
офлайн-игрок переходит под AI и остаётся в мире; гость разрешён.**

- [x] **Шаг 1 — аккаунты и сессии** (`world/accounts.py`): гость / регистрация
  (почта + pbkdf2-хэш) / вход; сессии-токены с TTL, апгрейд гостя без потери
  прогресса. Пока на JSON (прото-таблицы accounts/sessions).
- [x] **Шаг 3 (ядро) — мультиплеер-рантайм** (`mp.py`): один общий регион, много
  игроков; вход по аккаунту (1 персонаж), офлайн→AI, перма-смерть→хроника,
  со-присутствие (видно других игроков в деревне), все намерения, per-player вид,
  персист. Один тик-поток под `RLock` — намерения применяются по порядку.
- [x] **Гость — только для теста** (`GAME_ENV`): в проде (`GAME_ENV=prod`)

### Что осталось оптимизировать (замечено по ходу)
- **Пуш по изменению, а не раз в секунду.** Сейчас сервер шлёт полный снимок
  каждому раз в игровой час. Для многих игроков это N снимков/с. Дальше: dirty-флаг
  на тик (слать, только если вид игрока изменился) + дельты вместо полного снимка.
- **По потоку на соединение** (ThreadingHTTPServer + reader-поток). Ок на десятки-
  сотни игроков; для тысяч — asyncio/epoll, один цикл на много сокетов.
- **Снимок мира одной строкой.** Просто и durable, но хроника/могилы в проде лучше
  отдельными строками (канон «мир помнит» — чтобы память не зависела от снимка).
- **JSONB вместо TEXT** в Postgres — индексация по полям персонажа без распаковки.

Запуск мультиплеера: `python3 netserver.py` → http://127.0.0.1:8090
Прод-режим без гостя: `GAME_ENV=prod python3 netserver.py`
На SQL-хранилище: `GAME_STORAGE=sqlite python3 netserver.py`
(одиночная песочница `python3 thin.py` сохранена).

## 1. Главный принцип (уже заложен)

**Мир один и общий, живёт на сервере; клиент — лишь окно.** Клиент не считает
игру, он шлёт *намерения* («наколоть дров», «идти в Кривичи», качество мини-игры),
а сервер решает исход и рассылает изменения. Это уже так в прототипе (`thin.py`
шлёт на `/api/*`, считает `world/`). Для мультиплеера это и есть фундамент:
нельзя доверять клиенту — только намерению.

**Игрок — это агент мира.** Мы специально сделали игрока обычным `Character`.
Значит «много игроков» = просто много агентов с `driver='player'` в тех же
деревнях, где живут NPC. Ничего нового в симуляции не нужно — нужен лишь слой
входа (аккаунты) и транспорт (сеть).

## 2. Аккаунт и персонаж (регистрация)

Разделяем две сущности — это важно на будущее:

- **Аккаунт (account)** — человек: логин, пароль, почта. Один на игрока.
- **Персонаж (character)** — его тело в мире (наш `Character`). У аккаунта может
  быть один или несколько персонажей (решить: пока 1).

`playerstore` из прототипа — это ровно прото-таблица персонажей, только в JSON.
Переход на БД = тот же набор полей, другой драйвер (программа доступа к хранилищу).

### Вход: три уровня, по возрастанию
1. **Гость (guest).** При первом заходе сервер выдаёт анонимный id + токен
   (случайная строка-пропуск), персонаж рождается «новичком» (как сейчас). Играть
   можно сразу, без формы. Прогресс привязан к токену в браузере.
2. **Регистрация.** Гость в любой момент «закрепляет» аккаунт: почта + пароль.
   Тот же персонаж, теперь восстановим с любого устройства.
3. **Вход.** Почта + пароль → серверная сессия (токен с сроком жизни).

### Безопасность пароля
- Хранить **только хэш** пароля (необратимый отпечаток), алгоритм **argon2id**
  (современный, стойкий к перебору). Никогда не хранить сам пароль.
- Сессия — токен в БД (таблица `sessions`) со сроком и возможностью отзыва;
  проще отзывать, чем JWT (самоподписанный токен, который нельзя «погасить»
  досрочно). Токен — в httpOnly-cookie (браузер не даёт JS его украсть).
- Антиперебор: лимит попыток входа на аккаунт/адрес.

## 3. База данных (PostgreSQL — уже решено в каноне)

### Ключевое решение: БД — это durable-хранилище, а не «мир в реальном времени»

Горячая симуляция крутится **в оперативной памяти** одного процесса-мира (как
сейчас `Region` в RAM). БД хранит *снимки* и *журнал*, чтобы мир пережил рестарт.
Это прямое продолжение `archive.py`: холодные деревни уходят «на диск» — теперь
диском становится Postgres.

- **Горячее** (где есть игроки/события) — в RAM, тикает почасово.
- **Холодное** — строки в БД + дешёвый суточный offline-шаг.
- **Снимок (snapshot)** горячего мира в БД — раз в N минут и при выходе.

### Таблицы (черновик схемы)

```
accounts(id, email UNIQUE, pass_hash, created_at, status)
sessions(token PK, account_id FK, expires_at, created_at)
characters(id, account_id FK, name, sex, age, settlement_id FK,
           coins, home, home_comfort, weapon, outfit,
           skills JSONB, favors JSONB, father, mother, updated_at)
inventory(id, character_id FK, item_id, where ENUM('bag','storage','equipped'))
cargo(character_id FK, resource, amount)                 -- караван-груз
deliveries(id, character_id FK, src_settlement, dest_settlement,
           giver, parcel, reward, status)
worlds(id, name, clock_hours)                            -- регион/часы
settlements(id, world_id FK, name, market, x, y,
            store JSONB, house_integrity, graves, temperature,
            archived BOOL, archived_pop, cold BOOL)
residents(id, settlement_id FK, name, sex, age, role,
          skills JSONB, renowned, ... )                 -- NPC-тела холодных деревень
quests(id, settlement_id FK, giver, kind, activity, title,
       need, have, dest, parcel, reward, accepted, done)
chronicle(id, settlement_id FK, year, day, text)        -- долгая память мира
```

Заметки:
- `JSONB` (бинарный JSON в Postgres) для навыков/услуг/склада — гибко, их форма
  ещё меняется; «горячие» поля (монеты, деревня) — обычные колонки, по ним ищем.
- NPC горячих деревень в БД держать **не обязательно построчно** — можно хранить
  снимок деревни целиком (как сейчас JSON в архиве). По-настоящему построчно
  нужны только игроки и долгая память (хроника, могилы, мастера).
- Хроника/могилы/мастера — переживают всё (канон «мир помнит»): отдельные строки,
  не внутри снимка.

## 4. Процессы и масштаб

```
                 ┌─────────────┐   WebSocket    ┌──────────────┐
   браузеры  ───▶│  gateway     │◀──────────────▶│ world-process │──▶ PostgreSQL
  (клиенты)      │ (вход,сессии)│   намерения    │ (тикает регион│    (снимки,
                 │  маршрутиз.  │   / дельты     │  в RAM, 1 поток│     журнал,
                 └─────────────┘                └──────────────┘     холодное)
```

- **gateway** — принимает подключения, проверяет сессию (кто ты), направляет к
  нужному процессу-миру. Тонкий, без игровой логики.
- **world-process** — держит один регион в RAM и тикает его (наш `Region`).
  Внутри — один поток симуляции (как сейчас `_lock`): все действия игроков
  выстраиваются в очередь и применяются в порядке тика. Так нет гонок
  (ситуаций, когда двое меняют одно и то же одновременно).
- **Шардинг (sharding — деление мира на куски по процессам):** один регион = один
  процесс. Переход игрока в другой регион = *передача* (handoff): сохранить
  персонажа, отцепить от старого процесса, подцепить к новому. У нас уже есть
  «в пути с караваном» — это естественный момент передачи между процессами.

Почему один поток на регион, а не многопоточно: симуляция — это общий изменяемый
мир. Один тик-поток = простая и верная модель (детерминизм, никаких блокировок по
каждому объекту). Масштаб берём не потоками, а *числом регионов* (процессов) и
тем, что горячего в каждом — мало (LoD уже даёт ×80–90).

## 5. Протокол (WebSocket)

HTTP-опрос каждые 2 c (как сейчас) заменяем на **WebSocket** — постоянный канал,
сервер сам шлёт изменения, без опроса.

- **Клиент → сервер (намерения):**
  `do {activity, quality}`, `travel {to}`, `trade {buy|sell,res,amount}`,
  `quest {accept|deliver, qid}`, `house {...}`, `item {...}`, `say {text}`.
- **Сервер → клиент:**
  - `snapshot` — полное состояние при входе (как сейчас `/api/state`);
  - `delta` — что изменилось за тик (дешёвые частые сообщения);
  - `event` — новость/хроника/прибытие/«кто-то вошёл в таверну».
- Рассылка по комнатам: подписан на свою деревню → получаешь её дельты и события.

## 6. Со-присутствие и «пить медовуху с другом» (канон)

Это уже заложено: `tavern_tonight` — список тех, кто сейчас в таверне. В сети:
- кто в одной деревне — видят друг друга в снапшоте (роли/имена);
- вечер в таверне → общая «комната» (room): видно, кто пьёт медовуху;
- действие `say` и совместный жест «выпить вместе» = сообщение в комнату +
  маленькое общее состояние (счётчик кружек, тост). Мир — история — иммерсивность.
- караван в пути — тоже мини-комната: несколько игроков могут идти вместе.

## 7. Честность исхода (анти-чит)

Слабое место: **качество мини-игры приходит с клиента** (0..1) — его можно
подделать. Пока прототип, это ок. На будущее, по возрастанию строгости:
1. Сервер **ограничивает** награду и скорость (нельзя слать действия чаще, чем
   занимает мини-игра; нельзя «накликать» 100 охот в минуту) — уже частично:
   усталость и `WORK_HOURS` сдерживают.
2. Сервер хранит сложность и **сверяет** правдоподобность (идеальные 1.0 подряд →
   подозрительно).
3. Позже — критичные мини-игры считаются/проверяются на сервере (клиент шлёт не
   «качество», а сами действия: тайминги нажатий), сервер пересчитывает.

Начать с (1)+(2): дёшево и закрывает грубые читы.

## 8. Путь от прототипа (что менять, что оставить)

Хорошая новость: ядро готово к этому по форме.

| Сейчас (прототип)            | В сети                                    |
|------------------------------|-------------------------------------------|
| `world/` чистая симуляция     | **без изменений** — это и есть ядро мира  |
| `playerstore` (JSON/игрок)    | таблица `characters` (+`inventory`,…)     |
| `persistence.save_region` JSON| снимок в `settlements`/`worlds` + журнал  |
| `thin.py` HTTP + опрос 2с     | gateway + WebSocket, тот же набор намерений|
| один игрок `PID='local'`      | много `account_id`, сессии                |
| `_lock` вокруг тика           | очередь намерений в один тик-поток региона|

Порядок внедрения (предложение):
1. Аккаунты + сессии (гость → регистрация), всё ещё на JSON — проверить вход.
2. WebSocket вместо опроса (один игрок) — проверить дельты/события.
3. Несколько игроков в одном процессе-мире — очередь намерений, со-присутствие.
4. PostgreSQL как хранилище (заменить JSON-драйверы на SQL за тем же интерфейсом).
5. Шардинг по регионам + передача при путешествии (когда понадобится масштаб).

## 9. Открытые вопросы (решить вместе)

- **Сколько персонажей на аккаунт** — один (проще, честнее для живого мира) или
  несколько?
- **Смерть игрока** — мир смертен (канон). Перманентная смерть (как у NPC, с
  могилой и строкой в хронике) или воскрешение? Это сильно влияет на тон.
- **Офлайн-игрок** — когда вышел из сети, его тело остаётся в мире (им «правит»
  AI, как NPC) или «замораживается»? Красиво: офлайн → `driver` временно 'ai',
  и мир живёт тобой, пока тебя нет. Ровно то, ради чего делали единую сущность.
- **Регистрация обязательна или гость навсегда** — порог входа vs. удержание.
- **Один мир на всех или несколько параллельных** — зависит от нагрузки и желания
  «единого мира-истории».

Моя рекомендация по умолчанию: один персонаж на аккаунт; перманентная смерть с
хроникой (это и есть ваша «живая история»); офлайн-игрок переходит под AI и
остаётся в мире; гость можно, но с мягким подталкиванием к регистрации.
