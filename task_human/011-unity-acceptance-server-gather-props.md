# 011 — Unity acceptance: server-authored terrain gather props

**Исполнитель:** владелец проекта.  
**Поддержка:** ChatGPT — исправление клиентских дефектов по F3 dump/логам; Claude — только если обнаружится расхождение серверного DTO.  
**Подсистема:** Unity 6 / URP / terrain streaming / v1.30 gather nodes.  
**Клиентская ветка:** `chatgpt/unity-terrain-gather-visuals-20261118-main`.  
**PR:** [#761 — Render server-authored terrain gather nodes](https://github.com/IskatelApelsinov/pogranichye/pull/761).

## Цель

Проверить в реальном Unity runtime, что семь серверных видов находок получают видимые 3D proxy-модели, стоят на фактической высоте terrain, не создают локальных игровых сущностей и синхронно отражают серверный запас.

Это первая геометрическая заглушка из общих Unity primitive meshes, а не финальный авторский art pack. Не оценивать её как окончательное качество моделей.

## Подготовка

1. Обновить репозиторий и переключиться на клиентскую ветку из PR #761 (не ждать её слияния в main).
2. Открыть проект в Unity `6000.6.7f1`, дождаться импорта и проверить Console на compile errors.
3. Запустить актуальный сервер из main (на момент создания задачи: `d7a18948`) и войти обычным игроком.
4. Сохранить исходный F3 diagnostic dump перед выходом в лес.

## Проверка

1. Выйти из поселения в лес/урочище, где серверный `/api/terrain.gather[]` возвращает узлы. Не создавать вручную тестовые кусты или предметы.
2. Проверить визуальную посадку на рельеф: модели не висят над землёй и не проваливаются; поворот стабилен после повторной загрузки чанка.
3. Проверить виды, когда они присутствуют в серверном ответе: `herb`, `mushroom`, `berries`, `hive`, `deadwood`, `nest`, `flax`. Не считать отсутствие вида дефектом, если сервер его не выдал в текущем seed/чанке.
4. Пройти персонажем через модель находки: она не должна блокировать движение и raycast как физическое препятствие.
5. Подойти к находке. Убедиться, что действие и название по-прежнему приходят из существующего интерфейса `place.gather[]`, а не из локально созданного компонента.
6. Собрать находку. До подтверждения сервера инвентарь/запас не должен меняться локально. После подтверждения проверить уменьшение `left`; при нуле модель скрывается.
7. Если возможно, дождаться серверного восстановления запаса и проверить, что следующий близкий full snapshot снова показывает модель.
8. Если другой игрок собирает узел, проверить обновление после попадания узла в ближайший `place.gather[]` snapshot. Известное ограничение: сервер отдаёт этот список только в радиусе 45 м и не отдаёт его на дороге, поэтому дальняя модель может временно выглядеть устаревшей до приближения.
9. Перезагрузить/сменить terrain chunk и вернуться: один и тот же server ID должен давать одну модель в одном месте, без дублей.
10. Открыть Unity Profiler на нескольких загруженных чанках. Зафиксировать число видимых узлов, Batches/SetPass, CPU/GPU frame time и заметные spikes при подгрузке.

## Что приложить

- Скриншоты или короткое видео 3–7 видов, которые реально присутствуют в чанках.
- F3 JSON dump с `place.gather[]` и, если доступно, сырой ответ `/api/terrain`.
- Полный текст Unity Console при любой ошибке.
- Profiler capture или хотя бы значения Batches/SetPass и frame time.
- Для сбора: исходный `left`, серверный ответ и `left` после подтверждения.

## Критерии выполнения

- Unity compile и PlayMode проходят без ошибок.
- Позиции совпадают с серверными chunk-local координатами и высотой terrain.
- Модели не имеют collider и не создают локальных loot/NPC/POI.
- Исчерпание/восстановление отображается только по серверному snapshot.
- Нет дублей после повторной загрузки чанков.
- Производительность приемлема; если один renderer на узел дорогой, зафиксировать числа и предложить batching/instancing отдельно.
- Wire contract v1, серверные ID, запасы и действия не изменялись.
