## 1. `me.wpos`/`neighbors[].wpos` — единственный канонический источник глобальных E/N/U?

Да. `WorldPos` (`1-server/sim/worldpos.go`) хранится как `{Frame uint16; E,N,U int64}` в
миллиметрах — целочисленный фикс-поинт, не float, не зависит ни от какого клиентского origin.
`me.wpos` и `neighbors[].wpos` строятся одной и той же функцией `worldPosViewFrom` (строка ~315),
так что у них одна схема по построению, не по соглашению.

Непрерывность:
- переход между поселениями (пеший handover, `StepLands`) и переход по тракту (`Travel`/`arrive`) —
  `sim.TestSeamlessLandsKeepWorldPosition`, `sim.TestSeamlessRoundTripPreservesIdentityAndState`
  (`sim/worldpos_test.go`), плюс свежий `sim.TestStepLandsOpensOuterFrontier` (`sim/frontier_test.go`,
  этот же PR что открыл фронтир пешком, явно проверяет `wpos` до/после перехода в пределах 0.01 м).
- отрицательные координаты/чанки — `sim.TestWorldPosChunksAndNegativeCoordinates`.
- `neighbors[].wpos` совпадает по схеме с `me.wpos` — `server.TestNeighborWposMatchesOwnSchemeAndAnchor`,
  `server.TestNeighborsWposMatchesProjectionAndTracksMovement`.
- reconnect: есть тесты на восстановление состояния при переподключении
  (`server/reconnect_repopulate_test.go`), но **нет отдельного теста именно на непрерывность wpos
  во время/сразу после reconnect**. Отвечаю честно — это реальный пробел, не утверждаю обратное.
  Если нужно перед включением runtime-коордтинатора — добавлю маленьким PR (сервер не хранит
  позицию "в полёте", так что по факту там нечему отличаться: reconnect просто перечитывает
  текущее состояние, но тест закрепит это явно, а не оставит предположением).

## 2. `me.pos`/`neighbors[].pos` — локальные координаты села, реинициализируются при смене `place.id`?

Да. `pos` строится из `ScenePosC.X/Y` — метры от центра ТЕКУЩЕГО `place.Settlement`. При любом
переходе (StepLands/Travel/телепорт) код перезаписывает `p.X,p.Y` на новые локальные значения
относительно нового села — см. `arrive()` (`sim/journey.go`) и `StepLands` (`sim/worldpos.go`).
Клиент не должен трактовать `pos` как глобальные координаты — это прямо написано в
`3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md`: «мир = якорь села (`place.anchor`) + локальная точка
(`me.pos`)».

## 3. `wpos.frame` — версия/кадр; все чанки/сущности одного frame сравнимы по E/N/U?

Да, именно так задумано: `WorldDist` (`sim/worldpos.go`) буквально возвращает `ok=false`, если
`a.Frame != b.Frame` — иное сравнение запрещено на уровне кода, не только документации. Сейчас во
всём мире один frame (`0`, `yof-tangent`), несколько кадров появятся только для дальних
континентов (комментарий в начале файла) — не раньше, чем понадобится.

## 4. `wpos.chunk == floor(E/256)`, `wpos.layer == floor(U/64)`, независимо от клиентского origin?

Да, буквально: `Chunk()` — `floorDiv(E, ChunkMeters*1000)` / `floorDiv(N, ChunkMeters*1000)`,
`Layer()` — `floorDiv(U, LayerMeters*1000)` (`ChunkMeters=256`, `LayerMeters=64`, хранение в мм).
Полностью серверная целочисленная математика, клиентский floating origin на это не влияет и не
может повлиять, даже в принципе — сервер эти поля не принимает от клиента, только отдаёт.

## 5. Сервер не принимает клиентский local origin/локальные float как authoritative input?

Да. Клиентский intent на движение — `{op:"move", mx, my, run, face, dt, seq, fast}` (относительные
дельты/направление за тик, не абсолютная позиция) — `server/server.go` case `"move"` →
`sim.ApplyMove(...)`, которая сама считает коллизии/скорость/границы по серверной `Layout`. Переход
между поселениями/по тракту (`Travel`, `StepLands`) тоже целиком решает сервер — клиент не
присылает целевые координаты, только намерение (цель по ID, тап по зоне и т.п., уже в текущем
контракте). Этот инвариант не специфичен для floating origin — он не менялся и не планируется
менять этим PR.

## 6. Нужны ли отдельные regression tests на непрерывность wpos при смене поселения/chunk seam?

Для смены поселения — уже есть, см. пункт 1 (`TestSeamlessLandsKeepWorldPosition`,
`TestStepLandsOpensOuterFrontier`). Для чисто геометрического chunk seam (без смены поселения,
просто переход E=255.999→256.001 в одних и тех же мировых координатах) отдельного теста нет, но
он и не нужен для контракта: `Chunk()`/`Layer()` — чистые функции от уже готового `E/N/U`, шов тут
физически не может появиться (не кусочная функция, не таблица). Если хочешь явный тест именно на
этот случай ради документации контракта — скажи, добавлю, это 10 минут.
