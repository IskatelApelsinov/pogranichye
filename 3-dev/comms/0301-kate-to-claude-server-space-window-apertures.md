# Kate → Claude: серверные оконные проёмы в /api/spaces

Дата: 2026-11-18  
Приоритет: P1 для визуальной работоспособности корчмы и будущих интерьеров  
Связанный клиентский PR: #749

## Контекст и найденный блокер

ChatGPT исправляет Unity footprint-фасады: вместо тёмных кубов поверх стены появляются реальные геометрические окна. Но аудит текущего `3-dev/contract/fixtures/spaces_v1.example.json` выявил второй слой геометрии: `WorldSpacePresentationBuilder` дополнительно рисует серверные `spaces[].surfaces`, а `1-server/sim/spaces.go` строит непрерывные стены через `spaceBuilder.ring()` / `spaceBuilder.wall()`.

У корчмы серверная оболочка накладывается на клиентский фасад и закрывает созданные в Unity окна. Поэтому одного клиентского изменения недостаточно, чтобы дневной свет действительно попал в интерьер корчмы.

## Задача

Сделать оконные проёмы частью серверно-авторитетной геометрии пространства, начиная с корчмы, без изменения правил движения и без локальной генерации новых игровых сущностей.

1. Провести аудит `spaceBuilder.ring`, `spaceBuilder.wall`, `buildBox`, `tavernSpace`, `spaces_fixture_test.go`, `spaces_test.go`, `spaces_size_test.go` и всех consumers `/api/spaces`.
2. Добавить детерминированные окна в стены корчмы на фасадах, не занятых дверью. Координаты/размеры должны вычисляться из размеров конкретного здания и его `facing`, без привязки к Починку или абсолютным координатам.
3. Оставить дверь отдельным серверным проёмом из существующего DTO `portals`; окна не должны создавать порталы, переходы между пространствами, входы или новые gameplay actions.
4. Сохранить серверную блокировку движения через окна. Не считать визуальный проём разрешением прохода: движение внутрь/наружу по-прежнему разрешено только действующей дверью и существующими правилами сервера. Если поверхности одновременно отвечают за render и local collider, предложить безопасное разделение визуальной геометрии и blocking collider на клиенте либо отдельное явное поле/описание — не ослаблять server movement validation.
5. Обновить пример `spaces_v1.example.json` и добавить регрессионные тесты:
   - окна находятся в границах стен и не пересекаются с дверью;
   - все четыре cardinal `facing` ориентируют окна на правильных фасадах;
   - окно состоит из верхней/нижней перемычек и боковых простенков, а не дырки в несущей коллизии;
   - нет новых порталов/ID пространств и не меняются права движения;
   - deterministic output и revision hash меняются при изменении оконной геометрии.
6. Обновить протокол-док и ADR/fixture, если структура wire-данных меняется. Предпочесть минимальное additive-решение; не менять `v:1`, существующие ID зданий/пространств, сохранения и правила Demo 1/2.

## Ожидаемый результат

- Отчёт аудита с точными файлами/участками.
- Server PR с тестами и обновлённой fixture.
- Таблица размеров/позиции окон относительно `space.origin` для всех четырёх ориентаций.
- Явное описание того, как Unity получает визуальные проёмы и при этом не позволяет пройти через окно.
- Проверки `go test ./...`, `go vet ./...`, contract fixture и deterministic revision.

## Границы

- Не добавлять клиентские/серверные NPC, жильцов, предметы, мебель или интерьерные сущности.
- Не назначать жильцам дома и не реализовывать occupancy здесь: это отдельная задача из handoff #745.
- Не создавать окна у каждого дома, пока у них нет серверных `spaces`; начать с уже существующей корчмы.
- Не мержить без Kate.
