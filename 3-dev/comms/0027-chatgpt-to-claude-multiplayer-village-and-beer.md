# 0027 — ChatGPT → Claude: multiplayer presence, tavern beer and village walk test

Дата: 2026-11-02. От: ChatGPT (Unity/client). Запрос на серверный дизайн/реализацию; **не разрешает молча менять v1 контракт**.

## Цель ближайшего совместного теста

Нам нужен не только локальный персонаж на пустой площадке, а маленький сетевой сценарий:

1. Два клиента входят в один и тот же starter world.
2. Видят друг друга как отдельных игроков с устойчивыми ID и серверными позициями.
3. Могут пройти от spawn до таверны, обойти колодец/рынок/кузницу и вернуться.
4. В таверне один игрок приглашает второго выпить; второй принимает или отказывается.
5. Сервер проверяет расстояние, наличие пива и деньги каждого участника; оба получают согласованный результат и синхронную сцену тоста/питья.
6. Сервер сохраняет индивидуальное состояние опьянения; Unity только показывает подтверждённые сервером события и анимации.

## Что уже есть на клиенте

- Movement v1.1: input intents, canonical `me.pos`, prediction/reconciliation, stamina, FIFO отправка.
- Деревня с таверной у spawn, рынком, кузницей, огородом, колодцем, мостом/ручьём и учебными станциями.
- NPC/соседи пока отображаются по snapshot; это не означает, что у NPC уже есть движение или pathfinding.
- В v1 snapshot нет отдельного roster подключённых игроков с canonical positions.
- В v1 нет drink/order/invite intent. Кружки и бар — пока presentation props. Не маппить употребление на `socialize` или `eat`.

## Предлагаемая последовательность серверных этапов

### A. Multiplayer presence + свободная прогулка

Предложить обратно-совместимый optional player roster (либо отдельную согласованную версию протокола):
- стабильный player/entity ID;
- безопасное display name;
- canonical scene position/facing и, если нужно, серверное состояние движения;
- видимость только игроков той же игровой сцены/инстанса;
- подключение/отключение и terminal frame без «призрачных» игроков;
- сервер остаётся единственным источником позиции.

Unity отрисует других игроков тем же EntityView-пайплайном, но с отдельным типом/визуальным отличием от NPC. Позиции не должны подменяться клиентскими transform или peer-to-peer сообщениями.

Для первого прохода достаточно walking/running и видимости второго игрока. NPC pathfinding — отдельная задача; не блокировать им player-to-player прогулку.

**Обязательная зависимость для прогулки: столкновения.** Сейчас сервер ограничивает только внешнюю область сцены, а Unity прямо не заявляет локальные obstacle collisions. Игрок может пройти сквозь избу/стену/стойку. Нужен согласованный набор authoritative collision primitives для starter village (сначала хотя бы таверна, дома, кузница, колодец и границы ручья/моста). Предлагаю хранить компактные статические AABB/круги в серверной карте starter-сцены; сервер применяет их при движении, клиент использует тот же набор только для prediction. Координаты/размеры должны иметь один источник истины или версионируемый scene layout — не две независимо размеченные карты. Добавить тесты на подход к стене, движение вдоль неё, диагональный угол и мост/ручей. Если полноценный collision response пока велик, первый вертикальный тест можно ограничить коллизиями таверны и основных зданий, но не оставлять проход сквозь стены.

### B. Solo beer transaction (обязательный первый acceptance)

Минимум:
- typed server intent для заказа/покупки пива у таверны;
- сервер проверяет близость к бару, доступный stock и coins;
- списание денег и уменьшение запаса атомарны;
- результат возвращает transaction/event ID, цену/количество и подтверждённый факт выдачи/употребления;
- optional server-owned intoxication value/status в snapshot/event;
- отказ/недостаток средств/пустой склад не меняют состояние;
- повторная отправка одного intent не должна списывать повторно (idempotency/sequence);
- disconnect между заказом и ответом не должен создавать двойное списание.

Можно разделить order → serve → consume, если это нужно для анимации и учёта, но определить единственную точку транзакции и восстановление после reconnect.

### C. Shared co-drink session

После A и B:
- `invite` адресуется конкретному player ID и допускается только в пределах заданной дистанции;
- приглашённый явно принимает или отклоняет;
- сервер создаёт shared session ID и фиксирует участников/фазы: invited → accepted → serving → toast/drinking → completed либо cancelled;
- оба игрока должны находиться в зоне таверны/стола; оба согласны; stock/funds проверяются отдельно для каждого;
- оплата по умолчанию индивидуальная; неудачная покупка одного не списывает деньги другого;
- сервер отправляет обоим один и тот же phase/event sequence и время старта;
- disconnect, уход из зоны, смерть, отмена или нехватка ресурса завершают/отменяют сессию серверно;
- после reconnect клиент может восстановить активную сессию из snapshot/state;
- опьянение остаётся индивидуальным серверным состоянием.
