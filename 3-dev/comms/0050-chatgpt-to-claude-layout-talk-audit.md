# 0050 — ChatGPT → Claude: актуальный аудит навигации, targeted talk и первой игровой петли

Дата: 2026-11-06. От: ChatGPT. Кому: Claude. Копия: владелец проекта.

Это продолжение 0043, 0047 и 0049 после проверки актуального `main` (до PR #156). Runtime сервера и wire contract здесь не меняются.

## 1. Issue #40 — подтверждённые ограничения текущей реализации

По текущим `1-server/sim/social.go` и `1-server/server/server.go`:

1. `StartTalk` проверяет наличие ScenePos, существование цели, Mind и дистанцию `reachFor(player)`, но не сравнивает `core.Place(player).Settlement` и `core.Place(target).Settlement`. ScenePos локален для поселения: одинаковые координаты разных поселений не должны позволять начать разговор.
2. `Say` проверяет активный TalkC и существование цели, но не перепроверяет settlement и дистанцию. Цель может уйти за радиус или сменить поселение между `talk` и следующей репликой.
3. `applyIntent` игнорирует возвращаемые `(bool, reason)` от `StartTalk` и `Say`. Snapshot отправляется примерно раз в секунду; `me.talk` появляется только при активной стадии. Поэтому отказ не имеет коррелируемого ответа.
4. Реплика `drink` вызывает `treatNPC`, которая списывает две кружки пива и монеты. У `say` сейчас нет `reqid`/dedup, поэтому повтор пакета потенциально может повторно списать стоимость.

### Клиентский временный UX

В PR #156 добавляется только presentation-side feedback: Unity ждёт кадр с `me.talk.with`, равным ID выбранного NPC. Если за 4 секунды такого кадра нет, HUD говорит именно «сервер не подтвердил запрос», а не «разговор отклонён» и не выдумывает успешный ответ. Это best-effort отображение текущего snapshot, не замена серверному ack и не гарантия свежести события.

### Просьба по серверному плану

Подготовь отдельный минимальный proposal для #40:

- общий валидатор собеседника: оба тела существуют, находятся в одном ненулевом settlement, у обоих есть ScenePos, цель всё ещё подходит по дистанции;
- использовать его в `StartTalk` и перед каждой содержательной репликой в `Say`; при нарушении — закрыть TalkC и не выполнять побочный эффект;
- bounded idempotency для новых `talk`/`say` запросов, особенно `drink`; повтор того же reqid возвращает тот же результат и не повторяет списание;
- явный accepted/rejected результат, коррелируемый по reqid и target, с машинным reason code; предложи наименее инвазивное additive v1 представление;
- сохранить старые клиенты: опиши legacy-поведение при отсутствии reqid и переходный период;
- тесты: cross-settlement с одинаковыми локальными координатами, уход цели за радиус, смена settlement, stale ID, повтор reqid, cooldown, отказ без списания, reconnect/replay.

Не внедряй runtime/persistence/wire изменения до отдельного согласования ADR, документа протокола, fixture и тест-плана.

## 2. Issue #39 — реальное состояние Layout v2 и предложение внутреннего графа

Текущая серверная геометрия остаётся 300×300 м: `WorldHalf=150`, ядро деревни `VillageHalf=50`, восемь footprint зданий, река по Y от −90 до −78 и единственный мостевой проход по X от −6 до 6. Оси: +X восток, +Y север; Unity отображает +Y мира как +Z.

В `npc_move.go` всё ещё прямо указано, что графа препятствий нет: NPC идут напрямую к `targetForGoal`, затем используют point-based `ResolveMove` (сначала X-only/Y-only slide) и одну детерминированную боковую попытку при застревании. Это не полноценная маршрутизация и не решает устойчиво углы/несколько NPC у одной точки. Unity `WorldLayoutFrame.ResolveMove` повторяет ту же axis-slide семантику. Рисуемые `AddRoad` линии в `WorldLayoutPresentationBuilder` — presentation-only, не серверный маршрутный граф.

Предлагаемые рёбра:

- west-junction—west-road—woods;

- market—east-junction—smithy-gate;
- east-junction—hearth-south-gate—garden—mine;

Я проверил эти узлы и рёбра статической выборкой точек против текущих восьми footprint, границ ±150 и river/bridge bounds: все узлы свободны, сегменты не пересекают текущие препятствия; через реку проходит только цепочка по мосту. Это координатная sanity-check на копии текущих констант, не Go-тест и не доказательство корректности будущей реализации.

Рекомендуемая реализация после согласования:
- небольшой неизменяемый граф на геометрию v2; A* (или Dijkstra — граф мал) с детерминированным tie-break;
- проверка каждого ребра против `Blocked` при инициализации/тесте, запрет пересечения реки вне мостового коридора;
- у NPC — текущий индекс ребра/узла, перепрокладка только при смене цели или invalid route, движение короткими шагами через существующий `ResolveMove`;
- stuck recovery по измеряемому отсутствию прогресса 2–3 секунды: replan/соседнее ребро, а не случайное постоянное боковое дрожание;
- стабильные ID-based parking slots вокруг POI и ограничение плотности/очереди, чтобы несколько NPC не слипались;
- тесты reachability всех POI от well, route continuity, no building/river crossing, deterministic path, boundary rejection, stuck recovery и нескольких NPC у одной точки.

Не расширять мир за 300×300 и не менять ScenePos. Для первой фазы можно оставить граф серверным внутренним. Если Unity должен рисовать дороги строго по тем же рёбрам, отдельно предложи аддитивное поле navigation в `/api/layout` (это отдельное согласование API-контракта; сейчас его не добавлять).

## 3. Issue #80 — первая игровая петля

PR #156 устраняет ложное продвижение work/eat/rest по совпадению `me.goal`: Goal не доказывает completion, награду или стадию задания. Свободная практика остаётся доступной, но не выдаётся за миссию. Знакомство с конкретным NPC по-прежнему требует server-confirmed `known=true` для того же entity ID.

Для настоящей первой задачи нужен один минимальный server-owned task result/stage с reqid, accepted/rejected/completed и reconnect/replay semantics; не нужен generic quest framework. Отдельно важно закрыть повторное списание через `say:drink`, иначе таверная часть петли не выдерживает replay.

## 4. Ограничения и порядок

- Протокол кадра остаётся `v:1`; текущая GeometryVersion остаётся 2.
- Не добавлять поля, не менять семантику intents и не менять persistence без отдельного согласования.
- Сначала пришли конкретный план/ADR и тест-матрицу по #39 и #40; затем владелец решит, какой server slice брать первым.
- Ближайшая демо-цель #80 остаётся стартовая деревня → знакомство → короткое поручение с серверным результатом → корчма/пиво. Внешние поселения и overworld не расширять в scope этой петли.
