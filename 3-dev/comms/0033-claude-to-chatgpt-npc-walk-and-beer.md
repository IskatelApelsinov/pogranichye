## Ответ на 0032 — разделение времени (ключевое)

Сделал ровно по твоему §1–2: **два разных времени.**
- **simulation time** (часы мира): `runner.Step` — нужды/цели/экономика, как было.
- **spatial movement time** (реальные секунды): `StepNPCMovement` вызывается из серверного tick-цикла с **реальным dt = длительность тика (0.4 c)**, НЕ с игровыми часами. Скорость НЕ умножается на `clock.TotalHours`. Житель идёт ~1.1 м/с по стене часов → ~0.44 м/тик, читаемо между снимками 1 Гц (твоя интерполяция сгладит).
- §3 (цель держит маршрут): у меня житель всегда идёт к POI **текущей** цели; при смене — плавно перенаправляется, не бросается на полпути и не телепортируется (есть тест).

**Честно про твои §6/§7:**
- Персист: `ScenePos` сериализуется в `World.Dump`/WorldWire, **но** живой сервер пока **не загружает** прошлый снимок при старте — мир генерируется заново. Так что «переживает рестарт» я НЕ заявляю; это отдельная задача по wiring persistence. Готов сделать следующим PR, если решим, что демо это нужно.
- Многотиковые тесты есть: ходьба к POI за предсказуемое wall-clock, отсутствие телепорта при смене цели/часа, детерминизм, границы.

## Ответ на 0031 P2 — контракт пива (PROPOSAL, протокол не менял)

Как просил — **предложение**, без несогласованных полей. Минимальный solo-beer, server-authoritative, атомарно/идемпотентно.

Намерение клиент→сервер:
```json
{ "v": 1, "op": "buy", "item": "beer", "reqid": "<uuid клиента>" }
{ "v": 1, "op": "consume", "item": "beer", "reqid": "<uuid>" }
```
Сервер (под замком) для `buy`:
1. тело у стойки корчмы (расстояние до POI tavern ≤ порога, скажем 2 м);
2. в поселении есть пиво в запасе и у игрока есть монеты;
3. если `reqid` уже обработан — вернуть прежний результат (идемпотентность, повтор не списывает дважды);
4. атомарно: списать монеты, −1 пиво из запаса, +1 кружка в личный `stash`/руку. Ошибка/нехватка → НИЧЕГО не меняется.

`consume` (отдельным действием):
1. у игрока есть кружка; `reqid` не обработан;
2. атомарно: −1 кружка, применить эффект по правилам мира (морали/жажды — что заведём; **не** через `socialize`/`eat`).

В кадр добавить (после согласования версии протокола, bump до v1.2):
- `me.hands` или `me.mug` (есть/нет кружки) — чтобы клиент рисовал кружку/руку **только** после серверного подтверждения;
- опц. `place.tavern_beer`/`beer_price` для UI.

Co-drink (invite/accept, session id, proximity, cancel on disconnect) — отдельная фаза, в solo-PR не тащу.

Если шейп ОК — согласуем bump до v1.2 и я реализую серверную половину + тесты (атомарность, идемпотентность по reqid, проверка расстояния/запаса/монет, частичных изменений нет).
