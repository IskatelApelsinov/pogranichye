# Синтетические испытания большого мира и 100 одновременных игроков

Дата: 2026-11-17  
От: ChatGPT  
Кому: Claude  
Тема: воспроизводимый нагрузочный стенд для большого мира, HTTP/API и 100 настоящих WebSocket-клиентов

## Цель

Нужен повторяемый synthetic/load test, который проверяет не только ECS/симуляцию, но и полный серверный путь: HTTP API → регистрация/авторизация → WebSocket → резервирование тел → полные snapshots → действия → AOI → отключения/reconnect.

Существующие sim/scale_test.go (300 поселений, NPC/heat/terrain benchmarks) и server E2E (1–2 WS клиента) полезны, но не доказывают, что сервер выдерживает 100 одновременно подключённых игроков в большом мире. Не подменять сетевую нагрузку тестом с искусственно добавленными ctl или player-компонентами.

## Предлагаемая реализация

Сделай отдельный инструмент без влияния на production-протокол, например 1-server/cmd/pogload (или cmd/loadtest, выбери согласованное с текущей структурой имя). Предпочтительно стандартная библиотека Go, чтобы не добавлять зависимость только ради теста. Если в проекте уже есть подходящий WS-клиент — переиспользуй его.

Инструмент должен подключаться к уже запущенному тестовому серверу и создавать настоящие независимые аккаунты:
- POST /api/register, затем POST /api/login;
- 100 отдельных авторизованных WebSocket-соединений /ws?token=...;
- читать и разбирать реальные серверные кадры, а не только держать TCP сокеты открытыми;
- отправлять поддерживаемые v1 intents по реальному контракту, проверять ACK/result там, где он предусмотрен;
- корректно закрывать соединения, иметь таймауты, контекст отмены и понятный отчёт по каждому этапу.
- уникальный префикс логинов + seed/run ID, чтобы повторные прогоны не сталкивались с уже существующими аккаунтами. Пароли и токены не писать в лог.

Не изобретать новые intents и не менять wire contract ради теста. Использовать 3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md и существующие тесты server как источник истины.

## Режимы сценария

Минимум:
1. co-located: 100 подключённых игроков в одном стартовом поселении — worst case для AOI/neighbor serialization и общего места. Если обычная генерация тел не позволяет гарантировать одну площадку, добавь только test-only подготовку мира/fixture, не production API.
2. distributed: 100 игроков распределены по нескольким поселениям/регионам; проверяется, что локальные snapshots не сериализуют весь мир и AOI ограничен.
3. churn: плавный запуск, затем случайные 5–10% отключений и reconnect; проверить освобождение сессий, отсутствие двойного управления телом и утечек активных сессий.
4. mixed: idle + ходьба/поддерживаемые активные действия + запросы /api/world, /api/terrain, /api/layout, /api/stats. Действия должны быть валидными по текущему протоколу; доли нагрузки конфигурируемы.

Нагрузку наращивать ступенчато: 1 → 10 → 25 → 50 → 100 игроков. Опционально 150/250 для определения предела, но acceptance target этой задачи — 100.

## Большой мир

Проверить минимум конфигурации 300 поселений (это соответствует текущему существующему BenchmarkTick), затем 1000 поселений как диагностический профиль, если генерация и память позволяют. Не выдавать 1000 за acceptance target без замеров.

Для мира фиксировать seed, число поселений и параметры запуска. Нагрузить:
- /api/world manifest;
- /api/terrain?cx&cz&step=... на последовательности соседних, дальних и отрицательных чанков;
- /api/layout для разных settlement IDs;
- /api/spaces для набора чанков;
- /api/stats во время нагрузки.
Проверить детерминизм повторных запросов, корректные границы чанков, отсутствие роста кэшей без ограничений и корректность после перехода/смены активного поселения. Использовать реально поддерживаемые query параметры.

## Метрики и артефакты

Отчёт JSON + краткая читаемая сводка:
- число попыток/успешных/ошибочных регистраций, логинов, WS handshakes, активных клиентов;
- connect/login/first-frame latency p50/p95/p99;
- snapshots: count, bytes total, bytes/sec, frame size p50/p95/p99, malformed/timeout count;
- intent send/ACK latency и reject/error counts;
- HTTP request latency p50/p95/p99 отдельно по endpoint + status/error;
- reconnect success/time, stale sessions, duplicate body control;
- /api/stats: entities, players, foes, hot/warm/cold, hour_ms;
- процессные CPU/RSS/heap/goroutines/GC — если надёжно доступно. Не добавлять открытый публичный pprof endpoint в production; профиль включать только отдельным dev/test флагом или собирать внешним способом;
- конфигурация прогона, commit SHA, Go version, OS/arch, seed, wall-clock duration.

Не ставить произвольные пороги производительности до первого baseline. Сначала получить измеряемый baseline на машине CI и на машине разработчика; затем задать regression thresholds. Жёсткие функциональные критерии: 100/100 WS клиентов подключились и получили валидный первый snapshot; нет дублированного управления телом; после закрытия все сессии освобождены; нет panic/race/data corruption; HTTP API продолжает отвечать.

## Автоматизация

- Unit/integration тесты для генератора сценариев и парсера отчёта.
- Небольшой smoke в CI (например 10 клиентов и небольшой мир), без нестабильных wall-clock assertions.
- Полный 100-player/300-settlement load run — отдельная manual/nightly workflow_dispatch, не на каждом PR.
- Команды запуска и ожидаемые параметры — в 3-dev/docs/ и 1-server/README.md.
- Сохранять JSON report как GitHub Actions artifact.
- Поддержать запуск против уже поднятого сервера, а также удобный локальный рецепт старта pogserver с отдельным save-файлом и отключённым/изолированным persistence, чтобы тестовые аккаунты/мир не загрязняли пользовательское сохранение.

## Важные границы

- Не менять клиент-серверный frame v1 и gameplay semantics ради нагрузки.
- Не использовать production аккаунты/сохранения. Явно предупреждать, если target URL не localhost/test environment; для удалённого target требовать явный флаг подтверждения.
- Не считать открытые TCP соединения успешными игроками: каждый бот обязан пройти auth, получить валидный frame и участвовать в сценарии.
- Unity профилирование оформить как отдельный acceptance checklist: 1/10/25/50/100 видимых игроков, фиксированная сцена/камера/качество, FPS frame-time p95, main/render thread, memory, draw calls/batches, сетевой RX/TX. Автоматизировать headless Unity только если это реально возможно; не выдавать серверный benchmark за Unity performance test.
