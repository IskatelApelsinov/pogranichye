# Kate → Claude: серверная авторитетность мини-игры рыбалки

Дата: 2026-11-18
Приоритет: P2 — корректность игровой механики
Связанный Unity-код: `2-client/game/Assets/_Project/Scripts/Runtime/CoreGameplay.cs`
Связанный серверный код: `1-server/sim/actions.go`, `FishCatch`

## Найденное расхождение

Сейчас Unity локально управляет фазами рыбалки:
- после заброса клиент выбирает случайную задержку через `Random.Range(1.8f, 5f)`;
- затем показывает окно поклёвки длительностью 1,2 секунды;
- при успешном локальном тайминге отправляет обычный `act:fish`.

Серверный `FishCatch` не получает результат мини-игры и не проверяет тайминг подсечки. Он проверяет место у реки, наличие сил, списывает энергию и выдаёт фиксированный улов. Поэтому локальная мини-игра сейчас не влияет на серверный исход: она только определяет, отправит ли клиент запрос.

## Просьба

1. Подтвердить, что это всё ещё актуальный intended design, а не временная заглушка.
2. Предложить серверно-авторитетную модель рыбалки: сервер открывает/закрывает окно поклёвки, клиент отображает фазу и отправляет попытку подсечки, сервер принимает/отклоняет попытку и определяет результат/улов.
3. Использовать reqid/idempotency и существующий RequestGate/ACK-паттерн; повторная отправка не должна дублировать улов или расход энергии.
4. Учитывать reconnect, задержку сети, потерю/дублирование кадров и выход игрока из зоны.
5. Перед изменением wire-контракта подготовить ADR, обновить fixtures и добавить тесты на слишком раннюю/позднюю/валидную подсечку, повтор reqid, истёкшее окно и смену места.
6. Не добавлять локальные серверные сущности или клиентские исходы. Если полноценная мини-игра пока не нужна, предложить честный простой серверный цикл без фальшивого клиентского тайминга.

Не меняй существующие action names/IDs без согласования. Сначала пришли решение и контрактный план; затем отдельный серверный PR.
