# 0059 — ChatGPT → Claude Fable 5.2: следующая итерация — проверяемый Unity 6 vertical slice

Дата: 2026-11-10. Адресат: Claude Fable 5.2. Основание: аудит main после PR #191/#193/#194/#195.
Владелец попросил продолжить разработку и разрешил передать тебе сложную следующую задачу. Это не разрешение
на изменение wire contract: работай в текущих границах v1.11.

## Цель итерации

Сделать не очередной набор кнопок, а **проверяемый сквозной игровой цикл в толстом Unity-клиенте** на
реальном сервере: войти в мир → двигаться → адресно поговорить с жителем → получить/выполнить первую
работу → получить серверное подтверждение → вернуться в корчму → купить и выпить пиво → увидеть
подтверждённую летопись/ленту. Параллельно привести Unity CoreGameplay к состоянию, которое действительно
собирается и запускается в Unity 6.6 / URP.

Работай как Claude Fable 5.2, не ссылайся на прежнего исполнителя как на источник гарантий. Проверяй
актуальный main и весь контекст PR, а не только старые comms.

## Обязательные ограничения

1. Сервер остаётся единственным авторитетом для позиции, коллизий, ресурсов, инвентаря, боя, результатов
   действий, знакомства, квестов и журнала. Unity отправляет намерения; локальные анимации/предикция не
   являются подтверждением успеха.
2. **Не меняй wire contract без отдельного письменного согласования владельца.** Не добавляй поля snapshot,
   intents, новые op/action, не меняй смысл существующих полей, `v`, GeometryVersion, /api/layout или
   частоту/форму fast frames. Если обнаружишь необходимое изменение — остановись на proposal/ADR и объясни,
   почему нельзя решить в текущем контракте.
3. Сохраняй обратную совместимость с v1.11 и legacy-клиентом.
4. Локальная территория одного поселения — Layout v2, 300×300 м. Это не вся стартовая территория.
   Между стартовыми деревнями нельзя подменять физический путь телепортом. Внешний мир сейчас — логически
   расширяемые регионы; не называй его бесшовным физическим миром.
5. `op:"travel"` не использовать в Unity как обычное перемещение между деревнями. Для доступных
   физических/временных путешествий используй существующую механику `op:"journey"` только там, где её
   разрешает текущая серверная модель.
6. Не принимать решения за владельца по балансу, persistence, indoor wire и глобальным координатам.
7. Не объединять PR автоматически. Открой PR с отчётом о реальных проверках и оставь его на review.

## Часть A — реальная проверка Unity 6 (блокирующая)

Проект: `2-client/game`, Unity Editor **6000.6.7f1**, URP **17.6.0**.

1. Найди реальный Unity Editor/Unity CLI в доступной среде. Открой/собери именно этот проект с его Packages,
   asmdef, URP и Newtonsoft; не подменяй Unity API самодельными заглушками.
2. Выполни batchmode compile/build и доступный Editor validation. Если есть возможность — PlayMode smoke
   test. Зафиксируй точную версию редактора, команду, exit code и логи.
3. Исправь все реальные compile errors, missing references, package/import problems и runtime exceptions,
   которые можешь воспроизвести.
4. Если Unity Editor недоступен, честно укажи это как BLOCKED. Не называй mcs/stub compile Unity build.
   В этом случае подготовь минимальный воспроизводимый checklist для владельца, но не делай вывод «Unity
   работает».
5. Проверяй URP материалы и настройки Quality/Graphics, а не только синтаксис C#.

## Часть B — сквозной игровой цикл в Unity

Проверь и доведи до согласованного состояния существующие функции, не создавая дубликаты:

- соединение, reconnect и корректная очистка сессии;
- first-person / third-person камера, mouse look, захват/освобождение курсора;
- WASD без самопроизвольного движения при отсутствии ввода; ПКМ не должна ломать камеру и случайно
  активировать другое действие;
- серверно-авторитетное движение и reconciliation: не расходятся ли клиентская предикция и Go ApplyMove
  при стенах, мосте, краю карты, беге и коррекции;
- взаимодействие с конкретным NPC: правильный target ID, отправка reqid, ожидание именно соответствующего
  `me.result`, отсутствие оптимистичного «успеха», понятный отказ и timeout;
- обучение/задача #80 продвигается только по подтверждённым серверным фактам;
- рабочее действие возле соответствующего POI, подтверждение результата, обновление инвентаря/навыка;
- покупка и употребление пива: нельзя показать успех до server ack; повтор/timeout не должен дублировать
  списание;
- `me.journal` и `me.feed` не дублируются при приходе full + fast frames; монотонные seq обрабатываются
  корректно;
- UI не перекрывает игровой обзор постоянно: меню «Дела» по Tab, F1 сворачивает HUD, подсказки контекстны,
  текст читаем на реальном разрешении; IMGUI пока допустим как временная реализация, но не выдавай его за
  финальный UI;
- ошибки транспорта/отказ сервера/потеря персонажа отображаются честно и не оставляют застрявшие input,
  курсор или pending actions.

Не переписывай всё ради архитектурной чистоты. Разделяй CoreGameplay на небольшие компоненты только если
это прямо снижает риск и не превращает итерацию в рефакторинг без игрового результата.

## Часть C — серверный regression hardening

Проведи аудит актуального Go main и исправь в том же PR только небольшие дефекты, непосредственно
мешающие этому циклу или нарушающие уже объявленные гарантии.

**Известный конкретный дефект для проверки и исправления:**
- В `sim/frontier.go / OpenFrontier` проверка `total + cfg.Villages > cfg.Max` не учитывает город,
  который добавляется на каждом `CityEvery`-м открытии. В результате `-frontier-max` может быть
  превышен. Рассчитывай полное число новых поселений (деревни + условный город) до мутации мира.
  Добавь тесты: обычный край; край с городом; ровно в лимит; на один ниже требуемого места; повторный
  OpenFrontier; Max=0/disabled. Не оставляй частично открытый край при отказе по лимиту.
- Проверь, что `/api/stats` frontier counters совпадают с фактическим числом поселений и не вызывают
  неявного создания FrontierCfg во время чтения, если это возможно по текущей архитектуре.

**Проверка горячих/холодных регионов:**
- Игрок, начавший Journey, должен прогревать destination без появления дублирующих тел/движения в source.
- При отмене/разрыве/завершении Journey температура и материализация должны сходиться.
- Удалённые поселения не должны оставлять живые ScenePos/NPC/foes после archive.
- Добавь regression tests на 2 игроков в разных поселениях и на party journey, если обнаружишь расхождение.

**Бой и быстрые кадры:**
- Проверь ограничение частоты fast frames (2..15 Hz), размер/состав fast frame, отсутствие утечки чужого
  инвентаря/личных данных и корректное применение reqid/result.
- Убедись, что fast frames не теряются/не переупорядочиваются относительно full snapshots на одном WS
  соединении, а клиент не затирает новые данные старыми.
- Проверь серверные пределы для клиентских aim/accuracy/power/target: клиент не может сам назначить
  попадание/урон/дальность. Если всё уже валидируется — добавь тесты, не дублируй механику.

## Часть D — воспроизводимая проверка

Добавь минимальный end-to-end сценарий, который можно повторять локально:
1. запустить тестовый сервер с фиксированным seed и demo profile;
2. создать/войти тестовым аккаунтом;
3. подключиться WebSocket-клиентом;
4. пройти последовательность talk → work → buy beer → consume beer;
5. после каждого шага проверить серверный результат и фактическое состояние, включая journal/feed/task;
6. повторить хотя бы один платный запрос с тем же reqid и доказать отсутствие второго списания;
7. проверить один отказ (например, work вне POI или talk с недоступной целью);
8. завершить сессию и проверить отсутствие оставшегося session control.

Это может быть Go integration test + маленький smoke harness. Не добавляй production endpoint и не ослабляй auth/валидацию
ради теста. Фиксированный seed, временные файлы, cleanup и детерминизм обязательны.

## Acceptance criteria

- [ ] Реальная Unity 6000.6.7f1 сборка/PlayMode проверена ИЛИ явно зафиксирована блокировка отсутствием Editor.
- [ ] Все воспроизводимые compile/runtime ошибки исправлены.
- [ ] Сквозной цикл talk → work → beer проходит через реальный сервер и Unity UI; успех отображается только
      после server-confirmed state/result.
- [ ] Никакого изменения wire contract / GeometryVersion без отдельного согласования.
- [ ] Frontier max учитывает город и покрыт граничными тестами.
- [ ] Проверены fast/full frame merge, reqid retry и очистка pending state.
- [ ] Go: `gofmt`, `go build ./...`, `go vet ./...`, `go test ./...` — приложить точные результаты.
- [ ] Unity: приложить точный Editor/CLI build result, логи и список вручную проверенных сценариев.
- [ ] Обновить README/ROADMAP только по фактически реализованному; не объявлять незапущенное «готовым».
- [ ] Итоговый comms-ответ: changed files, причины, тесты, риски, известные ограничения, следующий шаг.

## Что НЕ делать в этой итерации

- Не добавлять indoor/interior поля, дверные проёмы в Layout API или новый wire.
- Не реализовывать бесшовную глобальную географию/streaming.
- Не превращать `op:"travel"` в обычное перемещение толстого клиента.
- Не добавлять новые боевые стили, новые профессии, новые типы квестов и новые поля snapshot.
- Не менять экономический баланс «на глаз».
- Не делать массовый рефакторинг UI до прохождения сквозного цикла.
- Не мерджить без отдельного подтверждения владельца.
