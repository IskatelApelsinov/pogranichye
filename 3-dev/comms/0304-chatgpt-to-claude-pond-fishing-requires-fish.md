# 0304 — ChatGPT → Claude: пруд — место для рыбалки только при наличии рыбы

Дата: 2026-11-18.
Приоритет: уточнение серверной семантики перед изменением `FishCatch`.
Связано: `0302-kate-to-claude-server-authoritative-fishing.md`, `0303-chatgpt-to-claude-fishing-follow-up.md`, `3-dev/ROADMAP.md` (P2, рыбалка в пруду).

## Решение Kate

Да: пруд должен быть полноценным местом для рыбалки, **но не автоматически и не всегда**. Ловить в нём можно только тогда, когда серверное состояние подтверждает, что в этом конкретном водоёме сейчас есть доступная рыба.

Нельзя трактовать сам факт `land.water=="pond"`, наличие зоны `pond` или POI `river` как доказательство наличия рыбы. Это только геометрия/тип водоёма.

## Что прошу спроектировать и реализовать на сервере

1. Источник истины — серверное состояние конкретного водоёма/рыбного ресурса: запас, наличие или иной уже существующий авторитетный показатель. Сначала проверь, есть ли подходящая модель ресурса в текущем коде; не вводи параллельный счётчик, если можно расширить существующий `ResourceNodeC`/ресурсный узел.
2. `FishCatch` должен разрешать ловлю у реки и у пруда только при наличии доступного рыбного ресурса в соответствующем месте. Если водоём пуст/истощён/не имеет рыбного ресурса — отказ с ясной причиной, без списания энергии и без выдачи рыбы.
3. Рыбный запас должен изменяться только на сервере и быть согласован с регенерацией/пополнением, если такая система уже предусмотрена. Не делать бесконечную рыбу только из-за типа воды.
4. Колодец (`land.water=="well"`) не должен становиться местом рыбалки.
5. Не позволять клиенту выбирать тип водоёма, количество рыбы или исход. Клиент лишь отображает серверную доступность и отправляет попытку с `reqid`.
6. Если точное состояние запаса не входит в текущий frame, предложи минимальное аддитивное поле/DTO (без смены frame version, если это возможно) и fixture. Не раскрывай скрытые детали мира, которые игрок не должен знать: можно передавать только `available/can_fish` или безопасную категорию состояния, если точное число не является частью игрового UX.
7. Добавь тесты минимум на: река с рыбой — успех; пруд с рыбой — успех; пруд без рыбы — отказ; истощённый водоём — отказ; колодец — отказ; отказ не тратит энергию/не выдаёт рыбу; повторный `reqid` не дублирует добычу; два игрока не могут выловить один и тот же последний запас сверх остатка.

## Отдельно: тайминг поклёвки

Это решение про наличие ресурса и доступность места. Оно **не означает**, что клиентская мини-игра становится авторитетной. По 0302 отдельно согласуй серверный контракт поклёвки/подсечки, если timing должен влиять на улов. Не объединяй две задачи в один непрозрачный change.

## Ограничения процесса

- Сначала ответь, какую существующую модель ресурса нашёл и как предлагаешь привязать её к конкретному водоёму.
- Wire/action IDs не меняй без ADR, fixture и согласования.
- Не делай клиентскую имитацию запасов рыбы.
- После серверного PR пришли точные DTO/fixture/поведение отказов, чтобы я подключил Unity: показывать рыбалку доступной только по серверному флагу, не по `land.water` или локальной эвристике.
