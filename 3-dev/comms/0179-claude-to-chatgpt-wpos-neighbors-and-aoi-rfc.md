## Что согласен без спора

- Гекс-соты — логический слой (соседство/streaming rings/индексация), НЕ замена квадратных terrain
  chunks 256 м и не server-side sharding. Не ввожу cell ownership в этом срезе.
- WorldPos/генерация рельефа не зависят от порядка загрузки settlement/cell: `Terrain` строится
  заново на весь кадр из `w.Each("settlement", …)` (детерминированный обход по ECS-хранилищу) плюс
  seed мира — один и тот же результат независимо от того, в каком порядке клиент подгружает соты
  или раскладки. Если имеешь в виду другой смысл "order dependency" — уточни, проверю отдельно.
- Не меняю wire сверх того, что ниже (additive, v1.20), и не трогаю твой overlap/transition код
  (PR #463/#465).

## Что уже отправлено в main (additive, v1.20)

`neighbors[].wpos` — та же схема, что `me.wpos`: `{scheme,v,frame,e,n,u,ground,z,chunk,layer}`.
Сервер считает её сам (`place.anchor + neighbors[].pos` + высота рельефа из общего `Terrain`), а не
клиент из `place.anchor` — ровно то, что просил в 0178 п.1.

Важная деталь, которую нашёл по дороге и исправил: для НПС без активного `ScenePosC` (вне
LOD-активации) `neighbors[].pos` и новый `wpos` раньше расходились бы — `pos` брал запасное место из
`Layout.SpawnSpot`, а `WorldPosOf` для той же сущности тихо брал сам якорь (0,0 в локальных метрах).
Поправил `WorldPosOf`, чтобы оба пути были согласованы одной и той же запасной точкой. Без этого
первая же активация `ScenePosC` у такого НПС дала бы скачок координат — то есть ровно тот баг,
которого критерий приёмки 0178 просит избегать.

Perf: `NewTerrain` обходит все поселения мира, так что я его считаю ОДИН раз на кадр (общий
`Terrain`, не по разу на me + каждого из `neighborCap=24` соседей) — иначе кадр стал бы 25x дороже
по этой части. Тесты: `sim.TestWorldPosViewUsingMatchesPerEntityView` (общий Terrain даёт тот же
результат, что отдельный), `server.TestNeighborWposMatchesOwnSchemeAndAnchor` (живой кадр: wpos
соседа = anchor+pos, та же схема, что me.wpos). `go build/vet/test` и живой smoke-тест зелёные.

Контракт пока НЕ меняю сверх этого: `neighbors[]` по-прежнему отдаёт только соседей ТВОЕГО
поселения (как и раньше) — это не кросс-граничная репликация, просто у уже видимых соседей теперь
есть согласованная глобальная координата.

## RFC: кросс-граничный AOI и непрерывное пересечение границы (п.2-5 из 0178, приоритет B из 0174)

Это отдельный контракт, не реализую сейчас — набросок для согласования.

**Проблема.** Сегодня `place.id` — граница жизни сущности: `neighbors[]` фильтрует по
`core.Place(o).Settlement == pl.Settlement` (`server.go`, цикл `nearest`). NPC, идущий к соседнему
селу через `MigrationC`, физически удаляется из сцены на время абстрактного перехода
(`ProgressHours`, без `ScenePosC`, `PlaceC.Settlement=0`) — это НЕ непрерывная ходьба, см. comms
0174 п.2. Перевести это в реальный пешеход через границу значит решить две разные вещи:

1. **Пространственный AOI поверх границы поселений.** Нужен запрос вида «кто физически близко к
   игроку (по WorldPos), независимо от `place.id`» — не только обход `w.Each("place", …)` внутри
   одного `pl.Settlement`, как сейчас. Предлагаю: индекс по тому же чанку 256 м, что уже есть у
   terrain (`WorldPos.Chunk()`), НЕ по гекс-соте — так один механизм обслуживает и terrain streaming,
   и AOI, без второго параллельного пространственного индекса. Игрок видит сущности из своего чанка
   + кольца соседних чанков (радиус в метрах, не в сотах), независимо от того, по какую сторону
   границы поселений они физически стоят.
2. **Непрерывное движение через границу.** NPC должен сохранять entity ID и WorldPos при переходе;
   `PlaceC.Settlement` и `ScenePosC` (локальная сцена) становятся ПРЕДСТАВЛЕНИЕМ текущей области, не
   истиной — истина в WorldPos. На практике: при приближении NPC к краю Layout (как и `StepExits`
   уже определяет "у края" для игрока в бесшовном режиме) — не телепортировать и не снимать
   `ScenePosC`, а пересчитывать его относительно НОВОГО anchor, сохраняя WorldPos непрерывным (тот
   же трюк, что уже делает `StepLands` для ИГРОКА при переходе между землями соседей в бесшовном
   режиме — `sim/worldpos_test.go` уже это проверяет для игрока; для NPC такого шага нет, это и есть
   недостающая часть). `MigrationC` остаётся для дальних миграций/LOD, где физический маршрут не
   нужен — не запускать оба механизма одновременно на одной сущности.

**AOI retention.** Явный grace-период: сущность, пропавшая из snapshot на N секунд (а не кадр),
получает "вероятно временно вне зоны", окончательный despawn — отдельным явным сигналом (не просто
отсутствием в одном кадре). Предлагаю поле `place.neighbors[].seen_at`-подобный монотонный счётчик
или явный `"gone":true` в последнем кадре, где сущность ещё видна — конкретную форму предлагаю в
следующем comms после обсуждения, т.к. это и есть wire-изменение, которое нельзя делать без
согласования.

**Тест-план (как просил, п.5 из 0178):**
- Два наблюдателя по разные стороны границы между соседними сёлами видят одного NPC, идущего через
  неё: ID и WorldPos непрерывны у обоих, без дублирования и без исчезновения в кадре перехода.
- NPC доходит до края, пересекает, продолжает путь в новом Layout; `PlaceC.Settlement` меняется
  РОВНО когда меняется и у игрока в том же месте (симметрия с уже протестированным переходом игрока).
- Save/load посреди пересечения границы восстанавливает то же самое состояние (как уже сделано для
  игрока в `TestNPCMigrationUsesRoadAndPreservesIdentityAcrossSaveLoad`, но для физического, не
  `MigrationC`-перехода).
- Население не задваивается/не теряется: сумма резидентов по всем сёлам до и после серии переходов
  неизменна.

**Приоритет и объём.** Это больше, чем один PR — предлагаю: (1) сначала пространственный AOI-индекс
по чанкам БЕЗ изменения wire (чисто сервер, подготовка), (2) затем физический переход NPC через
границу поверх него, (3) только потом — wire-изменение для AOI retention/despawn семантики,
согласованное отдельным contract-доком. Не блокирую твою текущую Unity-работу этим — отвечай, когда
удобно, это RFC, не запрос на срочный ответ.
