## Что проверено в Unity main

- `WorldFrame.me.wpos` уже содержит глобальные координаты в общей системе `yof-tangent` (frame, E/N/U).
- `PlaceFrame.anchor` задаёт глобальный якорь текущего поселения.
- Но `NeighborFrame` пока содержит только `pos: ScenePositionFrame` (локальные X/Y/facing). Поля глобальной позиции у NPC/соседей нет.
- `EntityViewRegistry.Apply` преобразует `neighbor.pos` напрямую в Unity position и в конце кадра уничтожает все views, чьи ID отсутствуют в текущем `place.neighbors`.
- Следовательно, клиент не может корректно переносить NPC через границы поселений: локальные координаты двух поселений несопоставимы, а отсутствие NPC в одном snapshot приводит к удалению его GameObject.
- Клиентская README прямо отмечает, что текущий settlement-scoped layout/terrain путь не готов к seamless; это верно и должно оставаться критерием приёмки.

## Запрос к серверной стороне

Предлагаю сначала согласовать additive v1 контракт (без немедленного изменения runtime до согласования):

1. Добавить необязательный `neighbors[].wpos` той же схемы и семантики, что `me.wpos`: `scheme, v, frame, e, n, u, ground, z, chunk, layer`. Глобальные координаты должны быть серверно-авторитетными, не вычисляться клиентом из меняющегося `place.anchor`.
2. Реплицировать игроков и NPC по пространственному AOI через границы поселений. `place.id` не должен быть границей жизни entity или причиной смены/сброса entity ID.
3. Определить стабильное поведение при временном выходе из AOI: grace/retention policy и явный despawn либо tombstone, чтобы клиент отличал кратковременное отсутствие snapshot от окончательного удаления.
4. Уточнить, остаётся ли `neighbors[].pos` как локальная совместимость/анимационный ориентир, и как выбирается authoritative источник позиции при наличии `wpos`.
5. NPC movement должен идти в общей мировой системе координат непрерывно; переход через границу settlement/hex cell не должен быть телепортом или пересозданием entity.

## Запрос к Unity-клиенту после согласования

- Сохранять один `EntityViewRegistry` на протяжении перехода и связывать view с постоянным server entity ID.
- При наличии `wpos` преобразовывать глобальную позицию в локальную относительно текущего presentation origin (с double precision до финального Vector3).
- Не удалять view только потому, что entity временно отсутствует в одном snapshot; удаление — только по явному despawn/TTL и политике AOI.
- Не пытаться вычислять глобальную позицию соседа из текущего `place.anchor`, если сосед может находиться в другом settlement.
- Оставить локальный `pos` fallback только для старых серверных кадров без `wpos`, с явно ограниченным режимом совместимости.

## Отдельный layout streaming

Клиентская multi-layout cache работа должна опираться на глобальный anchor и frame каждого layout. Старый и новый layout roots могут сосуществовать во время overlap; нельзя вызывать глобальный cleanup при замене одного поселения. Кэш должен иметь ограниченную retention policy и освобождать root/assets только после выхода игрока из зоны удержания и готовности следующей геометрии.

Не меняем размер существующих квадратных terrain chunks 256 м и не подменяем их гекс-сотами. Hex cells остаются логическим уровнем.

## Критерии проверки

- NPC подходит к границе, проходит её пешком и остаётся тем же entity ID/Unity GameObject.
- Игрок видит NPC с обеих сторон границы без исчезновения, дублирования, скачка координат и смены анимации.
- Возврат через границу сохраняет личность, знакомство и актуальное состояние.
- При потере AOI и настоящем despawn view удаляется предсказуемо, без утечек.
- Два и более layout roots одновременно отображаются с корректными глобальными смещениями; выгрузка одного не портит материалы/меши другого.
