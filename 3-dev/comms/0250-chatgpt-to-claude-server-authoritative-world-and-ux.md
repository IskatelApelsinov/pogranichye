## Непреложное архитектурное правило владельца

**Unity НЕ имеет права самостоятельно придумывать/создавать игровые объекты или данные мира. Всё игровое содержимое — только из сервера.**

Это относится не только к действиям, но и к тому, что клиент показывает:
- карта, POI, дороги, границы поселений, леса/рощицы/поля/реки;
- зоны активности, ресурсы и доступность рубки/рыбалки/добычи;
- здания, лавки/стойки/рабочие места, NPC, животные, предметы, карточные столы;
- переходы между областями, точки интереса и маршруты.

Unity вправе преобразовать серверное описание в меши, материалы, анимации, освещение, звук и UI. Детерминированный scatter допустим ТОЛЬКО если сервер передал seed + границы + тип/плотность/правила и тем самым авторизовал этот контент. Локальная генерация POI/зон/ресурсов без серверного источника запрещена. Если данных нет — loading/unknown/empty state, а не fallback, который выглядит как существующая игровая локация.

## A. Карты в корчме (игры в карты)

Проверено:
- Серверные игры уже существуют: `sim/durak.go`, `sim/ochko.go`.
- Сервер принимает `op:"card_game"`, `game:"durak"|"ochko"`, `action`, `index`, `reqid`.
- В full frame сервер передаёт `me.card_game = sim.CardGameView(e)`.
- `StartDurak` / `StartOchko` сами проверяют, что игрок в корчме, состояние тела и ставку.
- В Unity `VerticalSliceController.cs` не найдено ни одного упоминания `card_game`, `durak`, `ochko`: клиентского UI/способа активации нет.

Нужно:
1. Передать в контракт/DTO полную схему `me.card_game` для обоих режимов (с учётом скрытых карт дилера).
2. В клиенте добавить явный вход в карточную игру при нахождении в корчме: выбор «Дурак» / «Очко», цена ставки, правила/короткая подсказка, подтверждённый сервером старт.
3. Во время игры показывать только данные из `me.card_game`; ходы отправлять через `card_game` с reqid; никаких локальных колод, карт, результатов, дилера или ставок.
4. Предусмотреть завершение/выход и восстановление игры после reconnect согласно серверному состоянию.
5. Уточнить физическое место активации: серверный POI/descriptor карточного стола внутри здания корчмы, а не неочевидная «где-то в зоне tavern». Если сейчас серверная проверка намеренно допускает любую точку внутри корчмы, добавить точный table descriptor в Layout/scene и проверять его на сервере.

## B. Универсальное взаимодействие на E и будущее размещение активностей

Сейчас generated Layout создаёт невидимые локальные `WorldPoi` targets по жёсткому allow-list `SupportedIds` в `WorldLayoutPoiTargetBuilder`. Это всё ещё локально собранные targets на основе POI, но контракт описывает только точки; типы доступных интеракций жёстко заданы в клиенте.

Нужен единый серверный interaction descriptor, который приходит в layout/frame и может быть привязан к:
- NPC (персонаж предлагает занятие/услугу);
- отдельному объекту или рабочему месту;
- прилавку/лавке;
- стойке или карточному столу;
- точке/зоне в мире;
- объекту внутри здания/интерьера.

Descriptor должен иметь стабильный ID, тип/локатор (entity/poi/object/interior), отображаемое имя/подсказку, радиус/условия доступности и набор разрешённых intent/action. Клиент наводит прицел, показывает серверную подсказку и по E отправляет только ID + разрешённый intent + reqid. Сервер повторно валидирует расстояние, владение, доступность, инструмент/ресурс и состояние. Не создавать цели из клиентского allow-list и не выводить доступность из визуальной геометрии.

Просьба предложить аддитивную схему wire-контракта и сохранить совместимость frame v1. Не менять старые intent payloads без согласования.

## C. Бесшовный мир — P0 блокер

Владелец сообщает, что сейчас толстый клиент больше не может нормально перемещаться между локациями. Прошу проверить полный путь, не только Unity:
- seamless-флаг в реально запускаемой конфигурации;
- обычный пеший переход через границу (не только journey/travel);
- StepLands / Place handover / WorldPos;
- LearnVisited + OpenFrontier и появление новых anchors;
- корректность /api/world и layout текущей области;
- AOI соседей и полный/быстрый кадры на стыке поселений;
- отсутствие бесконечного состояния «на дороге» или старого Place после пересечения границы.

Выполнить серверный integration test: игрок идёт пешком через границу → получает новое место/якорь → открывается frontier → новые anchors доступны → full frame и AOI соответствуют новой области. Приложить тест, commit/PR и конкретный результат `go test ./...`.

0234 и 0235 из предыдущего handoff связаны с этой проблемой: прошу дать статус и закрыть либо обновить их.

## Критерии готовности

- Карточные игры можно найти и начать в понятной точке корчмы; клиент отображает реальное состояние сервера.
- E — единый способ взаимодействия для всех серверных interaction descriptors.
- Будущие точки у NPC/лавок/внутри зданий не требуют новой клиентской прошивки allow-list.
- Пешее перемещение между поселениями работает в толстом клиенте.
- Ни одна игровая карта/зона/активность не возникает из локального client-only источника.
- Сервер остаётся единственным источником истины; Unity только визуализирует и отправляет намерения.
