## Приоритет 1 — проектирование реального NPC spatial simulation

После #16/#17 подготовить отдельный design/implementation PR для server-owned spatial movement поверх существующего mind loop.

Требования:
1. У каждого NPC stable ID и persistent canonical ScenePos (X/Y/Facing), а не координата, вычисляемая только при snapshot.
2. Цели/занятия по-прежнему выбирает существующий mind/activity loop. Spatial layer переводит цель в маршрут/движение, не дублируя AI.
3. Маршруты через POI/waypoint graph для стартового поселения; движение должно быть детерминированным/seeded и устойчивым между тиками/переподключениями.
4. Нужны server-side статические препятствия и collision/navigation constraints. Не делать вид, что локальные Unity collider'ы синхронизированы с сервером.
5. Согласовать минимальную общую геометрию и её версию: POI/waypoints, проходимые сегменты/зоны, здания/заборы/вода/мост. Предложить способ держать Unity presentation layout и серверную навигацию согласованными. Не добавлять protocol fields без согласования.
6. Для дальних NPC определить coarse/offline simulation policy; они не должны телепортироваться в случайное кольцо при возвращении игрока.
7. Snapshot `neighbors[].pos` должен использовать фактическую persistent ScenePos. Удалить `NeighborPos(id)` из runtime snapshot path только после того, как реальные позиции готовы.
8. Добавить unit tests: стабильность seed/позиции, движение по маршруту, отсутствие прохождения через blocked edge/obstacle, смена activity goal, восстановление после reconnect/restart в рамках принятой persistence-модели.
9. Сначала маленькая вертикаль: 4–6 жителей, несколько POI (таверна, кузница, огород, колодец/рынок), один короткий маршрут туда-обратно. Не пытаться сразу симулировать весь город.

До начала кодирования пришли в PR/комментарии:
- какие существующие компоненты/системы можно использовать;
- минимальную модель ScenePos/route/POI и где хранить состояние;
- точную геометрию стартовой деревни и способ синхронизации с Unity;
- tick rate/LoD policy;
- набор тестов и разбивку на PR.
После краткого design review можно реализовывать первую малую вертикаль. Никакого client-side fake NPC movement.

## Приоритет 2 — серверный пивной цикл для конференционной демо

Параллельно подготовить **предложение контракта**, но не менять протокол и не писать несогласованные серверные/клиентские поля.

Требуемый сценарий:
- игрок подходит к стойке/корчмарю;
- сервер проверяет расстояние, наличие пива/запаса и монет;
- покупка атомарна и идемпотентна (повтор запроса не списывает монеты дважды);
- сервер возвращает/реплицирует факт покупки и предмет/состояние кружки;
- игрок выполняет отдельное действие употребления; сервер изменяет соответствующие needs/status только по правилам мира;
- клиент показывает кружку, руку и анимацию только после серверного подтверждения/состояния.
- Ошибка или недостаток средств/запаса не должны частично менять состояние.
- Не использовать `socialize` или `eat` как подмену питья.

Для будущего co-drink отдельная фаза: invite/accept/decline, session ID, синхронизированное начало, proximity, отдельные проверки оплаты/запаса, cancel on disconnect/leave. Не включать её в минимальный solo-beer PR, если это увеличит риск.
