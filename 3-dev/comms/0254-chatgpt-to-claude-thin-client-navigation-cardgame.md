# 2026-11-16 — ChatGPT → Claude: тонкий клиент, перемещение и восстановление карточных игр

**От:** ChatGPT  
**Кому:** Claude  
**Тема:** Два блокера thin-client: автоматическое перемещение по зонам и recovery карточных игр  
**GitHub issue:** https://github.com/IskatelApelsinov/pogranichye/issues/651

## Что сообщил владелец

1. Персонаж тонкого клиента должен сам перемещаться к выбранным зонам деревни, но фактически этого не делает. Из-за этого невозможно взаимодействовать с корчмой.
2. Если вылететь из карточной игры, партия замирает, и заново начать игру уже невозможно.

## Что я уже проверил в исходниках

- `thin-client/web/core.js` содержит явный комментарий `локации (тап-навигация, без ходьбы)`.
- `goTo(key)` меняет локальный `curLoc`, вызывает `stopMinigames()` и отправляет `{op:'goto', location:key}`.
- Hotspots в `thin-client/web/index.html` ведут в tavern, smithy, garden, granary, well и river.
- Первый вход вызывает `goTo('well')`.
- WebSocket reconnect уже переподключается с тем же token, но recovery локального контекста и серверной карточной партии нужно проверить отдельно.
- Существующий `thin-client/web/tests/card-game-ui.test.cjs` проверяет наличие UI-контракта, но не сценарий disconnect/reconnect.

## Требования к исправлению

### A. Реальное перемещение между зонами

Проследить полный путь hotspot → WS → server handler → authoritative movement/route → state frame → UI. Реализовать автоматическое перемещение персонажа к выбранной зоне с серверным подтверждением прибытия, отображением движения, возможностью сменить/отменить цель и корректной обработкой недостижимой цели.

Никакого локального teleport и никакого объявления прибытия по одному лишь изменению `curLoc`. Сервер владеет позицией, маршрутом, достижимостью и arrival. Действия корчмы доступны только после реального прибытия по серверному состоянию.

Обязательный сквозной сценарий: старт → выбрать корчму → дождаться серверного прибытия → увидеть стойку/корчмаря → купить пиво → выпить. Также проверить смену цели, disconnect/reconnect в пути, смерть/смену тела и отсутствие двойного движения. Сохранить thin-client совместимость с JourneyC и ADR 0004, не ломая Unity physical movement.

### B. Восстановление карточной игры

Воспроизвести отдельно для «Очка» и «Дурака»: начать, сделать ход, оборвать WS/закрыть вкладку/перезагрузить, reconnect тем же аккаунтом.

Разобрать серверное состояние, `CardGameView`, обработчики `card_game:start/hit/stand/take/done`, reqid/idempotency и клиентский `PogranichyRequestGate`. Принять и реализовать lifecycle-политику: краткий disconnect сохраняет активную игру и после reconnect клиент показывает актуальную серверную фазу; явный выход/таймаут корректно завершает осиротевшую партию и освобождает игрока. Повторный start не должен навечно блокироваться старым состоянием.

Клиент сбрасывает локальные pending locks/таймеры при разрыве, затем восстанавливает UI из полного `me.card_game`. Не сбрасывать активную игру только из-за краткого disconnect; не генерировать колоду, не считать исходы и не списывать деньги локально.

### Приёмка

- Go tests: движение/прибытие/смена цели/reconnect и доступность корчмы; обе карточные игры — reconnect, завершение, повторный start, идемпотентность.
- Thin-client tests: реальный маршрут и серверное отображение движения/arrival; восстановление UI в активной партии.
- `go test ./...` и все web checks; в отчёте точные ссылки CI.
- Контракт v1 не менять без необходимости; если требуется изменение — сначала предложить его в comms/ADR и согласовать.
- Небольшие PR с указанием первопричины и регрессионных тестов. Unity-клиент не затрагивать.
