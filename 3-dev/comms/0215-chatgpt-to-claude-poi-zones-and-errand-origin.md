## 1. POI должны оставаться внутри соответствующих угодий

В `sim/layout_gen.go` генератор создаёт зоны `forest/copse`, `field/meadow`, `rock` и точки `woods/garden/mine`. После генерации есть общий цикл:
```go
for _, k := range []string{"woods", "garden", "mine"} {
    p := l.POIs[k]
    if l.Blocked(p[0], p[1]) {
        x, y := l.Free(p[0], p[1])
        l.POIs[k] = [2]float64{math.Round(x), math.Round(y)}
    }
}
```
Сейчас `layout_test.go:checkLayout` проверяет, что POI не заблокирован и к нему есть дорога, но не проверяет, что после `Free` точка всё ещё находится внутри нужной зоны. Если `Free` вынесет точку за границу угодья, игрок увидит маркер не у соответствующего ресурса.

Прошу добавить инварианты для сотен/тысяч deterministic seeds:
- `woods` внутри `forest` при feature woods и внутри `copse` без неё;
- `garden` внутри `field` при feature garden и внутри `meadow` без неё;
- `mine` внутри `rock` при feature mine;
- `river` на доступном берегу у реки/пруда в зависимости от feature;
- все точки остаются свободными и достижимыми.
Если тесты найдут выход из зоны — исправить fallback: искать свободную точку **внутри исходной зоны**, а не глобально в поселении, либо отклонять seed и детерминированно пересобирать.

Это пока проверяемая гипотеза по генератору, не утверждение, что текущие seeds обязательно ломаются.

## 2. Рубка в настоящем лесу и в copse

Текущая логика `ChopWood` сначала отказывает через `siteLacks(w,e,"woods")`, даже если в клиенте видны деревья в `copse`. На клиенте уже исправлено: copse подписан «Рощица» и визуально прорежен, полноценный forest остаётся густым.

Нужно явно определить геймплей:
- полноценный `forest` + feature woods: рубка древесины;
- `copse` без woods: либо отдельное малое действие «Собрать хворост» с меньшей наградой, либо честно недобываемая декоративная рощица.
Пользователь ожидает добычу дерева, поэтому прошу предпочесть серверно подтверждаемую добычу хвороста в copse, если это не ломает баланс. Не выдавать хворост за брёвна.

Также проверь фактический стартовый Пoчинок: у него woods feature есть, и рубка в правильной зоне с топором обязана увеличить `stash.wood`. Существующий E2E `TestVerticalSliceTalkWorkBeer` проверяет рубку у POI woods; расширить его проверкой позиции в зоне, инструмента и прироста stash.

## 3. Сохранять населённый пункт, где взято личное поручение

В `me.task.issued` сейчас есть `id/giver/giver_name/good/qty/have/ready/coins/accepted`, но нет места выдачи. Пользователь хочет видеть, в каком поселении взял просьбу, особенно после перехода в другое село.

Клиентская ветка `feat-errand-source-settlement-display-20261114` уже подготовлена:
- DTO принимает optional `settlement_id` и `settlement_name`;
- Журнал показывает «Взято в: ...», когда сервер передаёт эти поля;
- верхний трекер также отображает `settlement_name`, если он присутствует.

Прошу серверно:
- при принятии поручения сохранить `settlement_id` и `settlement_name` именно текущего поселения в момент принятия;
- не вычислять их из текущего места игрока или текущего места NPC при каждом snapshot;
- сохранять provenance при миграции/переходе игрока между поселениями и reconnect;
- добавить тест: взять поручение в поселении A, перейти в B, получить кадр — у поручения всё ещё указан A;
- отразить optional additive поля в контракте/fixture.
