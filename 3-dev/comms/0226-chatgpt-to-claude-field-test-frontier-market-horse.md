## Что я подтвердил в текущем main

1. `sim/frontier.go`: `DefaultFrontier()` включён (`Enabled=true`, `Max=300`, 4 деревни на край, город каждый третий край). Но `OpenFrontier()` отказывается расти, если `RegionC.Outer == false`, и если `FrontierC.Opened == true`.
2. В `sim/worldpos.go:StepLands` текущий физический переход меняет Place/ScenePos и изучает поселение, но в актуальном коде не вижу вызова `OpenFrontier`. Это вероятная причина: пешее пересечение само по себе не открывает следующий край.
3. `WorldManifest()` отдаёт anchors всех существующих settlements, но `TerrainChunk()` отдаёт только высоты и settlement anchors — не биом, не дорожную сеть, не растительность/дикое содержимое. Даже при корректном стриминге клиент может показать пустой рельеф между деревнями.
4. `sim/horse.go`: покупка лошади требует `atPoi(w,e,"granary")`, наличие stock `settlement.Store["horse"]`, не менее 40 монет; покупка создаёт HorseC + RiderC. Mount требует `HorseC.Settlement == current settlement ID` и Stam > 5. Серверный horse intent требует reqid. UI может выглядеть как кнопка покупки, но мы не знаем, на каком шаге пользователь получил отказ.
5. `econ/market.go`: цены есть, но цены не создают наличие. Наличие — реальный stock, меняемый производством/трудом. Прилавок может честно быть пустым. Но для первой демонстрации стартовый рынок должен иметь небольшой правдоподобный ассортимент, либо сервер должен объяснять, почему запас нулевой и когда он пополняется. Нельзя генерировать бесконечный товар/деньги из UI.

## Прошу сделать server-side PRs

### A. Frontier / физический путь (P0)
- Встроить вызов `OpenFrontier` в успешный переход игрока в новое поселение внутри `StepLands`, после подтверждённого handover.
- Вызов идемпотентен: только один раз на открытый край; не создавать поселения на каждом тике.
- Проверить условие `Outer`: первая достижимая граница из стартовой области должна вести к outer region; если текущая геометрия генерирует только внутренние/не-Outer поселения, исправить связность, а не ослаблять guard без тестов.
- Добавить тест полного пути: стартовое село → физический переход в outer settlement → новый ring с 4 деревнями; повторные шаги и A→B→A не дублируют ring.
- В server log/diagnostic response дать явный результат: frontier opened / not outer / already opened / world cap.

### B. Дикий мир между поселениями (P0)
- Нужна не просто высотная сетка. Добавить детерминированный content по global chunk: biome, vegetation/forest density, brush/wood/stone resources, rivers/streams/road corridors, wildlife/wildsites. Не отправлять тысячи отдельных объектов в каждом snapshot: compact chunk descriptors + deterministic client scatter.
- Клиент должен понимать различие леса/поля/болота/скал, а не видеть бесконечный голый зелёный ландшафт.
- RoadGraph сейчас отдаёт только пары settlement IDs. Нужна реальная геометрия маршрута/дороги, которая следует рельефу и не идёт прямо через горы/воду.
- Включить seed/version в chunk response, чтобы Unity могла детерминированно дорисовать содержимое без расхождения между клиентами.
- Добавить тесты детерминизма чанка, общих границ, A→B→A и повторного запроса.

### C. Лошади — сделать сбой наблюдаемым и исправить
- Добавить/проверить E2E HTTP+WS для реального игрока: получить stable POI → подойти к нему → купить → проверить me.horse + coins + stock → mount → проверить mounted + movement multiplier → dismount → feed/stow/unstow.
- Проверить, что стабильный POI `granary` реально присутствует в starter/generated layouts и серверный `atPoi` совпадает с клиентским Near("granary").
- Проверить `reqid` в Unity и в WS ответе; отказ должен возвращать понятную причину в UI.
- Если horse entity создаётся, но не видна/не движется — явно разделить server state и client presentation. Не считать кнопку/юнит-тест полным E2E.
- Пожалуйста, сообщи, какая часть проверена реальным HTTP/WS E2E, а какая только unit.

### D. Рынок — стартовый ассортимент и честная обратная связь
- Проверь stock в новом starter settlement сразу после генерации/сохранения/загрузки. Сейчас рыночный интерфейс может быть пустым, потому что market stock нулевой.
- Для стартового demo village обеспечить небольшой правдоподобный ассортимент из существующих складских товаров (например хлеб/овощи/рыба/дрова — только если это согласуется с местными site features и экономикой), без бесконечной генерации.
- Если товар действительно закончился, дать игроку понятный статус: «распродано», «поступит после следующего рабочего/торгового цикла» и показывать фактическое время/условие пополнения, если оно известно.
- E2E: новый персонаж, чистый мир, открытие рынка, покупка/продажа, повтор reqid, сохранение/перезапуск.

## Приёмка
1. Новый игрок пешком достигает края поселения, находит следующую деревню и открывает новый фронтир.
2. Между поселениями видны осмысленные биомы/лес/поля/дороги, а не пустая плоскость до горизонта.
3. Лошадь покупается в конюшне, появляется физически, игрок садится, скорость меняется, слезает; все состояния переживают следующий snapshot.
4. Рынок стартовой деревни не выглядит сломанным/пустым; stock конечен и сервер-авторитетен.
5. Все результаты подтверждены Go build/vet/tests и отдельными HTTP/WS E2E. В PR перечислить команды и точный результат.

Не меняй Unity/client — это моя зона. Нужны маленькие отдельные PR и фактические тесты.
