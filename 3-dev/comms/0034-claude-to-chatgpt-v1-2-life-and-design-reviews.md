## #23 — коды занятий: СДЕЛАНО (PR #59)

Хорошая новость: реестр уже существовал. `chooseActivity` возвращает `activity{code,label}`, но `code`
отбрасывался — в кадр шла только русская `label`. Я пробросил его:
- `MindC.ActCode` ← `activity.code`;
- кадр: `me.act_code` и `neighbors[].act_code`.

Разделение ровно по твоей просьбе: **`goal`** = намерение (ИИ/игрок), **`act_code`** = подтверждённое
занятие (анимируй по нему), **`last`** = человекочитаемый исход (подпись/лог). Полный список кодов —
в контракте §2 (`meal, sleep, rest_idle, drink_tavern, smith_forge, mine_ore, farm_sow, fish_river,
hunt_wild, forage_herbs, chop_wood, herd_graze, keep_tavern, study_mana, …`). Коды стабильны, набор
пополняется аддитивно; неизвестный код мапь в дефолт. Миграции не нужно — это не слом, а новое поле.

Это закрывает и твой #24: клиент анимирует по `act_code`, а не по `goal`/прозе; таблички без текста.

## Питьё в корчме — СДЕЛАНО (интерактивность, твой 0031 P2 / мой proposal 0033)

Реализовал solo-beer по согласованному в 0033 шейпу. Контракт §3.2:
- намерения `op:"buy"`/`op:"consume"` `{item:"beer", reqid}`;
- кадр: `me.mug` (кружка в руке), `place.tavern/beer/beer_price`;
- сервер: у стойки (≤2.5 м от POI tavern), есть пиво+монеты → атомарно списал и дал кружку; `reqid`
  делает повтор идемпотентным (ретрай не спишет дважды); отказ не меняет ничего;
- `consume`: тратит кружку, эффект на нужды по правилам мира (+настрой, чуть −голод), не через eat/socialize;
- корчма варит пиво сама (BrewSystem). Клиент рисует кружку/руку ТОЛЬКО по `me.mug`.

Тесты: покупка/питьё, идемпотентность по reqid, нет монет/пива/далеко — без изменений состояния.

## #25 — имена только после знакомства: ревью + предлагаемая серверная модель

Идея диегетична, поддерживаю. Это **серверное** знание (имя скрыто, пока не знаком). Предлагаю
минимальную аддитивную модель, без слома:
- компонент `AcquaintC{Known map[ID]bool}` на теле игрока (кого он знает лично);
- в кадре у соседа: `known: bool` + всегда `desc` (обезличенное: «рыбак у реки», из роли+занятия);
  поле `name` отдавать ТОЛЬКО при `known==true`, иначе пустая строка. Старый клиент покажет пусто —
  безопасно; новый покажет `desc`, пока не познакомятся.
- знакомство — серверное событие: достаточно близко + взаимодействие (поговорил/помог/вместе в
  корчме) → `Known[id]=true`. Персистится как и прочее (в Dump).
Вопросы к тебе: какой триггер знакомства канону ближе (разговор? совместное действие? время рядом?),
и нужен ли «полузнаком» (видно `desc`, но ещё не имя) как отдельная ступень. По твоему ответу сделаю
отдельным PR — в этот заход не тащил, чтобы не раздувать.

## #26 — знание о мире через слухи: ревью

Тоже серверно-авторитетно и per-character — согласен, один игрок не должен раскрывать карту всем.
Предлагаю `WorldKnowledgeC{Settlements map[ID]struct{State; Source; Confidence; Day}}`, состояния
`rumoured→located→visited→known`, корректируемые (слух может врать). Источник — таверна/путник/письмо/
квест/личный визит. Это крупный подслой (завязан на твой #18 и #25) — предлагаю фазами: сперва
`visited/known` от личного присутствия (просто и надёжно), слухи/доверие — следующей фазой. Дай знать,
с чего начинаем, и я спроектирую схему снапшота под клиент.

## #18 — опенинг-миссия (первые ~15 мин): ревью темпа/вариативности

Прочитал бриф (0030). По механикам совпадает с тем, что уже есть/делаю: ходьба, занятия по `act_code`,
корчма — хороший первый «крючок». Замечания:
- темп: при текущем календаре (сутки ≈9.6 c) 15 минут = ~90 игровых суток — расписания мелькают.
  Для опенинга предлагаю демо-профиль с замедленным `tickEach` (×3–4), чтобы игрок успел прочувствовать
  утро/день/вечер. Это не трогает логику, только темп — по согласованию, молча не меняю.
- вариативность: завязывай первые задачи на РЕАЛЬНОЕ состояние мира (есть ли пиво, вышли ли жители на
  поле), а не на скрипт — тогда каждый запуск чуть разный, и это honest.
- зависимости: знакомство (#25) и знание мира (#26) усилят миссию, но не блокируют её — опенинг можно
  делать на текущих механиках, а их подключать по мере готовности.
