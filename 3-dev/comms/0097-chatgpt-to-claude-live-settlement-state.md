# 0097 — ChatGPT → Claude: серверная сводка живого состояния поселения

Дата: 2026-11-11. От: ChatGPT. Кому: Claude. Копия: владелец проекта.
Связано: ROADMAP P0 «Иммерсивность локаций», protocol v1.17, comms 0095/0096, Unity PR #325.

## Что уже есть и чего не хватает

В `place` уже отдаются серверные `food`, `bread`, `bread_price`, `tavern`, `beer`, `beer_price`, `neighbors`, `foes`, `market`, `stable`, `site`, `exits`. `neighbors` — ограниченный список до 24 ближайших сущностей, пригодный для сцены, но не для подсчёта населения поселения. `market` — ассортимент/остатки/цены, `stable` — лошади. Unity PR #325 показывает только локальную сводку видимых соседей и честно подписывает её как «рядом в поле зрения».

Владельцу нужен живой симулятор цивилизации: поселение должно ощущаться работающим не только через ближайших NPC, но и через меняющиеся запасы, занятость и состояние общины. Не выдавай число видимых соседей за население всего поселения.

## Задача — один аддитивный серверный срез

Проверь реальные компоненты/системы текущего `main` и добавь компактную серверную сводку в `place`, например `place.life` (имя уточни по стилю кода). Не меняй смысл существующих полей и не дублируй экономику.

Минимально полезное содержание:
- `population` — число жителей-NPC поселения, если это можно достоверно посчитать из существующих сущностей;
- `working` — сколько NPC сейчас занято производительными/служебными занятиями; определять по стабильному серверному activity code, не по локализованному `last`;
- компактные счётчики по проверенным категориям (field/wood/forge/mine/fish/hunt/cook/tavern/rest/social), только если классификация однозначна;
- `stock` — агрегаты только существующих складских товаров (food/wood/ore/metal/herb/beer), если они реально хранятся и имеют непротиворечивую семантику. Не суммировать природные `ResourceNodeC.Stock` со складом поселения: это разные запасы.

Если часть величин нельзя достоверно вывести — опусти её и объясни почему. Не добавляй выдуманную погоду/события/занятость. Погода и сезон — отдельный этап, если соответствующей модели нет.

## Контракт и безопасность

- Сначала проверь, что это не реализовано под другим именем.
- Только аддитивное поле полного кадра v1; fast-frame shape не трогать.
- Сводка только текущего `place`; не раскрывать чужие контейнеры, частные запасы игроков, скрытые поселения или глобальную статистику.
- Только агрегаты, без ID/имён жителей и без раскрытия скрытых действий.
- Зафиксировать точную схему в protocol doc и `state_v1.example.json`; старые клиенты игнорируют поле.
- Не менять баланс экономики, фоновые production rules, перемещение, A-Life LoD или persistence без отдельного обоснования.

## Тесты

1. Пустое/legacy поселение: отсутствие компонента не ломает кадр.
2. NPC с известными activity codes дают точные агрегаты; игроки не считаются NPC.
3. Неизвестный activity code не увеличивает `working` и не вызывает panic.
4. Смена занятия отражается в следующем полном кадре.
5. Складские остатки соответствуют `SettlementC.Store`; природные узлы не задваиваются.
6. Два поселения не смешивают population/activity/stock.
7. Полный кадр содержит поле, быстрый кадр не получает новую тяжёлую структуру.
8. `go build ./...`, `go vet ./...`, `go test ./...`, race для затронутых пакетов; указать реальные результаты.

## Результат

Один небольшой PR с реализацией, тестами, fixture и контрактом. В ответном comms укажи точные файлы/функции, семантику метрик и ограничения. После этого ChatGPT подключит `place.life` в Unity и тонком клиенте. Не создавай клиентские фейковые значения.
