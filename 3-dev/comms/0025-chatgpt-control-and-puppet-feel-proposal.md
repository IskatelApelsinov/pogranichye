# Pogranichye — схема управления персонажем и взаимодействий

Дата: 2026-11-02  
Статус: предложение для владельца и Claude; **не меняет сетевой протокол**.

Цель — управление «марионеткой»: игрок ощущает тело, инерцию, вес и намерение персонажа, но не борется с интерфейсом. Сложность должна появляться из игровых решений и освоения движений, а не из неудобных клавиш. Основной принцип: **одна и та же кнопка означает одно и то же действие в любом контексте**, а контекст может уточнять результат, но не подменять его неожиданно.

## 1. Два режима камеры, одна схема тела

### Third-person — обзор и социальное взаимодействие
- Камера следует за персонажем с мягким сглаживанием.
- Движение мыши без удержания кнопок — орбита камеры вокруг персонажа; персонаж не разворачивается от одного лишь осмотра.
- ПКМ — контекстная кнопка альтернативного режима удерживаемого предмета/инструмента: прицеливание из лука, подготовка заброса удочки, особая стойка/прицел инструмента, плетение магии и другие классовые действия. Сама ПКМ не должна автоматически останавливать обзор; конкретный режим решает, как использовать мышь.
- Колесо мыши — приближение/отдаление.
- При столкновении камера плавно приближается к персонажу, не проходит сквозь стены.
- Персонаж поворачивается по направлению движения, а не по направлению камеры, пока игрок не задаёт движение.
- Подходит для ходьбы по деревне, общения, осмотра одежды/снаряжения, бытовых действий, крафта и совместных сцен.

### First-person — точное действие
- Движение мыши всегда управляет взглядом; горизонтальный обзор задаёт направление взгляда/намерения, вертикальный ограничен комфортным диапазоном.
- ПКМ включает альтернативный режим текущего предмета/инструмента. Для лука — прицеливание (мышь продолжает управлять взглядом); для удочки — подготовка/заброс; для магии — плетение, где режим явно захватывает движение мыши и временно фиксирует камеру. Не каждый альтернативный режим должен перехватывать мышь.
- Отображаются руки и предмет в руках; тело остаётся полноценной сущностью мира.
- Центральная точка прицела помогает выбирать цель, инструмент, дверь или объект.
- Подходит для исследования, боя, инструментов, магии и точных взаимодействий.

Переключение вида: **V**. Переключение не телепортирует персонажа и не меняет серверную позицию. Переходы камеры плавные и не должны перехватывать управление неожиданно.

## 2. Предлагаемая клавиатура и мышь

| Ввод | Действие | Поведение |
|---|---|---|
| W / A / S / D | Движение | Вперёд / влево / назад / вправо относительно направления персонажа/камеры по согласованной схеме |
| Shift (удерживать) | Бег | Ускорение с затратой серверной выносливости; отпускание возвращает обычный шаг |
| Ctrl (удерживать) | Осторожный шаг / присесть | Тише и ниже силуэт; точные эффекты определяет сервер |
| Space | Прыжок / преодоление | Только если сервер поддерживает прыжок и проверяет поверхность/выносливость; иначе не показывать действие как доступное |
| Движение мыши | Осмотр / орбита | В FPS — взгляд; в TPS — орбита камеры; без удержания кнопок |
| ПКМ (удерживать) | Альтернативный режим предмета/инструмента | Лук — прицеливание; удочка — подготовка/заброс; магия — плетение. Только режимы жестового ввода явно захватывают мышь у камеры |

| Колесо мыши | Камера | Зум в TPS; в FPS не менять предмет/слот неожиданно |
| E (короткое нажатие) | Контекстное взаимодействие | Поднять, открыть, поговорить, начать работу, использовать станцию — в зависимости от подсказки |
| E (удерживать) | Контекстное меню | Открывает радиальное меню, только если у цели есть несколько допустимых действий |
| ЛКМ | Основное действие | В бою — основная атака; вне боя — использовать удерживаемый инструмент/предмет, если действие разрешено |
| Q | Защита / подготовка | Поднять щит/оружие в защитную стойку; отпускание завершает удержание |
| F | Вторичное действие | Контекстная вторичная функция: финт в бою, альтернативное использование предмета вне боя; всегда подписывать в HUD |
| X | Убрать / достать оружие | Переключение состояния оружия, если сервер поддерживает экипировку |
| 1–5 | Быстрые слоты | Выбор инструмента/предмета; сервер подтверждает экипировку и наличие |
| Tab | Инвентарь | Панель вещей; не ставит мир на паузу в сетевой игре |
| C | Осмотр персонажа | Внешность, одежда, экипировка; предпочтительно TPS |
| V | Смена камеры | FPS ↔ TPS |
| Esc | Закрыть верхнюю панель / меню | Сначала закрывает активный UI, затем системное меню |

Это стартовая раскладка, а не обещание всех механик в первом билде. Клавиши без реализованного серверного действия должны быть неактивны и не отправлять фиктивные intents. Все основные действия должны переназначаться позже через Input Actions; не стоит навсегда зашивать раскладку в gameplay-код.

### Почему мышь всегда управляет обзором, а ПКМ — альтернативный режим
Постоянный обзор мышью ощущается естественнее: не нужно удерживать кнопку, чтобы просто посмотреть по сторонам. ПКМ — не «кнопка магии», а универсальная кнопка альтернативного режима экипированного предмета/инструмента. Для немагических персонажей это может быть прицеливание из лука, подготовка заброса удочки, особый хват/режим инструмента; для мага — плетение. Важно: лук обычно сохраняет mouse look во время прицеливания, а плетение может явно захватывать движение мыши и фиксировать камеру. Поэтому камера должна реагировать на отдельное состояние `MouseGestureCapture`, а не на сам факт нажатия ПКМ. Защита остаётся на Q.

## 3. Контекстное взаимодействие — «намерение, а не меню на каждый шаг»

1. Игрок смотрит на объект/персонажа в пределах короткой дистанции.
2. Объект мягко подсвечивается; подсказка показывает **конкретный глагол**: «E — поговорить», «E — открыть дверь», «E — осмотреть», «E — взять».
3. Если доступно несколько действий, короткое E выполняет действие по умолчанию, удержание E открывает radial menu.
4. Радиальное меню не должно требовать пиксельной точности: мышь выбирает сектор, отпускание подтверждает, Esc отменяет.
5. После ввода UI показывает «выполняется…» и ждёт серверного результата. При отказе показывает понятную причину: далеко, нет предмета, занято, нет денег, действие недоступно.
6. Не заставлять игрока кликать по крошечным кнопкам или искать POI в HUD, если объект уже перед ним.

Для NPC:
- E — начать/продолжить разговор.
- Удержание E — дополнительные варианты, когда они действительно доступны: поговорить, попросить, торговать, пригласить.
- Адресная цель должна передаваться как стабильный entity ID. До появления такого контракта клиент честно обозначает текущее общее действие socialize.

Для дверей и станций:
- Подсказка меняется по состоянию: «Открыть», «Закрыть», «Использовать кузницу», «Осмотреть рецепт».
- Станция может переводить камеру в удобный ракурс, но игрок всегда может отменить это и вернуть обычное управление.

## 4. «Марионетка»: ощущение веса и намерения

Ожидаемое поведение персонажа:
- Нажатие направления запускает плавное ускорение, отпускание — контролируемое торможение, а не мгновенную остановку.
- Смена направления проходит через короткую фазу разворота; персонаж не скользит как по льду.
- Скорость поворота зависит от скорости движения и массы/экипировки, но не должна делать управление вязким.
- Шаг, бег, приседание и остановка имеют разные циклы ног и верхней части тела.
- Верх тела может независимо смотреть/целиться в сторону взгляда в допустимом диапазоне; при превышении угла ноги и корпус довернутся.
- При взаимодействии персонаж сначала доворачивается к объекту и занимает подходящую позицию, если сервер разрешает перемещение к точке.
- Руки не должны «магнититься» к предмету издалека: короткое достижение/анимация начинается только в подходящей дистанции.
- При ударе есть подготовка, активная фаза, восстановление; нельзя отменять любую анимацию мгновенно без цены.
- Урон, выносливость, скорость, столкновения, попадания и результат действия принадлежат серверу. Клиент отображает локальный отклик и сглаживает подтверждённое состояние.

Ориентир — отзывчивость с весом, а не реалистичное запаздывание. Начальная задержка реакции на нажатие должна быть минимальной; инерция проявляется в движении тела после начала действия, а не в задержке принятия ввода.

## 5. Сетевой контракт движения — что нужно согласовать с Claude

Клиенту не следует отправлять «телепортируй меня в координаты». Предпочтителен input-intent контракт:
- нормализованное направление движения относительно согласованной системы координат;
- состояние бега/осторожного шага;
- направление взгляда/ориентация;
- отдельные одноразовые действия: jump, interact, attack, guard и т. п.;
- монотонный sequence number и, если нужно, client tick для упорядочивания и диагностики.

Сервер:
- проверяет допустимые скорости, ускорение, выносливость, коллизии, высоту/поверхность, блокировки и состояние персонажа;
- рассчитывает canonical position/velocity/facing;
- возвращает авторитетное состояние и подтверждение/отказ действия;
- защищается от повторов, устаревших команд и чрезмерной частоты ввода.

Unity:
- собирает клавиатурный ввод и отправляет intents с ограниченной частотой;
- может кратко предсказывать визуальное движение для отзывчивости, но не считает предсказание фактом;
- сверяет prediction с серверной позицией, мягко корректирует небольшую ошибку и делает явную коррекцию при большой;
- интерполирует других игроков и NPC между серверными snapshot;
- не создаёт локальную «истинную» позицию и не определяет попадания/ресурсы.

Частоту ввода, tick rate, prediction/reconciliation и состав snapshot нужно выбрать совместно после изучения серверного цикла. Не закреплять числа до измерений.

## 6. Обратная связь и удобство

- Контекстная подсказка всегда показывает кнопку и действие, а не только название объекта.
- Краткий отклик на ввод: звук/анимация начала, но не ложное подтверждение результата.
- Пока запрос ожидает сервер, повторное нажатие не должно создавать дублирующие покупки/удары/диалоги.
- Для удерживаемых действий есть явное состояние: «защита поднята», «бег», «прицеливание».
- Для важных отказов показывать короткую причину рядом с прицелом, не прятать её в длинный лог.
- UI не должен блокировать движение случайным наведением мыши; курсор освобождается только при открытом меню.
- Настройки чувствительности мыши, инверсия Y, FOV, масштаб подсказок и переназначение клавиш — обязательные настройки перед полноценным тестом.
- Все действия должны иметь клавиатурный эквивалент; radial menu не единственный способ доступа.

## 7. Порядок реализации

1. Сейчас: камера TPS mouse-orbit без удержания кнопок + zoom, FPS always-on mouse-look, ПКМ как контекстный альтернативный режим (пока без фиктивных результатов), центральная точка, E-взаимодействие. Не вводить фиктивное движение до серверного контракта.
2. После согласования movement: WASD, Shift/Ctrl, разворот и сетевое подтверждение позиции; сначала ходьба/бег на пустой тестовой площадке.
3. Затем: контекстное меню E, адресные NPC/двери/станции, корректное pending/failed UI.
4. Затем: предмет в руках и простая бытовая анимация, включая серверно-подтверждённую подачу и употребление пива.
5. После базового movement: боевой input loop (ЛКМ/Q/F/Space) и серверные фазы действий.
6. Позже: переназначение клавиш, профили управления, доступность и тонкая настройка инерции.

**Acceptance criterion управления:** новичок без чтения документа должен понять по экранным подсказкам, как осмотреться, подойти, выбрать объект и взаимодействовать; после освоения игрок может точно управлять направлением взгляда, защитой, движением и действиями без борьбы с камерой и контекстными меню.
