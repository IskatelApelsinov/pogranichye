## 1. Preserve identity when a resident becomes a bandit

PR #618 currently removes the resident entity and spawns a new FoeC. This makes the former resident lose its stable entity ID and most of its identity; the journal text is the only trace.

Proposal:
- Keep a stable person identity across the transition. Prefer an explicit shared/person ID (or reuse the resident entity ID if the ECS component model permits safe component replacement).
- Carry name, sex/age/appearance seed, settlement of origin, and a compact history/lineage field into the bandit representation.
- Expose optional additive fields in `place.foes[]`: `person_id`, `display_name`, and optionally `origin_settlement_id`. Keep existing `id/kind/name/x/y/facing/hp/max/state/aware` unchanged.
- Do not expose private biography or hidden NPC knowledge to players who have not met the person.
- Add tests: resident→bandit preserves person identity; save/load and reconnect preserve it; the player cannot be converted; death/removal does not duplicate the person.

If reusing entity IDs is unsafe, keep a separate persistent `person_id` and document the distinction between transient foe entity ID and stable person identity.

## 2. Make cross-settlement foe AOI spatially bounded

PR #617 adds foes from every candidate settlement selected by anchor distance ≤1200m. This is a useful first pass, but unlike neighbors it currently does not perform an exact viewer-to-foe distance cutoff and can include all foes of a candidate settlement. Please:
- Apply a configurable exact world-distance radius to each foe before serialization (same AOI policy/radius as the corresponding neighbor visibility where practical).
- Keep the current settlement's existing behavior compatible.
- Ensure only hot/active settlements contribute simulated foes; do not wake every settlement just because its anchor is nearby.
- Add tests for a foe just inside/outside the AOI radius, two settlements close enough to be candidates but whose foe is too far away, and no duplicate IDs across own/neighbor settlements.
- If the client needs canonical world position for remote foes, consider optional `wpos`; otherwise explicitly document that foe x/y are already projected into the viewer's local frame and how they update as the viewer crosses settlement boundaries.

The current client uses stable foe IDs and settlement-local projected x/y. Any additive fields must preserve v1 compatibility.

## 3. Tavern door metadata and movement

Client parses the additive `building_id/room/interior_id/door` metadata and builds a physical opening for the current starter layout. Please keep these invariants:
- door x/y remains on the actual wall; facing points outward; width is full clear width.
- Server collision and client visual opening use the same side and center.
- The interior is walkable without teleport/scene transition; entity ID, inventory, purse, task, WPOS and AOI remain unchanged.
- Add a generated-layout test for all four possible door sides, not only the starter south-facing door.
- Consider exposing door metadata on every tavern generated by all layout plans and guarantee one stable tavern ID per settlement.

## 4. Performance and scale

Please avoid raising the per-frame neighbor cap as a substitute for AOI. For the 10k+ world target:
- Keep candidate settlement selection cheap, then exact spatial filtering.
- Prefer a spatial index/grid or chunk buckets for hot entities if world scans become material.
- Add benchmarks for AOI at representative world sizes (1k/10k/100k resident+foe entities), with deterministic ordering and stable IDs.
- Separate simulation activation from visibility: a settlement being in the viewer's AOI should not automatically cause full NPC/foe simulation there.
