# Производительность симуляции — консультация Grok

Дата: 2026-11-14  
Статус: ориентир, не план срочных PR  
Принцип канона: **живой мир → геймплей → оптимизация**. Сейчас P0 демо важнее микрооптимизаций. Этот документ — карта того, что уже сделано и куда идти, когда масштаб реально упрётся.

## 1. Что уже есть (не изобретать заново)

### 1.1 Heat / A-Life LoD (`sim/heat.go`)

Три уровня поселения:

| Level | Имя | Поведение |
|------:|-----|----------|
| 2 | hot | игрок здесь: полная сцена, тела, движение в реальном времени |
| 1 | warm | тот же край: нужды крупным шагом (раз в 2 ч) |
| 0 | cold | далеко: нужды раз в 4 ч, **тел в сцене нет** |

- `lodStep` разносит холодных по `id`, чтобы не тикали все разом.
- При cold→hot: `materializeResidents` — позиции из цели/занятия, не «все от колодца».
- При hot→cold: `archiveResidents` — снять ScenePos/nav, врагов сцены.
- `HeatTracker` кэширует топологию: пока игроки в тех же settlement, полный пересчёт heat не гоняется на каждом fastStep (10 Hz).

Экономика / mind / демография по задумке идут для всех честно; дешевеет то, что можно интегрировать большим шагом и то, чего никто не видит.

### 1.2 Индексы и масштаб

- В СКЕЛЕТЕ: убран квадратичный скан жителей; индекс place→поселение за один проход в день.
- `residentIndex` / pre-grouped slices в heat transitions — не сканировать весь мир на каждую деревню.
- `core`: индекс по видам компонентов; `BenchmarkEachIndexed` на 10k сущностей.
- `sim/scale_test.go`: `BenchmarkTick` на **300 поселений** — эталон масштаба:
  ```
  go test ./sim/ -run x -bench BenchmarkTick -benchmem
  ```
  Исторически в docs: ~7 мс/час мира на ~10k сущностей / ~7k душ (цифры перепроверять на текущем main).

### 1.3 Детерминизм

Оптимизации **не имеют права** ломать:
- порядок обхода сущностей (по возрастанию id);
- именованные потоки `dice`;
- побайтное равенство после snapshot/load.

Любой «parallel for» без стабильной редукции — регрессия канона.

## 2. Где реальные риски (по мере роста)

| Зона | Симптом | Направление |
|------|---------|-------------|
| AOI / neighbors | neighborCap, place-only filter | spatial index по WorldPos, hysteresis, не `cap++` |
| Hot villages | много игроков в одном селе | уже full sim; профиль StepNPCMovement, nav, combat |
| Terrain API | NewTerrain O(settlements) на каждый chunk | кэш Terrain на запрос/кадр (в коде уже предупреждение про WorldPosViewUsing) |
| Heat full scan | много settlement при частой смене игроков | tracker уже есть; дальше — dirty regions |
| Persistence | полный JSON snapshot всего мира | позже: chunked / cold regions on disk (в СКЕЛЕТЕ как следующий шаг) |
| Frontier growth | Max 300 settlements | OK; за Max — политика, не «ускорить тик» |

Сейчас полевой FAIL — **логика seamless/frontier/content**, не «тик 7 мс вместо 1 мс». Ускорение пустого горизонта не лечит.

## 3. Что делать / не делать сейчас

### Делать (когда берётесь за perf)

1. **Измерить baseline на main**  
   `BenchmarkTick` 100 / 300 / 1000 поселений; отдельно hot-only vs cold-heavy. Записать в comms числа + commit SHA.

2. **Профилировать один hot settlement с игроком**  
   `go test -cpuprofile` на сценарии StepNPCMovement + needs + mind час. Не оптимизировать вслепую.

3. **Spatial AOI** (связано с P0 «нет жителей» / cap)  
   Это и correctness, и perf: правильная выборка по близости дешевле «всех в place» + огромный cap.

4. **Кэш Terrain / anchors** на время сборки кадра и terrain HTTP  
   Уже частично осознано в worldpos; довести, если pprof покажет NewTerrain.

5. **Не трогать** порядок систем и смысл cold archive ради скорости.

### Не делать сейчас

- Микрооптимизации ради P0 демо (пустой мир, таверна, лошадь).
- Параллельный тик mind/econ без доказанной необходимости и стабильного порядка.
- Повышение neighborCap как «оптимизация видимости».
- Вынос симуляции в другой язык / ECS-rewrites «для FPS».
- Оптимизация Unity draw calls под видом server perf.

## 4. Связь с P0

| P0 пункт | Perf-аспект |
|----------|-------------|
| 009 OpenFrontier | дешёвый; cold new settlements (Heat 0) — уже в дизайне frontier |
| 010 Terrain content | descriptor должен оставаться **компактным**; не спавнить entity на каждый куст |
| NPC в кадре | spatial AOI > большой cap |
| Таверна/AOI | hot materialize должен класть жителей в readable POI, не «оптимизировать их отсутствие» |

Новые края с `HeatC{Level:0}` — правильный perf-default: мир растёт дёшево, пока туда не пришли.

## 5. Предлагаемые эталонные команды

```bash
cd 1-server
go test ./sim -run x -bench BenchmarkTick -benchmem -count=3
go test ./core -run x -bench BenchmarkEachIndexed -benchmem
# точечный профиль (пример):
go test ./sim -run TestVerticalSlice -cpuprofile=/tmp/cpu.pprof
go tool pprof -top /tmp/cpu.pprof
```

После каждого крупного sim-PR — одна строка в comms: bench ns/op до/после на одинаковом N.

## 6. Вывод консультанта

Симуляция **уже спроектирована под масштаб** (heat LoD, индексы, cold archive, детерминизм).  
Узкое место демо сейчас — **корректность пути игрока и данные для клиента**, не скорость тика.  

Оптимизацию включать в очередь **после** 009/010 и стабильного P0-среза, либо точечно если pprof на hot-селе покажет явный виновник (nav/AOI/Terrain rebuild). Любая perf-работа — маленькие PR + bench numbers + запрет на ломку детерминизма.
