# Аудит task_ai/002 — серверная симуляция, генерация мира и контракты

Дата: 2026-11-16. Исполнитель: Claude. Источники: `AI_WORK_RULES.md`,
`3-dev/docs/СКЕЛЕТ-ЖИВОГО-МИРА.md`, `ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md`, ADR 0003/0004/0006,
код `1-server/` на момент слияния PR #660 (v1.22) + #661.

Формат: по пунктам «Что проверить» из `task_ai/002`. Для каждого — карта кода, что
подтверждено тестами, и разрывы концепция→код→тест→контракт, если найдены.

## 1. Два режима входа (ADR 0006 §2)

**Код:** `server.reserveBody` (`server/server.go:365-401`) — единственный путь, которым
новый пользователь получает тело. Логика: если у аккаунта уже привязано тело (`acc.CharOf`)
и оно есть в мире — берёт его; иначе — **первое свободное взрослое тело, не занятое другой
сессией, перебором `world.Each("ident", ...)` по возрастанию ID, без фильтра по региону,
поселению или «котёл/внешний мир»**.

**Разрыв**: ADR 0006 §2 требует ДВА различимых режима — демо-котёл (появление в одной из
стартовых деревень котла, с распределением новых игроков МЕЖДУ деревнями котла) и
open-world start (появление во внешнем мире, с учётом региона/страны/происхождения,
БЕЗ спавна всех в одной точке). Критерий готовности ADR 0006 §7: «Demo spawn создаёт/
возвращает игрока в одну из деревень котла», «Full-game spawn… во внешнем мире, не в
котле». **Этого выбора в коде нет вообще** — `reserveBody` не знает о существовании котла
как отдельной области и не принимает параметр режима. Какое тело попадётся новому игроку
зависит только от того, какой ID свободен первым — т.е. от порядка генерации мира, а не от
намерения игрока или конфигурации старта.

Отдельно: модель «вселения» (possession) в уже существующее сымулированное NPC-тело —
это осознанное решение раздела 9 СКЕЛЕТА («игрок по токену вселяется в тело»), не ошибка
само по себе. Разрыв именно в отсутствии выбора ОБЛАСТИ появления.

**Не исправлено в этом аудите** — это не точечный баг, а отсутствующая фича с решением
о UX (как выбирается режим: по профилю регистрации? по настройке сервера? случайно между
котлом-деревнями для демо?). Требует согласования с владельцем до реализации (ровно то,
что просит task_ai/002 делать для разрывов такого масштаба — зафиксировать, не чинить
втихую). Предлагаю отдельный task_ai с явным ADR-уточнением механики выбора.

## 2. Переходы фронтира при перемещении

**Код:** `sim.OpenFrontier` (вызывается из `Travel` и из пешего перехода, `sim/expansion.go`),
`sim.StepLands` (бесшовный мир: идущий переходит в земли ближайшего села), `sim.arrive`/
seamless handover (task 009, PR #657). Идемпотентность: `OpenFrontier` проверяется флагом
на регионе (`RegionC`), не повторяет открытие. Персистентность: регион — обычная сущность
с компонентом, попадает в снимок памяти без потерь (раздел 4 СКЕЛЕТА) как любая другая.

**Подтверждено тестами**: `sim.TestStepLandsOpensOuterFrontier`,
`sim.TestSeamlessLandsKeepWorldPosition`, `sim.TestAOINeighborsCrossBorder`,
`sim.TestAOINeighborsIncludesPhysicalMigrantsBeyondAnchorPrefilter`. Физическое открытие
фронтира в любом направлении и непрерывность `WorldPos` через границу регионов —
подтверждено, не только заявлено.

Разрыва с концепцией не найдено на уровне сервера. ADR 0003's запрет на выдачу всего мира
в кадре соблюдён — геометрия отдаётся отдельными ресурсами (`/api/terrain`, `/api/world`),
не инлайнится в `me`.

## 3. Генерация глобального мира

**Код:** `sim.Generate`/`GenerateStarter`/`generateOuterWorld` (`sim/worldgen.go`) — seed→
детерминированные регионы/реалмы/поселения (`dice` потоки по имени, раздел 5 СКЕЛЕТА).
Биомы и рельеф: `Terrain.Biome`/`Terrain.Height` (`sim/worldpos.go`) — ближайший якорь;
покров/ресурсы/дороги/дикие места — `sim/terrain_content.go` (task 010, PR #659),
`sim/wildlands.go` (v1.22, PR #660, урочища из семени с конечным восполняемым запасом).

**Подтверждённый детерминизм**: `sim.TestTerrainContentDeterministicAndOrderIndependent`.

**Разрыв, уже зафиксированный честно в протоколе (не новый)**: вода НЕ моделируется вообще
— в `Terrain` нет понятия уровня воды/рек/озёр как геометрии, только `cover.wet`
(декоративная плотность). Дороги/тропы/мосты/перевалы не различаются по типу — всё
«road». Это явно отмечено как отложенное в `ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md` (аддитивный блок
`/api/terrain`) и в comms 0254/0259 — не скрытый разрыв, но стоит повторить здесь, так как
п.3 явно спрашивает «не заканчивается ли мир пустой плоскостью» у воды: технически да,
воды как содержательной геометрии нет, только декоративная плотность.

`generateOuterWorld`/`GenerateStarter` сами явно помечены ADR 0006 §4 как «прототипная
затравка… не финальная генерация планеты» — это ОЖИДАЕМОЕ, документированное ограничение
(Fable отвечает за финальную географию), не баг этого аудита.

## 4-5. Контракты render/manifest/карта знаний игрока

**Рендер-геометрия** (без привязки к знаниям персонажа, нужна клиенту для отображения
местности независимо от того, что «знает» душа): `/api/terrain` (`TerrainChunkUsing`),
`/api/world` (`WorldManifestUsing` — схема координат, якоря сёл, тракты), `/api/planet`.
Все три — публичные HTTP-эндпоинты БЕЗ привязки к токену/сессии игрока.

**Карта знаний персонажа**: `sim/knowledge.go` (`VisitedKnown{Visited,Known bool}`),
собирается в поле кадра `known_places` (протокол §v1.5, `server.go:1235`) — ТОЛЬКО для
поселений, которые персонаж посетил/о которых знает (`sim/roads.go` — "here"/"visited"/
"known" статусы по графу дорог от текущего положения), не полный список сущностей мира.

**Разрыв — мельче, чем выглядело при первом чтении**: протокол УЖЕ называет `/api/world`/
`/api/planet` «знанием клиента-стримера и разработчика, не игрока», а `known_places` уже
документирован как separate player-facing поле с `visited`/`known`. Оба факта были
зафиксированы, но раздельно, без явной перекрёстной ссылки друг на друга — то есть
правило «не показывать игроку сведения персонажа из /api/world» выводилось читателем
сам, а не было прописано прямо. **Исправление**: добавил в протокол явную перекрёстную
ссылку у `/api/world` на `known_places` и прямую формулировку запрета (см. ниже) — чтобы
это не нужно было выводить.

## 6. NPC/экономика/ресурсы/лошади/рынок

Авторитетность, конечные запасы, reqid/idempotency — покрыты существующими тестами
(`sim/scale_test.go`, `sim/study_test.go`, `sim/room_ops_test.go`, рыночные/конюшенные
тесты, `econ/` пакет целиком зелёный). Разрывов не найдено сверх уже известных и
зафиксированных задач (011 — блокирован на полевой тест, не код).

## 7. Время/offline/persistence/RNG/масштаб

Персистентность и детерминизм RNG через снимок — подтверждены (раздел 4 СКЕЛЕТА,
`server.TestOchkoPersistsAcrossWorldSaveLoad` как пример компонента, переживающего
save/load). Масштаб — `sim/scale_test.go`, бенчмарк 300 деревень из СКЕЛЕТА §10.

**Разрыв**: нет offline/catch-up симуляции — если сервер не работал N часов реального
времени, при перезапуске мир просто продолжает тикать с сохранённых часов, не «доигрывая»
пропущенное время отдельным быстрым прогоном. Это может быть осознанным упрощением
(мировое время = время работы сервера, а не реальное время), но оно НЕ зафиксировано ни в
одном ADR как решение — только отсутствие кода. Не исправляю (архитектурное решение не
мой уровень полномочий без владельца), фиксирую как открытый вопрос.

## Итоговый список разрывов (приоритет по значимости)

1. **Нет выбора режима появления (демо-котёл / открытый мир)** — ADR 0006 §2/§7 не
   реализован в `reserveBody`. Требует решения владельца о механике выбора, затем отдельный
   task_ai. Самый значимый разрыв концепция→код из всех найденных.
2. Вода не моделируется как геометрия (уже известно, не скрыто).
3. Явного документированного разделения «рендер-геометрия vs карта знаний персонажа» не
   было — добавлено этим PR в протокол.
4. Нет offline catch-up симуляции — открытый вопрос, не решение.
5. Нет портала котёл↔внешний мир (ADR 0006 §3) — ожидаемо: ADR сам называет это будущим
   этапом («Текущий физический перевал v1.15 — рабочий прототип»), не регрессия.
