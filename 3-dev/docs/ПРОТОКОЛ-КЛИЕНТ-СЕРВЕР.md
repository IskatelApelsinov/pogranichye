## 0. Принципы границы

- Сервер — авторитетный владелец мира. Клиент рисует представление и шлёт НАМЕРЕНИЯ, не результат.
- Протокол engine-agnostic: обычный HTTP + WebSocket, тело — JSON (UTF-8). Никаких бинарных/
  движковых форматов в v0.
- Регистрация/вход отделены от мира (служба `accounts`): один аккаунт — любой клиент.
- Одна учётка привязывается к ОДНОМУ персонажу мира («вселение»). Клиент не создаёт сущности —
  сервер выдаёт тело.

## 1. Транспорт и эндпойнты

Базовый адрес по умолчанию: `http://<host>:8090`.

| Метод | Путь | Назначение |
|------|------|-----------|
| POST | `/api/register` | создать учётку |
| POST | `/api/login` | войти, получить токен |
| GET  | `/ws?token=<TOKEN>` | WebSocket: вселение + поток состояния + намерения |
| GET  | `/` | тонкий web-клиент (статика) |

### 1.1 POST /api/register
Тело: `{"login": "<строка>", "pass": "<строка>"}`
Ответ: `{"ok": true}` или `{"ok": false, "msg": "<причина>"}`.

### 1.2 POST /api/login
Тело: `{"login": "<строка>", "pass": "<строка>"}`
Ответ: `{"ok": true, "token": "<TOKEN>"}` или `{"ok": false, "msg": "<причина>"}`.

Замечания:
- Имена полей сервер читает без учёта регистра (`login`==`Login`). Канон — строчные: `login`, `pass`.
- `TOKEN` — непрозрачная строка (сейчас HMAC-подпись). Клиент его не разбирает, а передаёт как есть.
- Пароль не короче 4 символов (проверяют и клиент, и сервер).

### 1.3 GET /ws?token=…
WebSocket (RFC 6455, текстовые кадры). Токен — query-параметр. При коннекте сервер:
1. валидирует токен (иначе HTTP 401),
2. ВСЕЛЯЕТ учётку в персонажа: привязанного ранее, если он жив, иначе свободного взрослого НПС
   (возраст ≥16). Нет свободного тела → HTTP 503.
3. сразу шлёт первый кадр состояния, далее — кадр ~раз в секунду, и читает намерения игрока.
При разрыве тело отпускается: им снова правит ИИ (лестница присутствия).

Коды отказа: `401` — нет/плох токен; `503` — нет свободного тела.

## 2. Сервер → клиент: кадр состояния (JSON, текстовый WS-кадр)

Один кадр = полное состояние видимой игроку части мира (в v0 — снимок, не дельты).

### Живой персонаж
```json
{
  "v": 1,
  "alive": true,
  "day": 128,
  "year": 2,
  "season": "осень",
  "me": {
    "id": "42",
    "name": "Добронега",
    "surname": "Кривонос",
    "role": "farmer",
    "sex": "ж",
    "age": 42.4,
    "health": 100,
    "hunger": 64,
    "energy": 86,
    "morale": 73,
    "goal": "rest",
    "last": "отдыхает",
    "home": "none",
    "coins": 23.4,
    "debt": 0,
    "wounds": { "leg": 3.0 },
    "bleeding": 0,
    "stash": { "bread": 4 },
    "pos": { "x": 0.0, "y": 0.0, "facing": 90, "stam": 1.0, "seq": 0 }
  },
  "place": {
    "name": "Белогорье",
    "tier": "city",
    "food": 466,
    "bread": 248,
    "bread_price": 0.4,
    "neighbors": [
      { "id": "43", "name": "Благана", "role": "farmer", "act": "отдыхает",
        "pos": { "x": 5.2, "y": -3.1, "facing": 210 } }
    ]
  }
}
```

### Мёртвый/покинувший мир персонаж
```json
{ "v": 1, "alive": false, "msg": "твоё тело покинуло мир" }
```

Поля:
- **[v1]** `v` — версия протокола (целое, сейчас `1`). Присутствует и в живом, и в мёртвом кадре.
- **[v1]** `me.id` и `neighbors[].id` — идентификатор сущности: серверный uint64, переданный
  **строкой** (чтобы JS не терял точность за 2^53). Unity парсит в `ulong` и держит как стабильный
  ключ Entity View. Стабилен в пределах жизни мира; тело мертво — id больше не появляется.
- `day`/`year` — целые с 1; `season` — строка из {весна, лето, осень, зима}.
- `me.role` — ремесло (farmer, fisher, cook, smith, herbalist, hunter, woodcutter, weaver, miner, herder, mage, tavernkeeper, idler).
- `me.sex` — "м" | "ж".
- `age` в годах мира (дробное); `health/hunger/energy/morale` — 0..100; `hunger` 0 = сыт.
- `goal` — текущая цель (см. §3); `last` — человекочитаемое последнее действие; `home` — none|rented|owned.
- **[v1.2]** `act_code` — СТАБИЛЬНЫЙ машинный код подтверждённого занятия (для анимаций клиента): им управляй визуалом, не `goal` (цель — лишь намерение) и не `last` (это человекочитаемый исход). Разделение: `goal` = намерение, `act_code` = подтверждённое занятие, `last` = исход/подпись. Коды стабильны; клиент мапит неизвестный код в дефолт. Текущий набор (может пополняться аддитивно): `meal, sleep, rest_idle, drink_tavern, visit_neighbors, seek_home, travel, wander, farm_sow, farm_nosow, farm_reap, farm_noreap, farm_mend, farm_tend, fish_river, fisher_mend, hunt_wild, hunter_empty, cook_hearth, brew_remedy, forage_herbs, smith_forge, smith_cold, weave, weaver_wait, mine_ore, mine_spent, chop_wood, herd_barn, herd_graze, keep_tavern, study_mana, work`.
- **[v1.2]** `mug` — держит ли персонаж кружку (bool). Клиент рисует кружку/руку ТОЛЬКО по этому подтверждённому состоянию, не по факту отправки `buy` (см. §3.2).
- **[v1.3]** `mana` — мана игрока для магического разряда (0..100, восстанавливается в реальном времени). Разряд доступен при `mana ≥ 25` (см. §3.3).
- **[v1.4]** `talk` — текущий разговор (или `null`): `{with, who, known, line, options:[{id,text}]}`. `who` — имя (если знаком) или обезличенное описание; `line` — последняя реплика собеседника; `options` — доступные ответы игрока (их `id` шлётся в `op:"say"`). См. §3.5.
- **[v1.4]** `invite_from` — кто из игроков зовёт выпить вместе (или `null`): `{from, who}`. См. §3.5.
- **[v1.6]** Характеристики: `me.trait` (черта характера), `me.origin` (происхождение), `me.nick` (прозвище), `me.skills` — карта «умение → уровень» (прокачка: труд и действия растят умения с замедлением). `neighbors[].trait` — черта соседа. Это уже симулируется сервером (навыки тренируются трудом/действиями), теперь отдаётся в кадр.
- **[v1.9]** `journal` — личная летопись игрока (#54): массив `{seq, day, kind, text}`, отсортирован по возрастанию `seq`. Записи СЕРВЕР-АВТОРИТЕТНЫ: появляются ТОЛЬКО по факту изменения реального состояния, не по клику. Текущие `kind`: `met` (познакомился с жителем), `worked` (впервые поработал), `drank` (выпил кружку в корчме) — набор пополняется аддитивно. Каждый род записывается ровно один раз (идемпотентно). Клиент показывает их во вкладке «Журнал» и дорисовывает новые по росту `seq`. Пустой массив = вех ещё нет.
- **[v1.5]** `social_event` — последнее ПОДТВЕРЖДЁННОЕ сервером соц-событие игрока (или `null`): `{seq, type, with}`, где `type` = `codrink`|`treat`. `seq` монотонно растёт; клиент проигрывает жест (чокнулись/тост) ОДИН раз на новый `seq`, а не по клику Accept или по изменению morale. Видно обоим участникам co-drink. (Закрывает ревью PR #69: успех co-drink теперь наблюдаем в кадре.)
- **[v1.5]** `known_places` — что игрок знает о поселениях (#26): массив `{id, name, visited, known}`. `visited` — физически был; `known` — есть осмысленное местное знание (познакомился с жителем). Строго различимы. Неизвестные поселения в кадр НЕ попадают. Первый шаг; слухи/located и глобальная карта — следующая фаза (нужен overworld-травел).
- **[v1.5]** `neighbors[].player` — это ЖИВОЙ ИГРОК (сессия управляет телом), а не НПС. Клиент рисует игроков отдельным типом/видом и предлагает `op:"invite"` (совместное питьё) ТОЛЬКО для них. Это закрывает presence-запрос из 0027 §A / 0028. Другие игроки появляются как соседи с их серверной позицией; сервер остаётся единственным владельцем позиции.
- **[v1.4]** `neighbors[].known` — знаком ли игрок с этим жителем; `neighbors[].name` непуст ТОЛЬКО при `known==true`, иначе клиент показывает `neighbors[].desc` (обезличенное: «рыбак», «кузнец»). Диегетично: имя узнаётся через знакомство, не выдаётся сразу (#25).
- `coins`/`debt` — личные деньги и суммарный долг.
- `wounds` — карта «часть тела → тяжесть» (head|torso|arm|leg); пусто = цел. `bleeding` — кровопотеря (0 = нет).
- `stash` — личные закрома «товар → сколько»; пусто = ничего.
- **[v1.1]** `me.pos` — КАНОНИЧЕСКОЕ положение тела в локальной сцене поселения (сервер — владелец):
  `x`,`y` — метры от центра площадки, +X восток, +Y север; `facing` — взгляд в градусах [0,360),
  0 = +X; `stam` — запал бега 0..1 (бег тратит, покой восстанавливает); `seq` — номер последнего
  обработанного сервером намерения движения этого тела (для сверки клиентского предсказания, см.
  §3.1). 1 юнит сцены = 1 метр. Это НЕ координаты на карте мира (мир пока «по поселениям») — только
  положение внутри текущей площадки.
- **[v1.1]** `neighbors[].pos` — положение соседа в той же сцене: `x`,`y`,`facing` (без `stam`/`seq` —
  соседей сервер в сцене пока не симулирует поштучно; раскладка устойчива по `id`, каноническое
  движение НПС — следующий шаг). Клиент расставляет их по этим координатам, а не выдумывает сам.
- **[v1.2]** `place.tavern` — есть ли в поселении корчма (bool); `place.beer` — запас пива в корчме (можно ли налить); `place.beer_price` — цена кружки в монетах. Для UI покупки.
- **[v1.2]** `neighbors[].act_code` — стабильный код занятия соседа (как `me.act_code`, для анимаций).
- `place` присутствует, только если персонаж в поселении; `neighbors` — до 8 соседей с их последним действием.

Числа — округлены сервером для показа (здоровье и т.п. целые, деньги/цены — до десятых). Клиент не
должен считать их точными до копейки.

## 3. Клиент → сервер: намерения (текстовый WS-кадр, JSON)

v1 поддерживает одно намерение — выбор цели персонажу. Пока игрок в теле, цель держится (ИИ не
перебивает); отпустил тело — снова решает ИИ.
```json
{ "v": 1, "op": "goal", "goal": "work" }
```
Допустимые `goal`: `work`, `eat`, `rest`, `socialize`, `seek_home`, `leave`, `wander`.
Неизвестный `op`/пустой `goal` сервер молча игнорирует. Поле `v` в намерении желательно (клиент
шлёт `1`); сервер v1 его пока не проверяет, но закладываем на будущее версионирование.

### 3.1 Намерение движения (op:"move") — [v1.1]

Толстый клиент ведёт ходьбу как input-intent: шлёт НАПРАВЛЕНИЕ и флаг бега, а не готовую позицию.
Сервер авторитетно интегрирует и возвращает каноническую `me.pos` в кадре.
```json
{ "v": 1, "op": "move", "mx": 1.0, "my": 0.0, "run": false, "face": 90, "dt": 0.1, "seq": 57 }
```
- `mx`,`my` — вектор желаемого направления в осях сцены (+X восток, +Y север). Сервер НОРМАЛИЗУЕТ
  его: длина игнорируется, разогнаться длинным вектором нельзя. Нулевой вектор = стоять.
- `run` — true: бежать (быстрее, тратит `stam`; без запала сервер откатывает к шагу). Скорости
  канонические на сервере (шаг ≈1.4 м/с, бег ≈3.2 м/с) — клиент их не задаёт.
- `face` — желаемый взгляд в градусах [0,360), 0 = +X. Можно поворачиваться, не двигаясь.
- `dt` — секунды, прошедшие с прошлого намерения этого тела. Сервер КЛАМПИТ `dt` сверху (≤0.25 с)
  как защиту от рывков/читерских больших dt. Клиент шлёт реальный кадровый `dt`.
- `seq` — монотонно растущий номер намерения (клиент ++ на каждом). Сервер применяет только больший
  `seq`, устаревший игнорирует, и возвращает последний применённый в `me.pos.seq` — клиент по нему
  сверяет предсказание и сглаживается к серверной позиции (а не телепортируется).

Модель: клиент предсказывает движение локально для отзывчивости (~100–200 мс), но сервер —
единственный владелец позиции; расхождение гасится по `seq`. **[v1.3]** Сервер держит тело в границах
мира (300×300 м) и НЕ пускает сквозь здания и реку (кроме моста) — движение упирается и скользит вдоль
преград. Геометрия — в `GET /api/layout` (§3.4); клиент делает ту же коллизию локально для предсказания.

### 3.2 Питьё в корчме (op:"buy" / op:"consume") — [v1.2]

Первое прямое действие игрока с миром. Сервер авторитетен; действия АТОМАРНЫ и ИДЕМПОТЕНТНЫ.
```json
{ "v": 1, "op": "buy",     "item": "beer", "reqid": "<uuid клиента>" }
{ "v": 1, "op": "consume", "item": "beer", "reqid": "<uuid клиента>" }
```
- `item` — пока только `"beer"`.
- `reqid` — уникальный id запроса от клиента (например uuid). Сервер запоминает последний
  обработанный `reqid` для каждого действия: ПОВТОР того же `reqid` НЕ применяется второй раз
  (не спишет монеты/пиво дважды при ретрае). Без `reqid` идемпотентности нет — клиент ОБЯЗАН его слать.

`buy` (сервер, под замком, всё или ничего):
1. тело у стойки корчмы (по сцене, ≤2.5 м от POI `tavern`);
2. в поселении есть корчма и пиво (`place.beer` ≥ 1);
3. у игрока нет кружки в руке (`me.mug == false`) и хватает монет (`place.beer_price`);
4. успех: −цена из кошеля, −1 пиво из корчмы, `me.mug=true`. Любой отказ — НИЧЕГО не меняется.

`consume` (сервер, под замком):
1. у игрока есть кружка (`me.mug == true`);
2. успех: `me.mug=false`, эффект на нужды по правилам мира (сейчас +настрой, чуть −голод). НЕ через
   `goal:"eat"`/`"socialize"` — это отдельное действие.

Ответа-сообщения нет: исход виден в следующем кадре (`me.mug`, `me.coins`, `place.beer`). Клиент
рисует кружку/руку/анимацию ТОЛЬКО по подтверждённому `me.mug`, не по факту отправки запроса.
Совместное распитие (invite/accept, session id, близость, отмена на разрыве) — отдельная фаза, не здесь.

### 3.3 Действия в мире (op:"act") — [v1.3]

Прямые действия игрока. Сервер авторитетен; повтор того же `reqid` идемпотентен.
```json
{ "v": 1, "op": "act", "action": "chop", "reqid": "<uuid>" }   // срубить дерево у леса → +бревно
{ "v": 1, "op": "act", "action": "fish", "reqid": "<uuid>" }   // рыбалка у реки → +рыба
{ "v": 1, "op": "act", "action": "cast", "reqid": "<uuid>" }   // магический разряд (демо-оружие)
```
- `chop` — рядом с лесом (запад, `x ≤ -70`, или ≤6 м от POI `woods`) и есть силы: −силы, +бревно в `me.stash`.
- `fish` — у реки (у северного берега) и есть силы: −силы, +рыба в `me.stash`.
- `cast` — тратит `25` маны; если в угодьях есть опасный зверь (волк/медведь/кабан) — прореживает его.
  Нет маны — отказ; нет зверя — просто искра (успех без эффекта). `me.mana` восстанавливается со временем.
Исход — в следующем кадре (`me.stash`, `me.energy`, `me.mana`). Клиент анимирует действие по
подтверждённому изменению состояния.

**[v1.5] Идемпотентность (касается `buy`/`consume`/`act`):** `reqid` ОБЯЗАТЕЛЕН и непуст — пустой
отвергается. Сервер хранит ограниченную историю (кольцо ≤64) успешно обработанных `reqid` на игрока;
повтор уже применённого `reqid` возвращает успех без повторного эффекта, в т.ч. повтор СТАРОГО id после
более новых запросов (не «только последний»). `reqid` записывается только при УСПЕХЕ, поэтому ретрай
того же id после неудачи (отошёл/нет сил) корректно сработает, когда условия выполнятся.
**[v1.5]** `cast` дополнительно требует быть в угодьях поселения на проходимом месте (не в стене).
**Ограничение:** близость к корчме/лесу/реке считается по координатам ОДНОЙ активной сцены (стартовой
деревни). Мир с несколькими поселениями, у каждого со своей корчмой, потребует сцены на поселение —
отдельная веха. Отдельного ack на действие пока нет: исход виден по следующему кадру (отказ и ожидание
клиент пока не различает) — backward-compatible ack с `reqid` можно добавить следующим шагом.

### 3.4 Геометрия мира — GET /api/layout — [v1.3]

Статическая версионированная геометрия (не в кадре — тянется один раз). Сервер владеет коллизиями по
ней, клиент по ней же рисует и предсказывает. Любая правка координат — подъём `version`.
```json
{
  "version": 2,
  "world_half": 150,          // мир [-150,150]^2 м (300×300)
  "village_half": 50,         // ядро деревни 100×100
  "buildings": [ {"name":"Корчма","kind":"tavern","x0":-40,"y0":14,"x1":-26,"y1":26}, … ],
  "river": {"y0":-90,"y1":-78,"bridge_x0":-6,"bridge_x1":6},
  "pois": { "tavern":{"x":-33,"y":12}, "smithy":{"x":29,"y":14}, … }
}
```
Сервер не пускает тела в `buildings` и в полосу `river` (кроме проёма моста) и за край мира: движение
упирается/скользит вдоль преград (и у игрока, и у НПС). Клиент должен делать ту же коллизию локально,
чтобы предсказание сходилось. Внутри препятствий тел не бывает.

### 3.6 Дискретная навигация менеджмент-клиента (op:"goto") — [v1.6]

Для тонкого web/mobile клиента (кликер-ферма, БЕЗ ходьбы — решение владельца, 0040/ADR 0002).
```json
{ "v":1, "op":"goto", "location":"<ключ POI>" }   // river|woods|tavern|smithy|garden|granary|well|mine|hearth
```
Сервер ставит тело игрока в точку выбранной локации (серверно-авторитетно — это не фальшивое
перемещение, а дискретная навигация; владелец позиции остаётся сервер). После `goto` действия,
завязанные на близость (`buy`/`fish`/`chop`/`talk`), работают, т.к. тело уже на месте. Толстый клиент
(Unity) навигацию делает непрерывной ходьбой (`op:"move"`); оба двигают ОДНО тело, выбор способа — за
клиентом. Локации = ключи `pois` из `/api/layout`.

### 3.5 Разговор, знакомство и совместное питьё — [v1.4]

Социальные намерения. Сервер авторитетен.
```json
{ "v":1, "op":"talk",    "target":"<id>" }          // заговорить с жителем рядом (≤5 м, у корчмы ≤8 м)
{ "v":1, "op":"say",     "line":"<option id>" }      // выбрать реплику из me.talk.options
{ "v":1, "op":"endtalk" }                            // отойти
{ "v":1, "op":"invite",  "target":"<id игрока>" }    // позвать ДРУГОГО игрока выпить (оба у стойки)
{ "v":1, "op":"accept" }                             // принять приглашение (me.invite_from)
{ "v":1, "op":"declinedrink" }                       // отклонить/отменить
```
- **Знакомство:** реплика `greet` в разговоре знакомит — после неё имя жителя появляется в `me.talk.who`
  и в `neighbors[].name` (а `known` становится `true`). У корчмы знакомиться проще (шире круг общения).
- **Угостить НПС:** у знакомого жителя в корчме доступна реплика `drink` — игрок платит за две кружки,
  у НПС растёт настрой (совместный тост). Не через `goal`.
- **Co-drink игроков:** `invite` зовёт другого игрока (сервер проверяет, что цель — игрок, оба у стойки,
  рядом). Приглашённый видит `me.invite_from` и отвечает `accept` (оба платят по кружке, оба веселеют,
  знакомятся) или `declinedrink`. Разрыв связи снимает приглашение у обоих.
- Исход — в следующем кадре (`me.talk`, `me.morale`, `me.coins`, `neighbors[].name/known`). Клиент
  рисует диалог и реплики из `me.talk`, не выдумывает варианты сам.

### 3.7 Ядро игры — [v1.10]

Общий принцип: **ввод отделён от разрешения**. Клиент присылает намерение («удар по этой цели, в эту
часть тела, с такой точностью»), сервер авторитетно решает исход. Клиент ничего не предсказывает:
попадание, урон, добыча, прогресс просьбы показываются только из подтверждённого кадра (`me.feed`,
`me.result`, `place.foes`). Все намерения ниже принимают `reqid`; расходные (плетение, выстрел,
ремесло, употребление, выход в путь) требуют его для идемпотентности.

**Быстрые кадры.** `GET /ws?token=…&fast=N` (N = 2..15 Гц) — между полными кадрами (1 Гц) сервер шлёт
лёгкие: `{"v":1,"fast":true,"alive":true,"me":{pos,health,energy,mana,combat,feed,result,wounds},
"place":{"neighbors":[{id,pos}],"foes":[…]}}`. Это НЕ полный снимок: клиент накладывает поля на
последний полный кадр. Без параметра `fast` поток прежний.

**Враги сцены — `place.foes[]`**: `{id,kind,name,x,y,facing,hp,max,state,aware,slow,weak,blind,stun}`.
`kind`: `hare|fox|boar|wolf|bear|bandit`; `state`: `roam|chase|flee|eat|dead` (туша лежит ~25 с).
Звери подняты из РЕАЛЬНОГО поголовья угодий (убил — в угодьях стало меньше) и существуют только там,
где есть игроки. Живут в диких зонах (западный лес, заречье, окрестности рудника); в ядро деревни
(`village_half`) не заходят и туда не преследуют.

**Бой.**
- `{"op":"attack","target":"<foeId>","aim":"head|torso|arm|leg","style":"slash|thrust|heavy|snap|drawn",
  "aimed":true,"acc":0..1,"power":0..1,"reqid":"…"}`.
  `aimed:true` — клиент целился сам (первое лицо): `acc` — качество попадания по его hit-test,
  `power` — натяжение лука; сервер проверяет дальность (ближний ≤ ~2.9 м, лук ≤ ~50 м) и сектор
  взгляда (ближний ±60°, лук ±30°; взгляд берётся из последнего `move.face`) — вне сектора `acc`
  обнуляется. `aimed:false`/нет — сервер сам поворачивает тело к цели и бросает кости от навыка
  (менеджмент-клиент). Без `target` — удар по ближайшему врагу в досягаемости. Оружие — `me.inv.hand`:
  кулаки, `knife`, `axe`, `sword`, `bow` (тратит `arrow`). Часть тела: голова ×1.8 и оглушает, рука
  ослабляет удары врага, нога замедляет. Удар по не заметившему врагу — ×2. У удара есть откат
  (`me.combat.cd`, сек).
- `{"op":"guard","on":true|false}` — блок (работает на удары спереди, тратит запал; `shield` в слоте
  `offhand` усиливает). `{"op":"dodge"}` — окно уворота 0.7 с. `{"op":"stance","stance":
  "aggressive|balanced|defensive"}` — стиль боя.
- `{"op":"trick","trick":"sand|feint|shove|bait|sneak"}` — хитрости: песок в глаза (ослепить),
  финт (следующий удар точнее и сильнее), толчок (отбросить и оглушить), приманка (кусок мяса
  отвлекает зверя), красться (зверь замечает позже; удар исподтишка).
- `me.combat`: `{stance,guard,sneak,feint,cd,shield,light,arrows,weapon,kills{вид:n},ko}`.
- Здоровье ≤ 5 — игрок падает без чувств: сервер переносит тело к очагу, раны остаются, часть монет
  пропадает (событие `ko` в ленте).
- `{"op":"goto","target":"<foeId>","qty":<метры>}` — ДИСКРЕТНЫЙ подход к врагу для тап-клиента
  (ADR 0002). Толстый клиент подходит ногами.

**Плетения.** `{"op":"weave","nodes":["knot","thread","barb","seal"],"target":"<id>","reqid":"…"}`.
Узлы: `knot` узел (сила), `thread` нить (дальность), `loop` петля (удержание), `fork` развилка
(цели/отряд), `barb` шип (урон), `seal` печать (замыкает). Действие ВЫВОДИТСЯ из состава: есть шип —
урон (нить даёт дальность, развилка — вторую цель, петля — жжение); петля+нить — заживление (себя или
`target`-человека); петля — щит (с развилкой — на отряд рядом); нить — толчок с оглушением; только
узел+печать — свет. Узор должен начинаться узлом и кончаться печатью, иначе сложность +3. Сложность =
число узлов + развилки; её сравнивают с ёмкостью ума (`me.weave.capacity`, растёт с навыком `mage`).
Сорванное плетение бьёт по магу (`backfire` в ленте). Знакомая схема (`me.weave.known[]`) держится
увереннее; удержанный незнакомый узор запоминается. Мана: 4×узлов + 4×узлы-knot.
`me.weave`: `{nodes[{id,name,hint}],capacity,max_len,known[{name,nodes[]}]}`.
`neighbors[].casting` — `""`, либо `"плетёт"`, либо имя узора (если наблюдатель — опытный маг).

**Лента — `me.feed[]`**: `{seq,kind,text,foe?,part?,dmg?}`, `seq` монотонный, клиент проигрывает
каждое событие один раз. `kind`: `hit|miss|kill|hurt|block|dodge|ko|weave|backfire|learn|loot|road|
quest|craft|party`.

**Просьбы — `me.quests`**: `{offers[],active[],done,rep}`. Предложение: `{id,kind,via,giver,
giver_name,good?,species?,qty,text,coins}`; `kind`: `deliver|cull|feed|heal|cheer`; `via`:
`board|keeper|npc` (как подать в мире: доска у колодца, слово корчмаря, просьба жителя). Предложения
вычисляются из РЕАЛЬНОГО состояния (мало еды/дров/руды, расплодился зверь, житель голоден/ранен/
тоскует) и исчезают вместе с нуждой. Плата — из настоящего кошеля просящего. Взятая:
те же поля + `have`, `ready`. Намерение: `{"op":"quest","action":"accept|turnin|drop","quest":"<id>"}`.

**Ремесло — `me.recipes[]`**: `{id,name,at,needs{товар:n},gives,qty,can,here}`; `at` — POI
(`smithy|hearth|granary`). `{"op":"craft","item":"<id>","reqid":"…"}`. Цепочки: руда→железо→меч,
шкура→кожа→куртка. Сырьё: `{"op":"act","action":"mine"}` у рудника, `"gather"` у огородов.
`{"op":"use","item":"stew|roast|potion|bandage|bread|fish|meat|…","reqid":"…"}` — съесть/приложить.
Новые вещи: `knife` (в руку), `jerkin` (слот `armor`), `shield` (слот `offhand`), `arrow`.

**Прилавок — `place.market[]`**: `{good,stock,price,sell}`; торговля прежним `op:"trade"`.

**Дорога — `me.journey`** (`null`, если не в пути): `{to,to_name,progress,eta,scene,note,follow,
event}`; `event`: `{kind,foe?,text,options[]}`, `kind`: `ambush|beast|traveller|camp|find`, варианты —
`fight|pay|flee|scare|talk|trade|pass|rest|gather`. `{"op":"journey","target":"<settlementId>",
"reqid":"…"}` — выйти в путь (только между поселениями по одну сторону гор; через горы — прежний
`op:"travel"` как врата, ADR 0003). Путь идёт в реальном времени и ЖДЁТ решения на встрече:
`{"op":"journey","action":"choose","choice":"<вариант>"}`. В пути `place` в кадре отсутствует,
`move/goto/attack/weave` не принимаются.

**Отряд — `me.party`**: `{leader,members[{id,name,leader,health,road,x?,y?}],invite_from}`.
`{"op":"party","action":"invite","target":"<playerId>"}`, `"accept"`, `"leave"`. Отряд выходит в путь
вместе с вожаком (решения на встречах принимает вожак), щит-плетение с развилкой накрывает своих.

**Прочее.** `hour` (0..23) на верхнем уровне кадра; `place.id`; соседей в кадре теперь до 24
БЛИЖАЙШИХ (раньше 8 первых по обходу); `GET /api/stats` — `{entities,players,foes,hot,warm,cold,
hour_ms,day,hour}` (нагрузка и «температура» областей: горячо там, где игроки).

## 4. Идентификаторы, версии, ресинхрон

- **Идентификатор сущности. [v1, в коде]** `me.id` и `neighbors[].id` отдаются — серверный uint64
  строкой (см. §2). Стабильный ключ Entity View / Prefab Registry на стороне Unity.
- **Версия протокола. [v1, в коде]** Кадр и намерение несут `"v": 1`. Дальше ломающие изменения
  поднимают число и версию этого документа.
- **Начальная синхронизация.** Первый WS-кадр приходит сразу после коннекта — это и есть полный
  снимок. Отдельного «snapshot/handshake»-сообщения нет.
- **Ресинхрон после переподключения.** Специальной докачки нет: клиент заново открывает `/ws` с тем
  же токеном, сервер вселяет в того же персонажа (если жив) и шлёт свежий полный кадр. Клиент должен
  быть готов, что тело могло умереть (`alive:false`) или измениться.
- **Частота.** Поток состояния — ~1 кадр/с (медленный мир). Боевой/активный темп (клиентское
  предсказание, ~100–200 мс) в протокол НЕ входит — это отдельный контракт (см. §6.5).

## 5. Чего в протоколе НЕТ (явно, чтобы не выдумывать параллельно)

- Нет дельта-обновлений (только полные кадры). Нет сжатия. Unity сравнивает соседние кадры по `id`
  и обновляет визуальные сущности (согласовано с ChatGPT).
- **[v1.1]** Есть локальные координаты сцены (`me.pos`/`neighbors[].pos`, метры от центра площадки)
  и ходьба (§3.1). Но это ВНУТРИ одного поселения — глобальных координат на карте мира (между
  поселениями/регионами) по-прежнему нет; мир крупно «по поселениям». Переход между площадками и
  карта мира — предмет §6.2.
- Нет боевых событий реального времени, строительства, чата. Всё это — будущие намерения/события,
  добавляются согласованно.
- **[v1.2]** Первое прямое действие с предметом уже есть — питьё в корчме (§3.2). Полноценные
  инвентарные операции (передача/крафт в руках игрока) пока нет — добавляются согласованно.

## 6. Решено для v1 и что ещё согласовать

Решения по v1 (согласованы Claude↔ChatGPT, см. `3-dev/comms/`, фиксируются ADR):

1. **id сущностей в кадре — ПРИНЯТО, в коде.** `me.id`/`neighbors[].id`, uint64 строкой. Unity →
   `ulong`, ключ Entity View.
2. **Координаты сцены — ПРИНЯТО в v1.1, в коде.** Локальная площадка поселения: метры от центра,
   `me.pos`/`neighbors[].pos` + намерение `move` (§3.1), сервер авторитетен. Глобальная карта мира
   (`region_id`/`place_id`, координаты МЕЖДУ поселениями, переход между площадками) — ещё ОТЛОЖЕНО,
   согласуем отдельно.
3. **Событийный канал — ОТЛОЖЕНО.** Пока полные снимки раз в секунду; отдельный канал событий
   (родился/умер/ранен/хворь) проектируем, когда появятся боевые и кратковременные события.
4. **Версионирование — ПРИНЯТО, в коде.** `"v": 1` в кадрах и намерениях.
5. **Быстрый боевой цикл — ПРИНЯТО в v1.10 (первая версия), в коде.** Ввод отделён от разрешения:
   клиент целится и шлёт `attack` с целью/частью тела/точностью, сервер проверяет дальность и сектор
   и решает исход; шаг реального времени на сервере 100 мс, быстрые кадры `?fast=N` (§3.7). Попадания
   клиент не предсказывает. Событийный канал (п.3) частично закрыт лентой `me.feed`.

Каждое новое решение по этим пунктам — ADR в `3-dev/docs/adr/` + правка этого документа + подъём
версии протокола.
