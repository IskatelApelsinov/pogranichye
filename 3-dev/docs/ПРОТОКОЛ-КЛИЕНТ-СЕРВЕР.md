# Протокол клиент↔сервер «Приграничье» (контракт)

Версия протокола: **v1** (технически согласована помощниками Claude↔ChatGPT 2026-11-02, ожидает
утверждения владельца проекта; см. `3-dev/docs/adr/0001-protocol-v1.md`
и `3-dev/comms/`). v1 = v0 + идентификаторы сущностей в кадре + поле версии `v`. Остальное из v0 без
изменений. Это НЕСУЩИЙ контракт между сервером (Go, зона Claude) и клиентами (тонкий web + толстый
Unity, зона ChatGPT). Любое изменение формата сообщений, модели сущности или семантики команды —
межсистемное: сперва правка этого документа и согласование, затем согласованно сервер и клиент.

Пометки происхождения полей: **[v0]** — было с первого контракта; **[v1]** — добавлено в v1 (уже в
коде сервера). Общий пример кадра — в `3-dev/contract/fixtures/state_v1.example.json` (его же берут
Go-тест `server/contract_test.go` и будущий Unity-тест совместимости).

Назначение: Unity-клиент (ChatGPT) строится ОТ этого документа, не читая серверный код построчно.
Если документ и код разошлись — это баг, сообщить, а не молча выбирать версию.

---

## 0. Принципы границы

- Сервер — авторитетный владелец мира. Клиент рисует представление и шлёт НАМЕРЕНИЯ, не результат.
- Протокол engine-agnostic: обычный HTTP + WebSocket, тело — JSON (UTF-8). Никаких бинарных/
  движковых форматов в v0.
- Регистрация/вход отделены от мира (служба `accounts`): один аккаунт — любой клиент.
- Одна учётка привязывается к ОДНОМУ персонажу мира («вселение»). Клиент не создаёт сущности —
  сервер выдаёт тело.

## 1. Транспорт и эндпойнты

Базовый адрес по умолчанию: `http://<host>:8090`.

| Метод | Путь | Назначение |
|------|------|-----------|
| POST | `/api/register` | создать учётку |
| POST | `/api/login` | войти, получить токен |
| GET  | `/ws?token=<TOKEN>` | WebSocket: вселение + поток состояния + намерения |
| GET  | `/` | тонкий web-клиент (статика) |

### 1.1 POST /api/register
Тело: `{"login": "<строка>", "pass": "<строка>"}`
Ответ: `{"ok": true}` или `{"ok": false, "msg": "<причина>"}`.

### 1.2 POST /api/login
Тело: `{"login": "<строка>", "pass": "<строка>"}`
Ответ: `{"ok": true, "token": "<TOKEN>"}` или `{"ok": false, "msg": "<причина>"}`.

Замечания:
- Имена полей сервер читает без учёта регистра (`login`==`Login`). Канон — строчные: `login`, `pass`.
- `TOKEN` — непрозрачная строка (сейчас HMAC-подпись). Клиент его не разбирает, а передаёт как есть.
- Пароль не короче 4 символов (проверяют и клиент, и сервер).

### 1.3 GET /ws?token=…
WebSocket (RFC 6455, текстовые кадры). Токен — query-параметр. При коннекте сервер:
1. валидирует токен (иначе HTTP 401),
2. ВСЕЛЯЕТ учётку в персонажа: привязанного ранее, если он жив, иначе свободного взрослого НПС
   (возраст ≥16). Нет свободного тела → HTTP 503.
3. сразу шлёт первый кадр состояния, далее — кадр ~раз в секунду, и читает намерения игрока.
При разрыве тело отпускается: им снова правит ИИ (лестница присутствия).

Коды отказа: `401` — нет/плох токен; `503` — нет свободного тела.

## 2. Сервер → клиент: кадр состояния (JSON, текстовый WS-кадр)

Один кадр = полное состояние видимой игроку части мира (в v0 — снимок, не дельты).

### Живой персонаж
```json
{
  "v": 1,
  "alive": true,
  "day": 128,
  "year": 2,
  "season": "осень",
  "me": {
    "id": "42",
    "name": "Добронега",
    "surname": "Кривонос",
    "role": "farmer",
    "sex": "ж",
    "age": 42.4,
    "health": 100,
    "hunger": 64,
    "energy": 86,
    "morale": 73,
    "goal": "rest",
    "last": "отдыхает",
    "home": "none",
    "coins": 23.4,
    "debt": 0,
    "wounds": { "leg": 3.0 },
    "bleeding": 0,
    "stash": { "bread": 4 }
  },
  "place": {
    "name": "Белогорье",
    "tier": "city",
    "food": 466,
    "bread": 248,
    "bread_price": 0.4,
    "neighbors": [
      { "id": "43", "name": "Благана", "role": "farmer", "act": "отдыхает" }
    ]
  }
}
```

### Мёртвый/покинувший мир персонаж
```json
{ "v": 1, "alive": false, "msg": "твоё тело покинуло мир" }
```

Поля:
- **[v1]** `v` — версия протокола (целое, сейчас `1`). Присутствует и в живом, и в мёртвом кадре.
- **[v1]** `me.id` и `neighbors[].id` — идентификатор сущности: серверный uint64, переданный
  **строкой** (чтобы JS не терял точность за 2^53). Unity парсит в `ulong` и держит как стабильный
  ключ Entity View. Стабилен в пределах жизни мира; тело мертво — id больше не появляется.
- `day`/`year` — целые с 1; `season` — строка из {весна, лето, осень, зима}.
- `me.role` — ремесло (farmer, fisher, cook, smith, herbalist, hunter, woodcutter, weaver, miner, herder, mage, tavernkeeper, idler).
- `me.sex` — "м" | "ж".
- `age` в годах мира (дробное); `health/hunger/energy/morale` — 0..100; `hunger` 0 = сыт.
- `goal` — текущая цель (см. §3); `last` — человекочитаемое последнее действие; `home` — none|rented|owned.
- `coins`/`debt` — личные деньги и суммарный долг.
- `wounds` — карта «часть тела → тяжесть» (head|torso|arm|leg); пусто = цел. `bleeding` — кровопотеря (0 = нет).
- `stash` — личные закрома «товар → сколько»; пусто = ничего.
- `place` присутствует, только если персонаж в поселении; `neighbors` — до 8 соседей с их последним действием.

Числа — округлены сервером для показа (здоровье и т.п. целые, деньги/цены — до десятых). Клиент не
должен считать их точными до копейки.

## 3. Клиент → сервер: намерения (текстовый WS-кадр, JSON)

v1 поддерживает одно намерение — выбор цели персонажу. Пока игрок в теле, цель держится (ИИ не
перебивает); отпустил тело — снова решает ИИ.
```json
{ "v": 1, "op": "goal", "goal": "work" }
```
Допустимые `goal`: `work`, `eat`, `rest`, `socialize`, `seek_home`, `leave`, `wander`.
Неизвестный `op`/пустой `goal` сервер молча игнорирует. Поле `v` в намерении желательно (клиент
шлёт `1`); сервер v1 его пока не проверяет, но закладываем на будущее версионирование.

## 4. Идентификаторы, версии, ресинхрон

- **Идентификатор сущности. [v1, в коде]** `me.id` и `neighbors[].id` отдаются — серверный uint64
  строкой (см. §2). Стабильный ключ Entity View / Prefab Registry на стороне Unity.
- **Версия протокола. [v1, в коде]** Кадр и намерение несут `"v": 1`. Дальше ломающие изменения
  поднимают число и версию этого документа.
- **Начальная синхронизация.** Первый WS-кадр приходит сразу после коннекта — это и есть полный
  снимок. Отдельного «snapshot/handshake»-сообщения нет.
- **Ресинхрон после переподключения.** Специальной докачки нет: клиент заново открывает `/ws` с тем
  же токеном, сервер вселяет в того же персонажа (если жив) и шлёт свежий полный кадр. Клиент должен
  быть готов, что тело могло умереть (`alive:false`) или измениться.
- **Частота.** Поток состояния — ~1 кадр/с (медленный мир). Боевой/активный темп (клиентское
  предсказание, ~100–200 мс) в протокол НЕ входит — это отдельный контракт (см. §6.5).

## 5. Чего в протоколе НЕТ (явно, чтобы не выдумывать параллельно)

- Нет дельта-обновлений (только полные кадры). Нет сжатия. Unity сравнивает соседние кадры по `id`
  и обновляет визуальные сущности (согласовано с ChatGPT).
- Нет пространственных координат персонажа/соседей в кадре (мир пока «по поселениям», не по карте
  в метрах). Для первого Unity-прототипа допускается ВРЕМЕННАЯ клиентская раскладка соседей вокруг
  игрока, явно НЕ являющаяся координатами мира. Физические координаты — предмет §6.2.
- Нет боевых событий реального времени, инвентарных операций, строительства, чата. Всё это —
  будущие намерения/события, добавляются согласованно.

## 6. Решено для v1 и что ещё согласовать

Решения по v1 (согласованы Claude↔ChatGPT, см. `3-dev/comms/`, фиксируются ADR):

1. **id сущностей в кадре — ПРИНЯТО, в коде.** `me.id`/`neighbors[].id`, uint64 строкой. Unity →
   `ulong`, ключ Entity View.
2. **Координаты — ОТЛОЖЕНО.** Физические координаты не выдумываем до серверной пространственной
   модели. Прототип — временная клиентская раскладка. Позже согласуем `region_id`/`place_id` и метры.
3. **Событийный канал — ОТЛОЖЕНО.** Пока полные снимки раз в секунду; отдельный канал событий
   (родился/умер/ранен/хворь) проектируем, когда появятся боевые и кратковременные события.
4. **Версионирование — ПРИНЯТО, в коде.** `"v": 1` в кадрах и намерениях.
5. **Быстрый боевой цикл — ОТЛОЖЕНО.** Отдельный контракт (клиентское предсказание + подтверждение
   сервером), проектируем совместно перед реализацией.

Каждое новое решение по этим пунктам — ADR в `3-dev/docs/adr/` + правка этого документа + подъём
версии протокола.
