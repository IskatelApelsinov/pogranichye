# ADR 0011 — Мировое состояние лошади и контекстное взаимодействие

Дата: 2026-11-20.
Статус: **ПРЕДЛОЖЕНИЕ (design-only).** Контракт НЕ меняется этим ADR. Реализация начинается только
после согласования с Kate и ChatGPT (см. запрос ChatGPT 0313-chatgpt-to-claude-horse-world-state,
ответ 0317-claude-to-chatgpt-horse-world-state-design).
Связано: comms 0313 (запрос), 0315/0316 (Unity input), PR #774 (Unity presentation/input, draft);
`1-server/sim/horse.go`, `1-server/sim/scene.go`, ADR 0005 (travel/housing), ADR 0007/0008 (координаты).

## 1. Контекст и проблема

ChatGPT (0313) просит серверный дизайн для полноценной механики лошади: видимая свободно стоящая
лошадь, «подошёл — удержал E — сел», «оставил у дерева — вернулся», привязь, стойло. Явно просит
**сначала согласовать дизайн, не менять wire-схему вслепую** и не начинать параллельную реализацию.

### Аудит текущего сервера (main, `1-server/sim/horse.go`)

- `HorseC{Owner, Settlement, Name, Stam, Bag}` — у лошади есть владелец, село «приписки» и седельная
  сумка, но **нет мировой позиции, направления, стабильного состояния размещения и якоря привязи.**
- `RiderC{Horse, Mounted}` — какую свою лошадь всадник ведёт и в седле ли. Лошадей у хозяина до 5
  (`MaxHorses`), ведомая одна.
- `mount` требует лишь: лошадь приписана к текущему селу (`h.Settlement == se.ID`) и `Stam > 5`.
  `dismount` разрешён везде, конюшню не требует (можно оставить как есть).
- `UpdateBurden` восстанавливает `Stam` всех лошадей (+0.4/с) безусловно — модель «лошадь всегда
  отдыхает в стойле», даже когда «оставлена в поле».
- Кадр: `me.horse` (ведомая), `me.horses[]` (все свои), `place.stable` (конюшня села). Запись
  `horseEntry` несёт `settlement_id/name`, `here`, `stam`, `bag`, но **не координаты.**
- Позиция тел в сцене — `ScenePosC{X,Y,Z,Facing,Seq,...}` + глобальная `me.wpos` (`wpos = anchor +
  pos`), та же схема уже у `neighbors[].wpos` и `place.foes[].wpos`. **Это и есть готовый шаблон для
  позиции лошади** — не нужно изобретать вторую систему координат.

**Следствие:** клиент не может честно показать свободную лошадь в сцене, навести на неё E и получить
стабильную позицию. ChatGPT правильно отказался от локального фейкового объекта.

## 2. Решение (предлагаемое, аддитивно к кадру `v:1`)

Сервер остаётся единственным владельцем позиции, владения и состояний лошади. Клиент только
запрашивает намерение и визуализирует подтверждённое сервером состояние. Ничего из этого не ломает
старые кадры: все поля новые и опциональные; `v` остаётся `1`.

### 2.1 Серверная модель

Расширяем `HorseC` (аддитивно, старые сохранения грузятся — новые поля нулевые):

```go
type HorseC struct {
    Owner      core.ID
    Settlement core.ID
    Name       string
    Stam       float64
    Bag        map[string]float64
    // --- ново (ADR 0011) ---
    State   string   // "stabled" | "standing" | "tethered" ; "" => legacy == "stabled"
    Pos     *ScenePosC // мировая позиция, когда State != "stabled"; nil в стойле
    Anchor  core.ID  // id серверного якоря привязи (POI/объект), только при State=="tethered"
}
```

- **`stabled`** — лошадь в стойле своего села (текущее поведение по умолчанию; `Pos==nil`). Не
  видна как свободная лошадь во дворе. Отдыхает (Stam растёт).
- **`standing`** — оставлена в подтверждённой мировой точке (`Pos`), видна как свободная лошадь.
  Не телепортируется в стойло при уходе игрока из зоны/чанка. Stam растёт медленнее (поле, не стойло).
- **`tethered`** — привязана к `Anchor` (реально существующий серверный объект: коновязь/дерево-POI).
  Радиус от якоря и отвязка проверяются сервером.

Переход `State` идёт только через авторитетные действия (ниже). `Pos` использует уже существующий
`ScenePosC` и общий `wpos = anchor_села + pos`, поэтому репликация для других игроков (AOI) работает
тем же путём, что `neighbors[].wpos` и `place.foes[].wpos` — отдельного кода проекции не нужно.

### 2.2 Descriptor в кадре (клиент читает)

Добавляем поля в существующую запись `horseEntry` (она питает `me.horse` и `me.horses[]`) —
аддитивно:

- `state`: `"stabled"|"standing"|"tethered"` — однозначная семантика размещения.
- `pos`: `{x,y,facing}` или отсутствует (в стойле). Локальные координаты села лошади.
- `wpos`: та же схема, что `me.wpos`/`neighbors[].wpos` — глобальная точка; отсутствует в стойле.
  Клиент показывает свободную лошадь только по `wpos` от сервера, не выводит её из terrain.
- `anchor_id`: id якоря при `tethered`, иначе отсутствует.
- `mountable`: bool — честный флаг «можно сесть здесь и сейчас» (владелец, рядом, не истощена,
  безопасная точка посадки есть). Аналог `can_fish` из v1.35 — вся проверка на сервере, клиент не
  гадает по дистанции сам.

Новый блок кадра (полный кадр, AOI) — **чужие** свободные лошади рядом, чтобы их было видно:

- `place.horses[]`: `{id, name, state, x, y, facing, wpos, owner_mine:false}` — только лошади в
  состоянии `standing|tethered` в зоне видимости; лошади в стойле и свои ведомые сюда не дублируются.
  Схема и порядок строятся ровно как `place.foes[]` (тот же AOI-путь), плюс лошадиные поля.

### 2.3 Намерения (клиент шлёт `op:"horse"`, идемпотентно по reqid)

Расширяем существующий обработчик `Horse(...)` новыми `action`, все через текущий
`reqid`/`alreadyDone` паттерн (bounded dedup), без нового `op`:

- `park` — спешиться и оставить лошадь `standing` в текущей подтверждённой точке игрока. Сервер
  фиксирует `Pos` = безопасная точка рядом, `State="standing"`.
- `lead` / `take` — подойдя к своей `standing`/`tethered` лошади (сервер проверяет дистанцию),
  снова сделать её ведомой; при `mount` — сесть. Повтор reqid не дублирует.
- `tether` + `target_anchor` — привязать к существующему серверному якорю (валидируется, что якорь
  реальный и в радиусе). `untether` — отвязать.
- `stable` / `unstable` — поставить в стойло реального села (только у конюшни) / забрать. В стойле
  `Pos=nil`, не видна во дворе.
- `mount` при свободной лошади рядом — как сейчас, но дистанция/безопасность проверяются сервером
  (сегодня `mount` смотрит только `Settlement`).

Короткое `E` остаётся обычным POI/NPC-взаимодействием (клиентская раскладка 0315/0316); удержание
`E` рядом со своей лошадью → `mount`/`lead`, удержание верхом → `dismount` — это клиентский маппинг
на серверные действия, сервер семантику ввода не знает.

## 3. Обратная совместимость и риски

- **Кадр.** Все поля аддитивны, `v:1`. Старый thin-client и старые Unity-клиенты игнорируют новые
  поля; лошадь для них ведёт себя как сегодня (ведомая/в стойле). Нет breaking changes.
- **Сохранения.** `State==""` трактуется как `"stabled"` (миграция «на чтение», без переписи
  сохранений). `Pos==nil`/`Anchor==0` валидны. Риск: `UpdateBurden` сейчас растит Stam всем лошадям
  безусловно — при `standing` надо развести темп восстановления (стойло быстрее поля). Инвариант
  проверяется тестом.
- **Мультиплеер/конкуренция.** `park`/`take`/`tether` меняют одно поле мирового состояния,
  читается/пишется последовательно обработкой действий (как апиарий/рыбный узел) — два игрока не
  уведут одну лошадь дважды; reqid гасит повтор. Чужую лошадь `take` не берёт (проверка `Owner`).
- **Удаление якоря.** Если `Anchor` исчезает из мира, лошадь при следующем обращении деградирует
  `tethered → standing` в своей последней `Pos` (не теряется, не телепортируется).
- **Смена села / пересечение межи.** `standing` лошадь остаётся в своей `wpos`; в кадр соседнего
  села течёт тем же кросс-граничным путём, что соседи/враги. Телепорта в стойло при уходе игрока нет.
- **Thin-client.** Текущий `thin-client/web/index.html` лошадь как сцену не рисует; он просто не
  использует новые поля — ничего не ломается. Отдельная задача — показать в нём state/mountable
  текстом (не обязательна для Unity-среза).

## 4. Список изменений при реализации (НЕ в этом ADR)

1. `1-server/sim/horse.go`: поля `HorseC`, новые `action` в `Horse()`, `mountable` расчёт, темп
   восстановления по `State`, `horseEntry` новые поля.
2. Новый `place.horses[]` (AOI) — отдельная View рядом с `FoesViewAOI` в `combat.go`/новом файле,
   тот же путь проекции `wpos`.
3. `3-dev/contract/fixtures/state_v1.example.json`: добавить `state/pos/wpos/mountable` в пример
   лошади и пример `place.horses[]`.
4. `3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md`: раздел v1.36 (аддитивно, кадр `v:1`).
5. Тесты (`1-server/sim/*_test.go`): переходы state (stable↔standing↔tethered), идемпотентность
   reqid у park/take/tether, запрет `take` чужой, деградация при удалении якоря, `mountable`
   отражает дистанцию/stam/безопасную точку, темп Stam по State, аддитивность кадра (старые поля
   не исчезли).

## 5. Порядок реализации (предлагаемый, по одному срезу за запуск)

1. **Срез A (сервер, без wpos-репликации чужих):** `HorseC.State/Pos`, `park`/`take`, `horseEntry`
   `state/pos/wpos/mountable`, миграция `""→stabled`, темп Stam, тесты. Свою лошадь уже можно
   оставить и забрать; видна в своём кадре.
2. **Срез B:** `place.horses[]` AOI — чужие свободные лошади видны рядом.
3. **Срез C:** `tether`/`untether` + валидация якоря, деградация при удалении.
4. **Срез D:** `stable`/`unstable` действия у конюшни (явные store/retrieve).

Каждый срез — отдельная feature-ветка и PR, контракт растёт только аддитивно, `v:1` неизменен,
мердж — когда Kate, Claude и ChatGPT вместе.

## 6. Что сознательно НЕ делаем

- Не вводим вторую систему координат — переиспользуем `ScenePosC`/`wpos`.
- Не даём клиенту генерировать деревья/якоря: `tether` только к реальному серверному `Anchor`.
- Не трогаем существующий `dismount` (он и так не привязан к конюшне).
- Не меняем `op`/формат кадра breaking-way; `v` остаётся `1`.
- Не начинаем реализацию до согласования (этот ADR — только предложение).
