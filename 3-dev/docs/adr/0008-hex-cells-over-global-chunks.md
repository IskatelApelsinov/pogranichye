# ADR 0008 — Логические гекс-соты поверх глобальных чанков

Дата: 2026-11-13. Статус: **предложено к принятию; архитектурное RFC, без изменения wire-протокола и runtime**.
Связано: ADR 0007, протокол v1.19, comms 0175–0177.

## Контекст

ADR 0007 уже определяет канонический `WorldPos` (кадр + E/N/U в миллиметрах), квадратный чанк 256 м и слой 64 м. Чанк — адресация terrain/данных, а не граница мира или симуляции. Нужен следующий уровень, который позволит планировать большой непрерывный мир, загружать окружение вокруг игрока и в будущем распределять серверную работу по пространству.

## Решение-кандидат

Добавить **логическую гекс-сетку регионов (сот)** поверх существующей системы. Не заменять и не переопределять:

- `WorldPos`, frame, E/N/U и правила перехода между кадрами;
- квадратные чанки 256×256 м и вертикальные слои 64 м;
- текущие terrain endpoint/cache keys;
- `place.id`, settlement anchor и локальные координаты Layout v2.

Сота — логический регион мира, а не сцена Unity, не отдельная копия мира и не обязательная единица сохранения. Поселения, дороги, реки, леса и POI — объекты/области внутри непрерывного пространства; они могут пересекать границы сот и чанков.

## Геометрия и идентификаторы

Использовать axial coordinates `(q,r)` с pointy-top гексами в плоскости E/N. Пусть `R` — расстояние от центра до вершины (метры), задаваемое конфигурацией мира, а не захардкоженное в клиенте.

Для одной соты:
- центр E = `R * sqrt(3) * (q + r/2)`;
- центр N = `R * 3/2 * r`;
- устойчивый ID: `<frame>:<q>:<r>`.

Шесть соседей в axial координатах: `(+1,0), (+1,-1), (0,-1), (-1,0), (-1,+1), (0,+1)`. Координаты соты вычисляются из глобальной E/N, а не из settlement ID. Для отрицательных координат и точек на границах требуется единая детерминированная cube-rounding реализация и тесты; нельзя независимо округлять q и r.

**Размер R пока не фиксировать.** Ввести параметр мира и сравнить кандидаты на реальном распределении поселений/ландшафта, сетевом трафике и Unity memory. Не путать радиус до вершины R с радиусом вписанной окружности.

## Разделение уровней

| Уровень | Назначение | Единица |
|---|---|---|
| WorldPos | Истинное положение сущности/точки | frame + E/N/U mm |
| Hex cell | Логическая география, соседство, streaming policy, будущий shard ownership | frame + q + r |
| Terrain chunk | Рельеф, коллизии, растительность и кэш ресурсов | 256×256 м + layer |
| Settlement / POI | Социальное и игровое содержание | стабильный ID + WorldPos/footprint |

Один гекс содержит много квадратных чанков; один чанк может пересекать границу гексов. Все запросы terrain остаются по chunk coordinates. Manifest/индексы могут связывать cell с пересекаемыми chunk IDs, но chunk не должен принадлежать только одной соте, если его геометрия пересекает границу.

## Потоковая загрузка Unity (целевое поведение)

Это политика-кандидат, а не утверждение о текущей реализации:

1. Центральная сота: полная детализация.
2. Первое кольцо (6 соседей): полные данные для непрерывного передвижения, коллизий и навигации.
3. Второе кольцо: облегчённые метаданные/LOD и фоновая предзагрузка.
4. Вне второго кольца: выгрузка только после проверки ссылок/активных объектов и безопасного retention.
5. Все соты/чанки загружаются с перекрытием. Старое окружение остаётся доступным, пока новое не загружено и не прошло валидацию.
6. Handover не меняет глобальную позицию, entity ID, velocity, цель камеры или сетевую сессию. Нет загрузочной сцены, телепортации или сброса NPC.
7. Очередь запросов приоритизируется по расстоянию/направлению движения и критичности (коллизии выше декора). Отменённый запрос не должен портить общий cache; поколение запроса отделяется от ключа ресурса.
8. Hysteresis: выгрузка использует более дальний порог, чем загрузка. Конкретный запас выбирается измерением, чтобы движение вдоль границы не вызывало дребезг.

Технически первый этап должен продолжать использовать уже существующие terrain chunk cache и overlap. Не вводить отдельный параллельный terrain cache «по сотам».

## Сервер и симуляция

- Положение игрока/NPC/предмета всегда задаётся WorldPos; соту можно вычислить из него.
- Переход через границу соты сам по себе не меняет entity, PlaceC, settlement, расписание, маршрут или владение предметами.
- NPC могут идти через соты по непрерывным глобальным маршрутам; серверный AOI выбирает сущности по пространственной близости, не только по `place.id`.
- Граница соты не является препятствием для дорог, рек, маршрутов, коллизий, видимости или звука.
- В будущем cell может быть кандидатом на серверный shard/worker ownership, но только после определения миграции сущностей, согласованного handoff и защиты от двойного владельца. В первом релизе соты не распределяют авторитетность симуляции.
- Протокол v1.19 не меняется. Не добавлять cell ID в snapshot до отдельного доказанного потребителя и согласованного контракта.

## Генерация и стыки

- Генерация рельефа/биомов/экологии должна быть детерминирована от world seed + frame + глобальных координат/идентификатора контента, а не зависеть от порядка загрузки сот.
- Общие границы terrain chunks продолжают использовать единые edge samples.
- Дороги, реки и nav graph должны пересекать границы без разрывов; сегменты принадлежат глобальным объектам/графам, а не дублируются с независимыми концами в каждой соте.
- POI и поселения имеют стабильные IDs и глобальные footprints; соты лишь индексируют пересечения.

## Этапы реализации

A. Pure C# axial math: world↔cell, соседство, отрицательные координаты, границы и deterministic ID; без Unity scene side effects.
B. Unit/regression tests и визуальный debug overlay (не runtime gameplay dependency).
C. Cell manifest/index поверх текущего /api/world + chunk cache, сначала локально вычисляемый клиентом.
D. Multi-cell streaming coordinator: ring policy, request prioritization, hysteresis, resource ownership/refcounts; сначала terrain/geometry.
E. Глобальные дороги/реки/POI и multi-layout presentation; затем global entity presentation.
F. Серверный spatial AOI и NPC movement — отдельные совместимые PR, после тестов двух наблюдателей на границе.
G. Только после измерений — решение о server shard ownership.

## Критерии приёмки

- Для одной WorldPos вычисляется один и тот же cell ID в Go и C#; таблица тест-векторов общая.
- Шесть соседей взаимны; axial distance и ring enumeration корректны.
- Границы сот не создают разрывов terrain/дорог/рек/nav.
- Перемещение через несколько сот не меняет entity ID/WorldPos непрерывность и не вызывает reset/reconnect.
- Быстрое движение и разворот на границе не вызывают постоянную перезагрузку; старые ресурсы не выгружаются до готовности новых.
- Нет дублированных NPC/объектов и двойного владения.
- Unity Editor/PlayMode и two-client tests обязательны для runtime acceptance; pure C# CI не выдаётся за проверку Unity.

## Не входит в это решение

Не менять размер terrain chunk, frame projection, settlement ownership semantics, protocol v1, текущий флаг seamless, сохранения и серверную авторитетность. Не делать гексы отдельными Unity scenes. Не вводить «загрузку локации» на границе поселения.
