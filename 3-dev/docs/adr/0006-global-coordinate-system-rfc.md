# ADR 0006 — Глобальная система координат: RFC перед реализацией

Дата: 2026-11-11. Статус: **Proposed / уточнён после PR #338–#339; требуется совместный review глобального физического адресного пространства**.
Связано: ADR 0004 §§3, 6–9, comms 0072–0073, 0098–0099, PR #338–#339, протокол v1.18.

## 1. Зачем отдельное решение

Миру нужна одна непрерывная физическая система координат для персонажей, NPC, поселений, дорог,
рек, POI, ресурсов, построек и сохранений. Координаты должны оставаться стабильными при потоковой
загрузке, переходах между поселениями, смене активного региона и Unity floating origin.

Нельзя смешивать физическое положение в мире (метры), индексы чанка и локальное смещение,
административную/климатическую широту и долготу, координаты региональной карты, локальные координаты
поселения/POI и Unity presentation coordinates после floating-origin shift.

ADR 0004 задаёт направление. В PR #338 уже добавлены сферическая азимутальная равноудалённая проекция, геодезические преобразования, кратчайшая дистанция и floor-адресация локальных метровых чанков. В PR #339 эта проекция подключена к SiteC.lat/lon: SettlementC.X/Y остаются прежними плоскими координатами-источниками, а SiteC получает CoordVersion и миграцию v0. Следовательно, сферическая геодезическая интерпретация уже существует в main. Однако это ещё НЕ полноценная canonical world position: SettlementC.X/Y не заменены глобальным адресом поверхности, физические сущности не адресуются чанками, а бесшовный global movement, world chunk manifest и Unity streamer не реализованы. Этот ADR уточняет границы уже сделанного и предлагает следующий этап, не отменяя PR #338/#339.

## 2. Инварианты

1. Один мир имеет стабильный world_id и версию пространственной схемы.
2. Глобальное положение не зависит от загруженного чанка/поселения.
3. Все физические расстояния и размеры выражаются в метрах.
4. Отрицательные координаты поддерживаются симметрично положительным.
5. Нормализация использует floor division/modulo, не усечение к нулю.
6. Чанк — единица адресации/стриминга/сохранения, не стена и не отдельная сцена.
7. Пересечение границы чанка/региона не меняет ID сущности, позицию, историю, соединение или симуляцию.
8. Unity floating origin меняет только presentation transform, никогда server/world coordinates.
9. Старые ScenePosC, me.pos, Layout v2, GeometryVersion 2 и frame v1 не переинтерпретируются молча.
10. Сервер авторитетен по позиции, столкновениям, доступности POI и переходам.
11. Thin client может временно пользоваться абстрактным Journey workflow, но не отдельной позицией.
12. Географическая широта/долгота/высота и климатические атрибуты не выводятся из локальных координат
    поселения и не подменяются индексами чанков.

## 3. Геометрия поверхности: что уже решено и что ещё требуется проверить

Сферическая поверхность — текущая техническая основа, уже используемая PlanetC/PlanetProjection и SiteC. PR #338/#339 не следует повторно реализовывать. Claude Fable должен проверить её пригодность для полного планетарного мира, включая масштаб/радиус, полюса, антиподы, антимередиан и маршруты.

Открытый вопрос теперь уже не «делаем ли широту/долготу на сфере вообще», а как адресовать физические метры, чанки и локальные tangent frames на всей сфере. Варианты ниже — сравнение способов tiled/local адресации поверх принятой сферической поверхности, а не отмена текущей геодезии.

### A. Бесконечная плоская метрическая сетка (только локальный физический frame)

Claude Fable должен сравнить минимум три модели.

### A. Бесконечная плоская метрическая сетка
Достоинства: простая точная локальная физика, лёгкий chunk addressing, совместимость с текущими X/Z.
Недостатки: нет естественных полюсов/долгот/замкнутой планеты; климатическую широту придётся задавать
отдельным world-field/биомным атрибутом. Подходит, если канон допускает плоскую географию или если
«глобальность» означает очень большой мир без планетарного обхода.

### B. Сферическая поверхность с локальными tangent frames (согласуется с текущей geodesy)
Достоинства: естественные широта, долгота, полюса, климатические пояса и глобальный обход.
Недостатки: локальная физика и чанки требуют проекции/кубической сферы или tangent-frame системы;
сложнее seam consistency, маршрутизация и Unity streaming; долгота не является линейной X на всех широтах.
Нужны радиус, datum, высотная модель и устойчивая адресация граней/чанков.

### C. Конечная tiled projection поверх сферы (например cube-sphere / HEALPix-подобная адресация)
Достоинства: конечный мир и глобальный охват с регулярной адресацией; можно избежать сингулярности
обычной широтно-долготной сетки.
Недостатки: сложнее локальных плоских координат; требуется точное правило перехода между гранями,
соседями и seam samples. Нужно доказать достаточную метрическую точность для дорог и геймплея.

Не начинать выбор с нуля и не откатывать уже внедрённую сферу без веской причины. Сравнить способы адресации чанков/локальной физики на ней. Проверить соответствие радиуса и распределения держав канону. Отдельно указать, достаточно ли текущей azimuthal equidistant projection как преобразования от котла для генерации поселений, или для далёких областей требуется иная tiled atlas. Художественный канон планеты Ёф уже есть в КАНОН-ЛОР-И-МЕХАНИКИ.md; техническая адресация поверхности не должна менять его.

## 4. Предлагаемый разделённый coordinate stack

Независимо от проекции рассмотреть слои:
1. World identity: world_id, coordinate_scheme, scheme_version.
2. Canonical world location: точная серверная координата выбранной проекции/поверхности.
3. Metric local frame: локальная метрическая система для физики, POI и коротких маршрутов.
4. Chunk address: знаковый индекс/набор индексов чанка плюс нормализованный локальный offset.
5. Geographic attributes: latitude/climate band, elevation, biome/ecoregion.
6. Settlement frame: локальные координаты поселения, преобразуемые через стабильный anchor/transform.
7. Unity render frame: float coordinates относительно floating origin, строго производные.

Точные типы (int64 миллиметры/сантиметры, float64 метры, fixed point или комбинация) выбрать после
анализа точности, дальности, сериализации и производительности. Не вводить float32 для абсолютных
мировых координат. Размер чанка 256 м и region 32×32 остаются кандидатами до benchmark.

## 5. Обязательные математические и API свойства

Определить canonical encode/decode и round-trip; расстояние/направление в локальном метрическом frame;
location → chunk address и обратно; нормализацию отрицательных координат; стабильные chunk IDs и
neighbour relation; правила границ; детерминированные seed inputs; сериализацию и backward-compatible
migration; overflow; точность на локальном радиусе физики и дальних расстояниях; перевод settlement-local
POI/ScenePos в world coordinates; правила движущихся сущностей при пересечении чанка.

Для tiled projection тестировать seam continuity: высоты, дороги, реки, навигационные связи, POI anchors
и collision должны совпадать с обеих сторон границы.

## 6. Безопасная миграция

1. Инвентаризировать все источники/потребители ScenePosC, me.pos, neighbor positions, POI, exits,
   NPC movement, resource nodes, saves, fixtures, Unity placement and movement.
2. Зафиксировать текущую семантику и диапазон Layout v2 / GeometryVersion 2.
3. Добавить pure conversion layer и тесты на известные settlement anchors, не меняя gameplay.
4. Ввести canonical world position отдельным полем/компонентом только после согласования схемы и миграции.
5. Сохранять старое представление для старых клиентов и legacy thin-client flows.
6. Переносить по одному домену: POI → NPC → resources → players → roads/collision → persistence.
7. Удаление legacy координат — отдельное решение и релиз.

Нельзя просто прибавить origin поселения к me.pos, если это меняет смысл или даёт двойное смещение Unity.
Нельзя использовать op:travel для физического движения Unity.

## 7. Этапы после совместного выбора

- G0 review: Claude Fable + ChatGPT проверяют уже merged spherical geodesy #338/#339, выбирают глобальную tiled/chunk addressing поверх неё и сверяют радиус/масштаб с каноном владельца.
- G1 math substrate: чистые координатные типы и функции, property/fuzz tests, golden fixtures;
  без ECS/wire/persistence/runtime integration.
- G2 legacy adapter: конвертация стартового поселения и POI; сравнение с текущей сценой.
- G3 persistence: additive save format, миграционные тесты и reconnect.
- G4 wire/resource API: additive protocol fields и chunk manifest endpoint.
- G5 Unity: world/local conversion, floating-origin service, debug overlay, chunk request shell.
- G6 physical traversal: после server collision/navigation/streaming proof.

Каждый этап — отдельный PR. G1 не должен незаметно превращаться в G3/G4.

## 8. Acceptance criteria для G1

- Property tests: decode(encode(p)) в пределах объявленной точности.
- Round-trip chunk address и проверка соседства.
- Отрицательные координаты по всем осям и значения по обе стороны нуля.
- Точки на границах чанка, включая углы и отрицательные границы.
- Большие координаты без float32 precision loss/overflow.
- Детерминизм encode/decode/ID при повторном запуске.
- Fuzz tests экстремальных значений и некорректных входов.
- Документированные единицы, диапазоны и ошибки.
- Нет изменений gameplay, wire, save format или Unity runtime.

## 9. До закрытия G0 запрещено

Не менять ScenePosC, me.pos, neighbors[].pos и wire frame; не добавлять production WorldPosition/ECS;
не менять save/load, world seed или IDs; не менять SceneRadius, Layout v2, GeometryVersion 2 и POI;
не менять movement, collision, NPC navigation, op:travel и Unity transforms/streamer.

Разрешены документация, source audit, математические прототипы вне runtime и тестовые таблицы сравнения.
Любое исключение требует отдельного согласования владельца.

## 10. Решение

До совместного review Claude Fable этот ADR остаётся Proposed. Уже существующая сферическая геодезия #338/#339 сохраняется; следующее решение касается canonical physical world address, chunk atlas, локальной метрической физики и миграции SettlementC.X/Y. После решения создать decision revision и обновить протокол только если появляется wire-level контракт.
