# ADR 0009 — Магическое пространство узлов и модель знаний (RFC)

Дата: 2026-11-16. Статус: **предложено к обсуждению; архитектурное RFC, без изменения wire-кадра `v:1` и runtime**.
Связано: comms 0262 (ChatGPT → Claude, направление магии, подтверждено владельцем), `1-server/sim/weave.go`, `1-server/sim/study.go`, ADR 0001 (протокол).

Это ответ на 6 пунктов из 0262. Сначала разбор и этапы — массовой реализации в этом срезе нет, контракт не трогается.

## 1. Сверка концепции с текущей реализацией

Факты из кода (не из памяти), `1-server/sim/weave.go`:

- **Палитра узлов — 10 типов**, `WeaveNodes`: `knot, thread, loop, fork, barb, seal` (v1.10) + `heat, chill, veil, eye` (v1.22). Это и есть «колесо на 10 UI-позиций» из 0262.
- **`weaveMaxLen = 12`** — предел ДЛИНЫ собранной последовательности, не размер палитры. Расхождения «10 против 12» нет: 10 — сколько РАЗНЫХ узлов можно поставить, 12 — сколько узлов (с повторами) умещается в одном узоре. Это две независимые оси.
- **`ReadWeave(nodes)` — чистая детерминированная функция**. Эффект (`WeaveSpec`: Kind/Power/Range/Targets/Stun/Linger/Complexity/Cost/Closed) выводится из МУЛЬТИМНОЖЕСТВА узлов (счётчики `n["barb"]` и т.п.) плюс признак замкнутости `Closed = nodes[0]=="knot" && nodes[last]=="seal" && n["seal"]==1`. Порядок сегодня влияет ТОЛЬКО на замкнутость (концы узора), не на само действие.
- **Свод схем `schemaLore` — 21 именованная схема**; у мага `GrimoireC.Known` (с рождения Светоч+Искра, до 28 штук). Открытие схемы происходит в `WeaveCast`, когда маг удержал незнакомый узор: совпал со сводом → имя из свода, иначе «Свой узор N».
- **Знание ≠ сила ≠ контроль уже разделены**: `g.knows(nodes)` даёт только `eff += 12` (увереннее держится) и подсказку имени; ёмкость ума — отдельная ось `arcane.Capacity(skillOf(mage))`; дар/потолок тела — `weaveGate`/`GiftView`. Срыв бьёт по магу (`backfire`).
- **Передача знаний уже начата**: `study.go` — `act:"study"` открывает простейшую ещё неизвестную схему у наставника-мага; книги помечены как «следующий срез (нужен предмет-источник)».

## 2. Что поддерживает текущая архитектура, а что требует новой модели

**Уже поддержано (концепция ложится на существующий код без ломки):**

- Детерминированность и воспроизводимость результата при равных входах и состоянии мира — `ReadWeave` чистая, `WeaveCast` идемпотентна (`reqid` + `markDone`).
- Сервер авторитетен для эффекта/стоимости/последствий; клиент передаёт только выбранные узлы и цель.
- Разделение «сила/расход/контроль/риск» (пункт 0262 «знание координаты ≠ безопасное мощное плетение»).
- Эффект вычисляется из состава, а не из таблицы готовых заклинаний (пункт 0262 «не прописывать 10 000 заклинаний»).
- Открытие узора экспериментом (пробой в `WeaveCast`) и у наставника (`study.go`).

**Требует новой модели / отдельного среза (и согласования до кода):**

- Явное разделение **знания ИГРОКА** и **знания ПЕРСОНАЖА** (сейчас есть только знание персонажа — `GrimoireC.Known`).
- Книги/записи/рукописи как ПРЕДМЕТЫ-источники координат, в т.ч. повреждённые/неполные.
- Передача записи между игроками (копируемый предмет).
- Небоевые эффекты (срубить дерево, очистить одежду, воздействовать на материал/среду) — нужна модель объектов/материалов мира, это отдельный ADR.
- Любой непрерывный 2D-ввод координат в толстом клиенте — только после того, как модель знаний себя оправдает.

## 3. Как читать «сетку 100×100»

Сетка из 0262 — **дизайн-метафора пространства принципов**, а не 10 000 рукописных заклинаний (0262 это подтверждает). Два пути согласования:

- **(A) Координата как индекс комбинации.** «Координата» — устойчивый вид на уже существующее комбинаторное пространство плетений: узор = путь из узлов, у канонической формы узора есть устойчивый идентификатор. Движок эффекта остаётся `ReadWeave`. Ничего не ломается. **Рекомендуется как старт.**
- **(B) Координата как новый примитив.** Заменить/дополнить палитру из 10 узлов непрерывной 2D-координатой на узел — большой сдвиг: нужен новый `ReadWeave`, риск сломать семантику `schemaLore`. Приемлемо ТОЛЬКО аддитивно и только если (A) окажется недостаточной.

Рекомендация: не выбрасывать логичную грамматику узлов. Ввести **детерминированную «координату» = устойчивый идентификатор канонической последовательности узлов**. Тогда «знать координату» = знать конкретный узор; «вручную попасть в неизвестную координату» = самому собрать узлы без автонаведения; эффект по-прежнему даёт `ReadWeave`. Это кладётся на текущий расчёт `eff` без нового кадра.

## 4. Обнаружение и передача знания (аддитивно, сервер-авторитетно)

- **Знание персонажа** = `GrimoireC.Known` (освоено: автонаведение + бонус `+12` к удержанию).
- **Знание игрока / подсказки-рецепты** (НОВОЕ, аддитивно): координаты, которые игрок может воспроизвести ВРУЧНУЮ (из книги/от игрока), но персонаж ещё не освоил — без бонуса `+12`, полный риск срыва. Точно ложится на текущий расчёт `eff` в `WeaveCast`.
- **Книги/записи** — предмет, несущий `Schema` + полноту. Повреждённая запись → неполный список узлов (игрок достраивает пробел сам). Точная запись → полный узор.
- **Наставник** — уже есть (`study.go`): передаёт освоение (мастерство персонажа).
- **Игрок→игрок** — копируемый/передаваемый предмет-запись.

Всё это — новые `me.*`-поля и серверные предметы; **кадр остаётся `v:1`**, поля только добавляются, со `state_v1.example.json` fixture и тестами, и только после согласования.

## 5. Три состояния знания — как сервер их различает (ложится на текущий код)

| Состояние | Сейчас в коде | Поведение |
|---|---|---|
| Известная координата (персонаж освоил) | `g.knows(nodes)==true` | автонаведение в UI, `eff += 12` |
| Ручное попадание в неизвестную координату | `ReadWeave(nodes)` читает любой валидный состав; `g.knows==false` | без автонаведения, полный риск срыва; при удержании — узор запоминается (существующая ветка «запомнил») |
| Освоенное понимание принципа | ось `skillOf("mage")` / `arcane.Capacity` / `weaveGate` (дар) | отдельно от знания конкретного узора: знание ≠ безопасная мощь |

Игрок может знать координату из книги (воспроизводит вручную), а персонаж при этом её не освоил — это и есть разделение «знание игрока ≠ знание персонажа».

## 6. Риски

- **Взрыв контента.** 100×100 как 10 000 рукописных эффектов — отвергаем; движок эффекта — комбинаторный `ReadWeave`.
- **Нечестная «пиксельная ловушка».** Непрерывный 2D-ввод по неизвестным координатам может стать нечестным. Сегодня дискретная палитра этого не допускает; при переходе к (B) точность должна быть квантованной/допускающей, а наведение — навыком и инструментами, не пикселем.
- **Чувствительность к порядку.** Сегодня порядок влияет только на замкнутость. Модель, где порядок начинает менять эффект, изменит исходы существующих `schemaLore` → допустимо только аддитивно/опционально.
- **Контракт.** Любые новые данные — только аддитивные `me.*`-поля; кадр `v:1`; fixture + контракт-док + тест в одном срезе с полем.
- **Воспроизводимость.** Любая новая модель — чистая функция входов и состояния мира, как `ReadWeave`.

## 7. Поэтапный план

- **S0 (этот срез):** ADR + сверка, без кода. ← вы здесь.
- **S1:** аддитивная серверная модель «рецептов, известных игроку» отдельно от освоенных схем персонажа; аддитивные поля `me.weave`; fixture + тест. Только после совместного согласования.
- **S2:** книги/записи как предметы мира (источник координат), повреждённые/неполные записи.
- **S3:** передача игрок→игрок (копируемый предмет-запись).
- **S4:** расширение пространства эффектов (небоевые: срубить дерево, очистить одежду, воздействие на материал) — нужна модель объектов/материалов, отдельный ADR.
- **S5:** опциональный непрерывный/координатный UX в толстом клиенте — только если S1–S4 оправдали модель знаний; точность — на клиенте, сервер валидирует фактически присланные узлы.

## Границы

- Толстый клиент в фокусе; тонкий клиент этой итерацией не ограничиваем и не проектируем (как просил владелец в 0262).
- Без изменения wire-кадра, без правки существующих узлов/схем, без слома совместимости.
- Сетка 100×100 — согласованная концепция для проработки, не окончательная техническая схема. Детали точности, координатной системы и семантики узлов требуют совместного дизайна до S1.
