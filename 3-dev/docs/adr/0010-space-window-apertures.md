# ADR 0010 — Оконные проёмы в серверной геометрии пространств (/api/spaces)

Дата: 2026-11-19. Статус: предложено (PR открыт, merge — только с Kate).
Связано: письмо Kate `3-dev/comms/0301-kate-to-claude-server-space-window-apertures.md`, клиентский PR #749,
`1-server/sim/spaces.go`, fixture `3-dev/contract/fixtures/spaces_v1.example.json`.

## Контекст

`/api/spaces` отдаёт серверно-авторитетную геометрию зданий (`spaces[].surfaces`). У корчмы сервер строил
сплошные стены (`ring`/`wall`), которые накладывались на клиентский фасад и закрывали окна, нарисованные в
Unity. Одного клиентского изменения мало — пока в серверной оболочке нет проёма, дневной свет не попадает в
зал, а параллельный клиентский «проём» рассинхронизирован с авторитетной геометрией.

## Решение

Окно — часть серверной геометрии, а не отдельная система и не портал.

- Новый вид поверхности `kind:"window"` с дополнительным полем `transparent:true`. Остекление остаётся
  `collidable:true, walkable:false`: сквозь окно нельзя пройти. `transparent` явно отделяет визуальную
  прозрачность (клиент рисует стекло и пропускает свет) от блокирующей коллизии (ответ на п.4 письма 0301:
  «безопасное разделение визуальной геометрии и blocking collider либо отдельное явное поле»).
- Окно — рама, а не дыра: вокруг светового проёма в тех же стенах остаются глухие `wall`-поверхности
  подоконника, перемычки и боковых простенков (`apertureWall`). Несущая коллизия не разрывается.
- Детерминированные размеры от здания, не от координат мира: ширина `winW=1.2`, низ `winSillH=0.9`, верх
  `winHeadH=2.0` м, минимальный простенок `winMinPier=0.6`. Окна ставятся по центру трёх фасадов БЕЗ двери
  (левый/правый/задний), на первом ярусе — и в наружной оболочке, и во внутреннем кольце (совпадают по
  фасаду), чтобы свет дошёл в зал. Ориентация идёт через те же оси `facing`, что и дверь, — проверено на
  всех четырёх сторонах света.
- Никаких новых порталов, id пространств, переходов, gameplay-действий. Права движения не меняются: внутрь/
  наружу по-прежнему пускает только дверь и существующие серверные правила; описание пространства прав не даёт.

## Контракт

Аддитивно. Кадр `v:1` не меняется. `GET /api/spaces` конверт и поля прежние; добавлен `kind:"window"` в
перечень видов `surface` и поле `transparent` только у окон. Старые клиенты, не знающие `window`, увидят
обычную поверхность и не ломаются; сохранения и Layout v2 не затронуты. Doc-метка — v1.35.

## Последствия / клиент

Unity: рисовать `window` как остекление/проём, но держать его collider'ом — не открывать проход через окно.
`revision` чанка меняется при изменении оконной геометрии (отпечаток считается по содержимому).

## Проверка

`go build/vet/test ./...` зелёные; `UPDATE_FIXTURES=1 … TestSpacesEndpoint` обновил `spaces_v1.example.json`.
Регрессии в `sim/spaces_window_test.go`: окна прозрачны+collidable+непроходимы, в пределах охвата, только на
первом ярусе, без лишних порталов; все четыре `facing` ставят окна на три фасада без двери; окно — пояс
`[sill..head]`, а не дыра во всю высоту; `revision`/описание реагируют на оконную геометрию.

## Отвергнутые варианты

- Дыра в стене без остекления — нарушает п.4 (проход через окно), отвергнут.
- Отдельная система «окно-портал» — избыточна, ввела бы переход/права; окно остаётся только геометрией.
- Окна у каждого дома — пока только корчма имеет серверные `spaces` (граница письма 0301).
