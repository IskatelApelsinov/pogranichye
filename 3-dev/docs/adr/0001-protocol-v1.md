# ADR 0001. Протокол клиент↔сервер v1: идентификаторы сущностей и версия

Дата: 2026-11-02. Статус: предложено (ждёт подтверждения Kate для merge).
Участники: Claude (сервер), ChatGPT (Unity). Контракт: `3-dev/docs/ПРОТОКОЛ-КЛИЕНТ-СЕРВЕР.md`.

## Контекст

v0 отдавал кадр состояния без идентификаторов сущностей и без версии протокола. Unity для
устойчивого визуального слоя (Entity View / Prefab Registry — сопоставление серверной сущности её
визуальному представлению) нужен стабильный ключ сущности. Также нужен способ версионировать
протокол, чтобы дальше не ломать клиент молча.

## Решение

1. В кадр добавлены `me.id` и `neighbors[].id` — серверный `uint64`, переданный **строкой**.
   Причина строки: JSON-число в JavaScript — double, теряет точность за 2^53; строка безопасна и для
   web-клиента, и для Unity (парсит в `ulong`). id стабилен в пределах жизни мира.
2. В кадр и в намерение добавлено поле `v` (целое, сейчас `1`). Сервер пока не отвергает намерения
   по версии, но поле заложено для будущей несовместимости.

Отложено (согласовано как НЕ входящее в v1): физические координаты (§6.2), отдельный событийный
канал (§6.3), быстрый боевой цикл (§6.5) — каждое станет своим ADR и подъёмом версии.

## Последствия

- Общий пример кадра зафиксирован в `3-dev/contract/fixtures/state_v1.example.json`; Go-тест
  `server/contract_test.go` проверяет, что живой кадр совпадает с ним по СХЕМЕ (набору полей).
  Unity-тест совместимости возьмёт тот же fixture.
- Любое изменение формы кадра теперь обязано обновлять и fixture, и этот контракт, иначе Go-тест
  падает — код и контракт держатся вместе.

## Альтернативы

- id числом — отвергнуто из-за потери точности в JS.
- Отдельное handshake-сообщение с версией вместо поля в каждом кадре — избыточно для v1; поле `v`
  проще и достаточно.
