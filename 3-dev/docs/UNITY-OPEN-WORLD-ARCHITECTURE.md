# Unity 6 — архитектура клиента для огромного открытого мира

Дата: 2026-11-16  
Целевая версия: Unity 6000.6.7f1 (Unity 6.6), URP  
Статус: архитектурное решение и план внедрения; не означает, что все подсистемы уже реализованы.

## 1. Главный принцип

«Пограничье» — единый постоянный мир, а не набор локальных Unity-сцен. Сервер владеет глобальной географией, координатами, состоянием мира, NPC, ресурсами, переходами и проверкой движения. Unity-клиент отвечает за локальную проекцию этого мира: видимую геометрию, анимации, звук, эффекты, UI, LOD и потоковую загрузку.

Клиент не должен создавать альтернативную игровую реальность. При этом чисто визуальные детали (например, трава или кроны деревьев) могут детерминированно строиться по серверным зонам/seed, если они не создают gameplay-сущностей, авторитетных коллайдеров, POI или ресурсов. Сервер остаётся источником границ и семантики зоны.

## 2. Что уже есть в проекте

- Серверная система координат E/N/U; глобальные позиции хранятся с миллиметровой точностью и передаются в JSON в метрах.
- Серверный terrain chunk: 256×256 м; heightfield сейчас имеет шаги 8/16/32/64 м.
- Вертикальный streaming layer 64 м — технический ключ, не номер этажа.
- Unity получает серверные layout/roads/zones/POIs и строит локальную презентацию.
- Серверный layout уже содержит упрощённые river band/bridge corridor, но это ещё не полноценная гидрология.
- Универсальный контракт этажей/пещер/порталов/лестниц пока находится в стадии согласования; предложенный `/api/spaces` не считать действующим endpoint до реализации сервером.
- Горный рельеф не является запретной кольцевой границей: крутые склоны затрудняют движение, отвесные скалы могут быть непроходимы, естественные перевалы и седловины доступны.

## 3. Разделить серверную сетку и клиентскую сетку рендера

Не нужно заставлять один размер чанка решать все задачи.

1. **Server data chunk** — текущие 256×256 м: удобная единица запроса/кэширования авторитетных данных.
2. **Render tile** — внутреннее разбиение чанка, ориентир 64×64 или 128×128 м. Это позволяет независимо строить mesh, LOD, collider и выгружать мелкие области, не меняя серверный контракт.
3. **Presentation cell** — ячейка объектов/растительности/звука и локальных эффектов; её размер может отличаться от render tile.
4. **Semantic space** — дом, этаж, комната, подвал, пещера, шахта. Это не отдельная Unity Scene и не отдельная физическая система координат.

Размеры 64/128 м — рабочая гипотеза для профилирования, не утверждённые серверные константы. Сначала реализовать один чанк и измерить стоимость.

## 4. Потоковая загрузка мира

Для каждой клиентской ячейки использовать явный жизненный цикл:

`Unloaded → Requested → DataReady → Building → Visible → Cooling → Unloaded`

- Запросы дедуплицируются по chunk/cell key.
- Каждая операция имеет generation token; поздний ответ от старого запроса/соединения не может заменить новое состояние.
- Соседние ячейки предзагружаются до входа игрока в них.
- Загрузка и построение ограничиваются бюджетом на кадр; нельзя синхронно создавать сотни объектов при пересечении границы.
- Радиус загрузки больше радиуса выгрузки (hysteresis), чтобы не было дребезга на границе.
- При выходе из радиуса сначала отключать presentation/colliders, затем освобождать meshes/textures после безопасного завершения ссылок.
- Отмена устаревших запросов и reconnect не должны очищать буфер нового сокета.
- Состояние мира/персонажа не должно зависеть от того, успела ли Unity загрузить визуальную ячейку.

Addressables полезны для асинхронной загрузки prefab/material/texture/scene assets, но сами по себе не являются системой серверного world streaming. Управление ячейками, версиями данных, отменой и memory budget остаётся отдельной подсистемой клиента.

## 5. Дистанционные уровни представления

Не держать весь мир в полном качестве.

| Дистанция | Что показываем | Физика |
|---|---|---|
| Ближняя | Полная геометрия, персонажи, интерактивные предметы, локальные эффекты | Коллайдеры только для нужных поверхностей и препятствий |
| Средняя | Упрощённые mesh/LOD зданий, деревьев и рельефа; редкие NPC как упрощённые представления | Обычно без детальных коллайдеров |
| Дальняя | Силуэты поселений, крупные формы рельефа, impostors/horizon | Нет |
| За пределами видимости | Только серверное состояние/кэш данных, без Unity GameObjects | Нет |

LOD должен зависеть от экранного размера и видимости, а не только от фиксированного расстояния. Для леса — отдельные батчи по серверным зонам, несколько уровней крон и подлеска; дальний лес можно заменить упрощённым canopy mesh/impostor.

## 6. Рельеф, вода и многоуровневые пространства

- Глобальная геометрия остаётся в серверной E/N/U системе. Unity переводит её в локальные координаты текущего floating origin.
- Heightfield на 8–64 м подходит для общей формы/дальнего рельефа, но не даёт достаточной детализации у ног игрока. Для ближнего слоя нужен более частый серверный heightfield (ориентир 1–2 м или 2–4 м) либо согласованный детерминированный detail layer, совпадающий с серверной проверкой движения.
- Между LOD/чанками нужны тесты непрерывности высоты и нормалей, чтобы не появлялись щели и ступени.
- Для рек/озёр нужны поверхности воды, берега, глубина/течение и мосты как связанные серверные данные; одной полосы river band недостаточно.
- Этажи, лестницы, чердаки, подвалы, пещеры и шахты — серверные spaces/portals/stairs с устойчивыми ID. E/N/U остаются непрерывными; semantic space/level меняются при переходе.
- Клиентские mesh collider используются для локальной обратной связи, но не решают, может ли персонаж пересечь гору, закрытую дверь или портал. Это проверяет сервер.

## 7. Большие координаты и floating origin

Unity Transform использует float-координаты. Нельзя напрямую переносить в Transform абсолютные координаты мира на сотни километров: точность будет теряться, появятся дрожание, ошибки контактов и несовпадение объектов.

Решение:
- Серверные координаты хранить/обрабатывать как long/int миллиметры или double в клиентской модели данных.
- В Unity Transform передавать только локальные float-координаты относительно текущего origin.
- Origin сдвигать пакетно, когда игрок удаляется от него на настраиваемый порог; начальный экспериментальный порог 2–4 км, затем профилирование.
- При сдвиге согласованно перемещать все локальные корни, активные rigidbody, камеру, временные эффекты и аудио-источники. Не менять глобальные координаты, reqid, chunk key или сетевое состояние.
- Сдвиг должен происходить в одной контролируемой фазе кадра, без рассинхронизации physics step.
- Тестировать движение через границу origin, teleport, reconnect, транспорт, NPC и несколько игроков рядом.

## 8. Рендеринг и производительность в URP

- Сначала использовать общие mesh/material/shader variants и батчить повторяющиеся объекты.
- GPU Resident Drawer / BatchRendererGroup — кандидат для массовых одинаковых деревьев, камней, травы и других совместимых объектов. Он в первую очередь снижает CPU draw-call overhead, но может увеличить GPU workload; включать после сравнения Profiler/Frame Debugger на целевых сценах.
- GPU occlusion culling не включать вслепую: он полезен при большом количестве повторяемой геометрии и сильной окклюзии, но может ухудшить кадр, если setup cost выше выигрыша.
- LODGroup и small-mesh culling использовать с визуальной проверкой на растительности, вывесках, проводах и тонких объектах.
- Не создавать отдельный GameObject на каждый куст/пучок травы. Предпочитать batched meshes, instancing или GPU Resident Drawer.
- Сократить realtime shadows: ограничить дальность, число каскадов и число объектов, отбрасывающих тени.
- Для больших открытых областей изучить Adaptive Probe Volumes streaming; не загружать весь baked lighting volume в память.
- Включить mipmap streaming и следить за texture memory; разделять texture budget для ближней/средней/дальней дистанции.
- Не полагаться на baked occlusion как на универсальное решение для постоянно меняющегося мира и динамически загружаемых объектов.

## 9. NPC и симуляция

- Сервер симулирует поведение и перемещение NPC; клиент не запускает собственный A-Life, который меняет факты мира.
- Вблизи игрока: полноценный skinned mesh, анимации, IK/interaction и аудио.
- На средней дистанции: упрощённая анимация/частота обновления.
- Вдали: серверное состояние без постоянного Unity GameObject; при необходимости — дешёвые crowd/impostor представления.
- Не обновлять каждый NPC каждый кадр: визуальная частота и детализация зависят от расстояния/видимости, а сетевые данные — от серверной политики.
- Интерактивные цели, двери, лестницы, ресурсы и коллизии должны иметь стабильную связь с server entity/POI ID.

## 10. Что не внедрять преждевременно

- Не переводить весь проект на DOTS/Entities только потому, что мир большой. Сначала профилировать текущую GameObject-архитектуру, использовать pooling, batching, LOD и ограничение активных объектов. DOTS рассматривать для конкретных измеренных bottleneck.
- Не использовать один гигантский Unity Terrain/Scene на весь мир.
- Не держать все дальние коллайдеры, NPC и физические объекты активными.
- Не делать клиентскую генерацию игрового рельефа, ресурсов или препятствий, отличную от серверной.
- Не превращать горы/границу карты в невидимую окружность или запретный wall collider.
- Не считать Addressables заменой серверной системе чанков и не блокировать кадр через WaitForCompletion.

## 11. План внедрения по этапам

1. **Надёжность координат:** единый adapter global E/N/U ↔ local origin; тесты precision и origin shift.
2. **Один серверный чанк:** построить terrain mesh, нормали, дороги, воду, POI; проверить швы со всеми четырьмя соседями.
3. **Streaming controller:** lifecycle, request deduplication, cancellation, hysteresis, preload/unload budgets и диагностика.
4. **LOD:** ближний/средний/дальний рельеф, здания, лес, трава; проверить pop-in и silhouette continuity.
5. **Physics tiers:** только ближние коллайдеры, серверная проверка движения, перевалы/склоны/порталы.
6. **Spaces:** один двухэтажный дом со лестницей, затем подвал и пещера; непрерывная E/N/U геометрия.
7. **NPC presentation tiers:** near/mid/far без локального изменения серверного поведения.
8. **Lighting/assets:** APV streaming, Addressables, mipmap streaming и профили памяти.
9. **Stress tests:** быстрый бег/лошадь, телепорт, несколько игроков, reconnect, границы чанков, долгий сеанс и нехватка памяти.

## 12. Обязательная телеметрия и критерии

Собирать runtime dump с:
- активными/запрошенными/строящимися/выгружаемыми ячейками;
- временем network fetch, mesh build, collider build и activation;
- количеством GameObjects, renderers, batches, triangles и colliders;
- CPU/GPU frame time, GC alloc, memory по meshes/textures/audio;
- количеством запросов, отмен, stale responses и ошибок чанковых швов;
- расстоянием до local origin и числом origin shifts;
- видимыми/LOD-уровнями NPC и vegetation.

Минимальные тесты: четыре стороны шва terrain chunk, одинаковые данные после reconnect, быстрый переход через несколько чанков, unload/reload без дубликатов, стабильность origin shift, отсутствие дальних коллайдеров, лестница между уровнями, перевал через горы и серверный отказ только на отвесной скале.

## 14. Реализация первого фундамента (16.11.2026)

Добавлены в клиент:
- `WorldOriginState` — чистая double-precision модель глобального origin, обратимые global/local преобразования и политика rebasing на сетку 256 м по горизонтали / 64 м по вертикали при выходе за порог 2048 м.
- `WorldChunkStreamingPolicy` — детерминированный порядок запросов квадратного окна чанков (центр первым, затем ближайшие) и единая проверка retention halo.
- `WorldOriginStateCheck` и `WorldChunkStreamingPolicyCheck` — regression checks; включены в Unity-independent CI.
- Существующий `VerticalSliceController` теперь использует общую streaming policy для планирования запросов и выгрузки чанков.

**Ограничение этой итерации:** `WorldOriginState` пока является проверенным координатным ядром, но ещё не перемещает Unity Transforms. Нельзя объявлять runtime floating-origin включённым до атомарной интеграции со всеми presentation roots, камерой, физикой, NPC и audio. Текущий игровой клиент продолжает использовать settlement-local frame для активной сцены. Следующая итерация должна подключить origin coordinator и проверить переход через границы поселений/чанков.
